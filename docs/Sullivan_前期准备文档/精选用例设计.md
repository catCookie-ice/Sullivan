## 核心创新用例 ⭐

### UC-核心 全景分割视觉辅助出行

| 项目 | 内容 |
|------|------|
| **用例名** | 全景分割视觉辅助出行 |
| **参与者** | 受护人（视障人士，已佩戴摄像头设备） |
| **前置条件** | 受护人已开启出行辅助模式，摄像头正常工作，网络连通 |
| **后置条件** | 无（实时持续服务） |

**基本流程（每帧处理循环）：**

1. 受护人佩戴的摄像头以固定帧率采集前方实时画面
2. 系统将画面帧发送至 `model-service` 进行全景分割推理
3. 全景分割模型输出像素级分类结果：
   - 识别障碍物类别（车辆/行人/台阶/路障/坡道/柱子等）
   - 生成各物体的分割掩码
4. 空间分析模块计算各障碍物的：
   - 相对距离（近/中/远）
   - 方位角（左前/正前/右前）
   - 运动趋势（静止/靠近/远离）
5. 根据当前场景生成语音引导指令：
   - **前方无阻碍** → _"前方安全，可直行"_
   - **前方有障碍** → _"前方约 2 米有台阶，请减速"_
   - **侧方有动态物体** → _"左侧有行人正在靠近"_
   - **路口场景** → _"前方是路口，直行通过"_
6. 语音指令通过 `notification-service` 合成音频并播报
7. 进入下一帧处理循环

**备选流程：**

- **2a** 网络延迟/帧丢失 → 使用上一帧的分析结果，提示"信号不稳定"
- **3a** 模型置信度低于阈值 → 生成保守提示（_"前方可能有障碍，请小心"_）
- **5a** 连续多帧无变化 → 降低播报频率，避免持续重复干扰

**技术指标：**

| 指标 | 要求 |
|------|------|
| 帧率 | ≥ 15 FPS |
| 分割模型延迟 | ≤ 100ms |
| 语音播报延迟 | ≤ 200ms（从帧采集到播报） |
| 最小可识别物体 | 20cm × 20cm |
| 距离提示精度 | ±0.5m |

## 一、用户域

### UC-01 监护人绑定受护人

| 项目 | 内容 |
|------|------|
| **用例名** | 监护人绑定受护人 |
| **参与者** | 监护人（已登录） |
| **前置条件** | 监护人和受护人均已注册，受护人未被绑定或可额外绑定 |
| **后置条件** | 绑定关系写入 `guardian_protectee`，受护人 `primary_guardian_uid` 更新 |

**基本流程：**

1. 监护人输入受护人的 UID 或手机号发起绑定请求
2. 系统校验受护人是否存在
3. 若受护人尚无主监护人，将当前监护人设为主监护人
4. 写入 `guardian_protectee` 绑定记录
5. 返回绑定成功

**备选流程：**

- **2a** 受护人不存在 → 返回错误提示
- **3a** 受护人已有主监护人 → 仅写入 `guardian_protectee` 作为额外监护人
- **3b** 绑定关系已存在 → 返回重复绑定提示

---

### UC-02 受护人触发安全报警

| 项目 | 内容 |
|------|------|
| **用例名** | 受护人触发安全报警 |
| **参与者** | 受护人（已登录） |
| **前置条件** | 受护人已绑定至少一个监护人 |
| **后置条件** | 报警通知推送至所有绑定的监护人 |

**基本流程：**

1. 受护人通过语音指令或物理按键触发报警
2. 系统获取受护人实时位置
3. 查询受护人绑定的所有监护人
4. 调用 `notification-service` 推送报警通知（含位置信息）
5. 记录报警日志

**备选流程：**

- **3a** 无绑定监护人 → 系统自动查找附近志愿者并广播求助
- **4a** 监护人不在线 → 转为短信/电话通知（视集成情况）

## 二、商户/机构域

### UC-03 商户创建AI客服

| 项目 | 内容 |
|------|------|
| **用例名** | 商户创建AI客服 |
| **参与者** | 商户管理员（已登录） |
| **前置条件** | 商户已注册且认证有效 |
| **后置条件** | `service_staff` 新增一条 `is_ai=1` 的记录，`ai_staff_config` 新增对应配置 |

**基本流程：**

1. 商户进入AI客服管理页面，点击创建
2. 填写客服名称、选择模型、设置人设（自定义/预设）、工作时间段、日限额
3. 系统校验 `ai_wallet` 余额是否足以支付最低钱包余额要求
4. 创建 `service_staff`（`type=0, is_ai=1`）和 `ai_staff_config`
5. 返回创建成功

**备选流程：**

- **3a** 余额不足 → 提示充值后再创建
- **4a** 选择的模型 `available_for_merchant=0` → 拒绝创建

---

### UC-04 商户充值

| 项目 | 内容 |
|------|------|
| **用例名** | 商户充值 |
| **参与者** | 商户（已登录） |
| **前置条件** | 商户已注册 |
| **后置条件** | `recharge_record` 新增记录，`ai_wallet` 余额增加 |

**基本流程：**

1. 商户选择充值金额并提交
2. 系统创建充值记录（状态：待支付）
3. 商户完成支付（对接第三方支付）
4. 系统收到支付回调，更新充值记录状态为已支付
5. `ai_wallet` 增加对应金额
6. 写入 `wallet_transaction`（type=0, 收入）

**备选流程：**

- **3a** 支付超时/取消 → 充值记录标记为已取消

### UC-05 机构发布志愿活动

| 项目 | 内容 |
|------|------|
| **用例名** | 机构发布志愿活动 |
| **参与者** | 机构管理员（已登录） |
| **前置条件** | 机构已注册且认证有效 |
| **后置条件** | `volunteer_activity` 新增记录 |

**基本流程：**

1. 机构填写活动信息（标题、描述、地点、时间、人数上限）
2. 系统创建活动，状态为"招募中"
3. 活动到达开始时间 → 状态自动变为"进行中"
4. 活动到达结束时间 → 状态变为"已结束"
5. 活动结束后自动创建活动群（`conversations`, `type=1`）
6. 所有报名通过的志愿者自动加入群聊

**备选流程：**

- **2a** 信息不完整 → 提示必填字段

### UC-06 AI客服自动回复

| 项目 | 内容 |
|------|------|
| **用例名** | AI客服自动回复 |
| **参与者** | 用户（已登录）、AI客服 |
| **前置条件** | 商户已创建并启用AI客服，`ai_wallet` 余额足够 |
| **后置条件** | 消息写入 `messages`，`wallet_transaction` 实时扣费，`model_usage_log` 记录调用 |

**基本流程：**

1. 用户在客服对话中发送消息
2. 系统判断当前时段是否匹配AI客服工作时间段
3. 查询 `ai_staff_config` 获取模型、人设、日限额等配置
4. 检查当日已消耗 Token 是否超过 `daily_max_tokens`
5. 调用 `model-service` 请求 LLM 推理
6. 计算本次消耗 Token 数和费用
7. 检查 `ai_wallet` 余额是否足够扣除
8. 实时扣除 `ai_wallet`，写入 `wallet_transaction`
9. 写入 `model_usage_log`（caller_type=0 AI客服）
10. AI客服回复写入 `messages` 并推送给用户

**备选流程：**

- **2a** 不在工作时间段 → 提示"当前非AI客服工作时间"，转人工客服（如有）
- **4a** 已达日限额 → 提示"今日额度已用完"，转人工客服
- **7a** 余额不足 → 提示"商户AI客服余额不足"，转人工客服

## 三、交易域

### UC-07 用户下单购买商品

| 项目 | 内容 |
|------|------|
| **用例名** | 用户下单购买商品 |
| **参与者** | 用户（已登录） |
| **前置条件** | 商品状态为"上架"，库存充足 |
| **后置条件** | `order` 和 `order_item` 新增记录，库存减少 |

**基本流程：**

1. 用户浏览商品并加入购物车
2. 用户提交订单
3. 系统校验库存并锁定
4. 计算订单总价（商品价格 × 数量）
5. 创建订单（状态：待支付）
6. 用户支付完成
7. 订单状态变更为已支付
8. 通知商户发货

**备选流程：**

- **3a** 库存不足 → 提示并取消订单
- **6a** 支付超时 → 订单自动取消，释放库存

### UC-08 用户评价商品

| 项目 | 内容 |
|------|------|
| **用例名** | 用户评价商品 |
| **参与者** | 用户（已登录） |
| **前置条件** | 用户已购买该商品且已确认收货，未评价过（初次评价） |
| **后置条件** | `product_review` 新增记录 |

**基本流程：**

1. 用户在订单详情页点击评价
2. 选择评分（1-5星）并填写评价内容
3. 系统校验该用户是否购买过该商品
4. 校验该用户对该商品是否有未完成的初次评价
5. 写入 `product_review`（`review_type=0`）

**备选流程：**

- **3a** 未购买过 → 拒绝评价
- **4a** 已评价过 → 提示已评价
- **追评流程**：初次评价一周后 → 用户可再次评价（`review_type=1, parent_review_id=原评价ID`）

---

### UC-09 用户评分商户

| 项目 | 内容 |
|------|------|
| **用例名** | 用户评分商户 |
| **参与者** | 用户（已登录） |
| **前置条件** | 用户在该商户至少完成过一次购买 |
| **后置条件** | `merchant_rating` 新增或覆盖评分记录 |

**基本流程：**

1. 用户在商户页面或订单完成后点击评分
2. 选择评分（0.0-5.0）
3. 系统校验用户是否在该商户购买过商品
4. 查询该用户是否已评过分：
   - 已评过 → 覆盖旧评分
   - 未评过 → 新增评分
5. 写入 `merchant_rating`

**备选流程：**

- **3a** 未购买过 → 拒绝评分

## 四、抽成与结算域

### UC-10 月度抽成等级更新

| 项目 | 内容 |
|------|------|
| **用例名** | 月度抽成等级更新 |
| **参与者** | 系统（定时任务） |
| **前置条件** | 到达 `next_commission_update_at` |
| **后置条件** | 各商户的 `commission_tier_id` 更新，`next_commission_update_at` 设为下月 |

**基本流程：**

1. 定时任务触发月度结算
2. 对每个商户计算上月评分均值（`merchant_rating`）
3. 根据评分匹配 `commission_tier` 等级
4. 计算钻石商家（评分+销售额 TOP N）
5. 检查爱心商家认证状态
6. 更新商户表的 `commission_tier_id` 和 `next_commission_update_at`
7. 新注册商户满一个月 → 按评分归入对应等级

**备选流程：**

- **2a** 商户无评分 → 保持当前等级
- **5a** 认证过期 → 降级到对应评分等级
