# SullivanMINI 开发日记：2026-10-24

**开发主题:** 修复「已登录后冷启动仍需手动选角色」
**适用范围:** SullivanMINI `[MINI]`，仅 `client-android/client-guardian`（不改服务端、不改受护人端）
**关联待办:** 无（`18`/`19`/`20` 登记的都是新能力，本条是既有缺陷）

## 1. 现象与定性

**现象：** 监护人 / 志愿者登录成功后，杀掉进程重新打开应用，账号明明还在
（重开后又直接是主页），但过程里仍然要被要求先选一次「监护人 / 志愿者」，
而选哪一张卡对已经登录的账号**不产生任何作用**。

**定性：这是一个交互缺陷，不是权限缺陷。** 服务端身份始终取自 JWT，
角色入口上那张卡片从来没有提升过任何权限 —— 它只是决定登录页的
标题文案（`LoginActivity.applyRoleHint`）。问题在于：这个「不产生作用」的
选择，被摆在了每一次冷启动都必经的位置上。

## 2. 根因

```
LAUNCHER = RoleEntryActivity ──(卡片)──> LoginActivity ──(isLoggedIn)──> Home
                ↑
          每次冷启动都从这里进，且完全没看登录态
```

`RoleEntryActivity` 的 `onCreate` 只做了 `setContentView` + 两个点击监听，
**没有任何登录态判断**；而 `LoginActivity.onCreate` 里有一句
`if (session.isLoggedIn()) { goHome(); return; }`。两段合起来的效果是：
冷启动 → 角色入口（无用的选择）→ 登录页（被瞬间跳过）→ 主页。

也就是说 `LoginActivity` 已经知道「已登录就直进主页」，但它的上游没把
这个结论接上。

## 3. 改动

### 3.1 角色入口：已登录直接进主页

`RoleEntryActivity.onCreate` 在 `setContentView` **之前**判断
`SessionStore.isLoggedIn()`，为真则 `startActivity(LoginActivity.homeIntentFor(this))`
并 `finish()`。先判断后建视图，是为了不闪一下「选择你的角色」。

这里**不判令牌是否仍然有效**：那需要一次网络请求，而本页的职责只是决定
先给用户看哪一屏。令牌失效由各页面收到 `401` 时自行处理，与本页无关。

### 3.2 落地页判定收敛成一份纯函数

`LoginActivity.homeIntentFor` 原先自己写着 `roles.contains(...)` 的分支，
而角色入口页若也要分流，很容易再写一份 —— 两份实现各自演化，正是
「登录一次去主页、冷启动又回入口」这类问题的成因。

新增 `ui/roleentry/HomeRoute`：

| 方法 | 用途 |
|---|---|
| `isVolunteerOnly(Iterable<String>)` | 只有「是志愿者且不是监护人」才去志愿者主页；兼任、空角色、未知角色一律监护人主页 |
| `describe(Iterable<String>)` | 入口页上的角色描述（`监护人` / `志愿者` / `监护人 · 志愿者`） |

`LoginActivity.homeIntentFor` 改为调用它，仍是**唯一**的落地页判断点
（账密登录、注册后自动登录、已登录直进、冷启动四条路径共用）。

**不看入口提示的理由**（`HomeRoute` 类注释里的原话）：`EXTRA_ROLE_HINT` 是
用户在卡片上点的那一下，服务端 `roles` 才是身份。要记住「上次从哪张卡进的」
就得额外存一个状态，而这个状态与 roles 可能互相矛盾（志愿者身份被撤销后，
记着的那条提示仍指向志愿者主页）。按 roles 分流没有这个不一致面。

### 3.3 顺带修掉的一处连带问题

`GuardianActivity` / `VolunteerHomeActivity` 发现本地没有登录态时，原来是
`startActivity(new Intent(this, LoginActivity.class))`。在 §3.1 之后，**
本地没有登录态**意味着登录页会正常显示表单，所以这条路径本身没问题；
但**从角色入口冷启动进来**时，登录页仍在栈里，直接再开一个会叠出
「返回键回不去的孤页」。改为 `LoginActivity.toRoleEntry(this)`
（`CLEAR_TOP | SINGLE_TOP`）：回到栈里那一层角色入口，并复用为新实例，
不留下上一次点错的角色提示。

### 3.4 新增 `LoginActivity.EXTRA_FORCE_FORM` / `reauthIntentFor`

登录页原先只有「已登录就跳主页」一条路。加上 §3.1 之后，如果将来某个页面
需要在 401 之后把用户送回登录框，调用方拿到的会是一个立刻自己关掉的页面。
新增的 extra 让调用方明确要求「显示表单」，**本次没有调用方**（各页面目前都是
清登录态 + 提示，不跳转，见 `17-开发日记-2026-10-18` §5 已知风险）。
登记在这里，是为了下一个写这类入口的人不必重新发现这个坑。


测试基线：本次之前本工程为 49 例，本次新增 `HomeRouteTest` 6 例，**55 例全绿**。

`HomeRouteTest` 覆盖：监护人 → 监护人主页；纯志愿者 → 志愿者主页；兼任 → 监护人主页
（两种集合顺序）；空/未知/大小写不符 → 监护人主页；`describe` 四种组合；
任意 `Iterable` 实现（Gson 反序列化出的 `Set` 具体类型不保证）。

## 5. 未验证的部分（**本节照例是本次最需要注意的地方**）

- **没有真机/模拟器运行**。判定逻辑由单测钉住，但「冷启动时是否真的直接进主页、
  有没有闪一下角色入口」只能在设备上确认。`RoleEntryActivity` 里那条
  「先判断再 setContentView」的注释，就是本次唯一无法用单测证明的假设。
- 没有验证 `FLAG_ACTIVITY_CLEAR_TOP` 在本应用栈里的实际表现（§3.3）。
- 本次只改 `client-guardian`。**受护人端 `client-protectee` 的情况不同，不需要同类修复**：
  它的 `ProtecteeHomeActivity` 直接作 LAUNCHER，本来就没有角色入口页
  （见 `17-开发日记-2026-10-18-受护人端拆分` §3.2）。

## 6. 人工验证清单（**待执行**）

1. 监护人账号登录 → 看到监护人主页 → 后台杀掉应用 → 重开：**直接进监护人主页**，
   不应出现「选择你的角色」。
2. 纯志愿者账号重复第 1 步：直接进志愿者主页。
3. 兼任账号（roles 含 `GUARDIAN` 与 `VOLUNTEER`）：直接进监护人主页，
   「申请兼任志愿者」卡片应当隐藏。
4. 在主页点退出登录：回到**角色入口页**（能选卡片），而不是被弹回主页。
5. 全新安装 / 退出登录后冷启动：正常显示角色入口页。
6. 清空本地数据（或令牌被服务端判失效后重开）：能回到角色入口页而不是卡死。

## 7. 与既有文档的关系

- `00` §4.2「Android 登录前必须提供角色选择入口」**未被违反**：
  入口页仍是未登录时的必经一屏，本次改动只是让已登录的账号跳过它 ——
  那句话管的是「登录前」。
- `00` §7 第 7 条「Android 三角色入口…均可到达各自核心功能」同样不受影响
  （本应用现在只有两个角色，受护人端已拆为独立应用）。
- 本条不是 `16` §1 的 `[FULL]` 预留点，也不与 `18`/`19`/`20` 的条目重叠，
  因此没有向那些台账登记。
