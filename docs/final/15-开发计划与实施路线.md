**文档版本:** v2.1

**前置决策:** `06-系统架构设计.md`、`13-技术栈选型与架构决策.md`

## 1. 计划原则

项目按 1 人、毕业设计、18 个阶段推进。阶段 1-15 开发，阶段 16-18 用于论文和答辩。计划优先保证“能演示的端到端链路”，不再为多个服务分别搭建骨架。

范围优先级仍为：P0 身份、绑定、导航、报警与安全降级；P1 公益闭环、语音指令和通知；P2 管理统计与界面细节。时间不足时按 P2、P1 顺序降级，P0 不裁剪。

## 4. 数据迁移计划

1. 将 `docs/final/db/schema.sql` 统一为一个 `sullivan` 数据库。
2. 当前 Java 身份迁移为 `db/migration/V1__registration_identity.sql`；旧 `user`、`navigation`、`welfare`、`admin` 目录仍待清理或合并。
3. Java 应用启动时执行 Flyway；本机真实验证已确认 V1 能在已有表结构上完成兼容迁移；Python 不执行迁移，只使用已存在的导航表。
4. 删除旧的四 schema 初始化、旧迁移目录和服务名引用前，先在空库执行一次完整基线并保存日志。
5. M1 以后只允许追加新的 Flyway 版本，不再直接修改已执行版本。

## 5. 扩展边界

允许保留模块接口、配置项和命名空间，但不能预先实现商业、聊天、视频、AI 客服或支付。未来扩展应新增 Java 模块或独立应用，并通过 `00` §8 变更流程进入范围；当前 Java 单体不因未来扩展而提前拆分。

## 6. 风险控制

| 风险 | 应对 |
|---|---|
| Python 推理性能不足 | M1 先做 GPU/CPU 基准，固定模型与分辨率后再做业务链路 |
| Java 单体代码膨胀 | 按领域包隔离，Controller、Application、Domain、Infrastructure 分层 |
| 两端 JWT 配置不一致 | 共用 `.env` 中的密钥、发行方和过期配置，加入跨端令牌测试 |
| 单库权限边界模糊 | Java 作为业务唯一写入方；Python 只操作导航表并限制 SQLAlchemy 模型 |
| Web 工作量过大 | 每个 Java 能力完成后立即补对应页面，M14 只做统一和治理页面 |
| 论文挤占开发时间 | M1 保存基准数据，M4 保存算法图和样例，M15 保存验收证据 |

## 8. 每阶段自检

1. 该阶段需求是否有正常、异常和越权测试。
2. 是否新增了服务、数据库、消息中间件或 `[FULL]` 业务入口。
3. Java/Python 的职责是否仍符合 `06` 的边界。
4. 单库迁移是否能在空环境重复执行。
5. 本阶段是否留下了可运行的演示链路或可验证的测试证据。
