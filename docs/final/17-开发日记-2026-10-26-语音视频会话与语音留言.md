# 开发日记 2026-10-26：语音/视频会话、摄像头共享与语音留言

**本次范围:** `[MINI]` —— 把「视频与摄像头共享」从 `[FULL]` 整体提升为 `[MINI]`，
新增语音留言；顺带把「用户可见标识」从 uuid 换成登录名，并按角色裁剪客户端入口。

**涉及端:** 服务端、`client-android/client-guardian`、`client-android/client-protectee`、`client-web/**`

## 1. 这一轮到底改了什么

用户提了四件事，它们看起来无关，其实是同一个问题的四个面：

> 监护人和受护人之间发起会话应该是语音会话、视频通话，或者监护人获取受护人的摄像头画面
> （这期间同样有语音通话）；紧急会话是视频通话。此外新增一个语音留言功能。

拆开来是：

| # | 需求 | 落地 |
|---|---|---|
| 1 | 会话要有形态：语音 / 视频 / 摄像头 | `realtime_session.session_type` 从只有 `BASIC` 扩到 `BASIC/VOICE/VIDEO/CAMERA/EMERGENCY` |
| 2 | 摄像头会话里也要能说话 | `CAMERA` 的媒体流是「受护人上行音视频、监护人只下行」，不是「只要视频」 |
| 3 | 紧急会话是视频通话 | 报警派发的会话改为 `EMERGENCY`，客户端按 `VIDEO` 处理 |
| 4 | 新增语音留言 | 新表 `voice_message` + 5 个接口 + 两端界面 |
| 5 | 按角色裁剪入口 | 受护人端去掉「公益活动」；两端「发起绑定」只留本角色方向 |
| 6 | 简化发起会话的流程 | 接收方点一次「接听」即进入会话 |
| 7 | 用户可见的地方不再出现 ID | 新增按登录名查找；绑定/会话/留言响应都带回双方名字 |

`5/6/7` 是用户在同一条需求里点名的，理由都是同一句：「注意各个角色直接的功能分布」。

## 2. 媒体通道：为什么是 WebRTC + TURN

这是本轮唯一一个真正需要做技术选型的地方。两个候选：

| 方案 | 代价 | 结果 |
|---|---|---|
| WebSocket 子协议中继音视频帧 | 服务端要转发每一帧音视频；两路 640×480 大约 1.5 Mbps，一台服务器撑不了几个并发；而且**服务端会持有全部通话内容** | 否 |
| WebRTC（P2P，跨网时经 TURN 中转） | 需要 TURN 服务器（coturn）；Android 要引 WebRTC SDK；信令要自己做 | **采用** |

选 WebRTC 的核心理由不是性能，而是**服务端不该持有通话内容**。中继方案里，服务端
每一帧都经手，等于它天然具备录音录像的能力与嫌疑；WebRTC 里服务端只转发 SDP 与
ICE 候选，媒体流根本不经过它。这一条也写进了 `16-扩展点登记表.md` 的 N-03：
**媒体永不落库**。

### 2.1 信令为什么复用现有的 `signal` 类型

新增了一个 WebSocket 信封类型 `signal`，与原有的 `relay` 并列：

```
{"type":"signal","sessionId":"rs_x","fromUid":"u_a","toUid":"u_b",
 "payload":{"kind":"offer","sdp":"v=0..."}}
```

`kind` 限定在 `offer/answer/candidate/hangup/renegotiate` 五个值里。**为什么要限死**：
不限的话这条通道就变成任意 JSON 透传，等于给了一个绕过其余所有校验的自由通道。

`signal` 比 `relay` 多一条前置条件：**会话必须已经 ACTIVE**。理由写在
`RealtimeWebSocketHandler` 的类注释里 —— 会话还停在 `REQUESTED` 时交换候选，
只会让两端各建一条连不通的 PeerConnection，然后各自显示「正在接通」。

**服务端不解析 SDP。** 它只检查「有 type、有 payload、payload 是个对象、kind 在白名单里」，
然后原样转发。理由有两条：解析 SDP 意味着服务端要知道每种浏览器/手机的编码组合细节，
而这份知识每个通话版本都会变；更重要的是 **SDP 里带着候选 IP 与网络拓扑**，落库或记日志
等于把用户的网络环境写成了永久记录。

### 2.2 TURN 凭据：短时有效，且不能假装没有

`GET /api/v1/realtime/ice-servers` 返回 STUN/TURN 配置。配了 TURN 时给的是**短时凭据**：

```
username   = <过期时间戳>:<uid>
credential = base64(HMAC-SHA1(turn_secret, username))
```

这是 coturn 的 REST API 约定。静态 secret 只留在服务端配置里，**从不下发**；客户端拿到的
用户名本身就带过期时间，所以它不能被缓存到本地长期复用。

**没配 TURN 时会怎样**：`urls` 只有 STUN，`username`/`credential` 为空。此时两端在同一
局域网还能靠本机候选直连，跨网几乎必然失败。客户端在这种情况下的行为被明确要求：
**如实提示「没有可用的中转服务器，跨网络可能无法接通」**，而不是显示成「已接通」。

这条在 `RealtimeCall` 里有两处实现：
- `start()` 时如果一个 ICE 服务器都没有，报一条 error；
- `onConnectionChange(FAILED)` 时提示「可能是网络受限（缺少中转服务器）」，而不是
  「对方挂断了」。

## 3. `CAMERA` 的方向：由角色定，不由「谁发起」定

这是本轮最容易写错的一处。三种媒体形态里，`VOICE`/`VIDEO` 是对称的，`CAMERA` 不是：

| 会话类型 | 受护人端 | 监护人端 |
|---|---|---|
| `VOICE` | 上行音频 + 下行音频 | 上行音频 + 下行音频 |
| `VIDEO` | 上行音视频 + 下行音视频 | 上行音视频 + 下行音视频 |
| `CAMERA` | **上行音视频** + 下行音频 | **只下行**（不采集任何东西） |
| `EMERGENCY` | 同 `VIDEO` | 同 `VIDEO` |

「监护人必须不上行摄像头」不是优化，是产品定义：他是去看人的，不是把自己的画面
送回给一个看不见屏幕的人。

第一版实现里我按「谁发起会话」决定方向（`iAmInitiator ? CAMERA_SEND : CAMERA_RECEIVE`），
这是错的：监护人主动「看看家里」时，发起方是监护人，代码会把摄像头开在监护人手机上 ——
正好是反的。改成按**角色**判断：受护人永远是拍的那一侧，监护人永远是看的那一侧。

客户端两层都做了这件事：
- 服务端 `02` §8.2 把「方向」写成了 `CAMERA` 的约束之一；
- Android `RealtimeCall.Mode` 用四个枚举值把「谁拍/谁看」写进类型，而不是在运行时猜
  `getUserMedia` 有没有拿到摄像头。

## 4. `EMERGENCY` 为什么客户端不能创建

`POST /realtime/sessions` 的白名单是 `BASIC/VOICE/VIDEO/CAMERA`。客户端传 `EMERGENCY`
会得到 **403「紧急会话只能由报警自动发起」**。

这条看着像是「少给了一个选项」，但反过来做会毁掉这个标记的全部信息量：

- 如果客户端能自己打上 `EMERGENCY`，它就只是「一个更吓人的标签」，任何人都能给自己
  的会话贴上，于是它不再表示任何事；
- 只有**只能由服务端在报警派发路径上写入**，它才等于「这条会话来自一次真实的求助」，
  监护人看到它时才敢把它当成优先级判断的依据。

对应地，`RealtimeAlertDispatcher` 建的会话从 `BASIC` 改成了 `EMERGENCY`，
并且自动会话在客户端按 `VIDEO` 处理（`mediaModeOf` 里 `"VIDEO", "EMERGENCY"` 共用一个分支）。

## 5. 语音留言：为什么它不是「一个更短的会话」

| 维度 | 实时会话 | 语音留言 |
|---|---|---|
| 双方是否要同时在场 | 要 | 不要 |
| 媒体是否落库 | **不落** | **落库**（音频对象 + 元数据） |
| 绑定解除后 | 立即无法连 | **历史音频也取不回** |
| 通知内容 | 无 | 只有「有一条留言」，不含音频与地址 |

第三行是这一块最要紧的设计。`VoiceMessageService.audio()` **每次取音频都重新校验
双方仍有 ACTIVE 绑定**，而不是「上传时校验过一次就够了」。理由很直接：解绑要收回的是
**能力**，不只是「不再新增」。否则「解除绑定」只断了一条路，对方仍能听过去留下的全部录音。

配套的几条：
- **不签发预签名 URL**。签名地址一旦发出去就收不回来，解绑之后它还能用。音频经
  `GET /voice-messages/{id}/audio` 流式转发，响应带 `Cache-Control: no-store, private`。
- **通知里不带音频、不带对象键、不带 URL**，只有一句提示。
- **对象键里不含 uid**：`voice/yyyy/MM/dd/<id>.m4a`。存储日志与目录列表会泄露键，
  把 uid 编进去等于在这些地方暴露「谁给谁留过言」。
- 白名单只收 `audio/mp4`、`audio/aac`、`audio/3gpp`、`audio/amr`、`audio/ogg`。这既是
  格式约束，也是一道**上传即任意文件**的防线。

`MediaStore` 抽了一层接口，`app.media.store=filesystem|minio` 二选一，默认
`filesystem`（`./data/media`）。**为什么默认不是 MinIO**：开发机不一定起了 MinIO，
而「先装一个对象存储才能试语音留言」会让这个功能在本地根本跑不起来。生产切
`app.media.store=minio` 即可，代码路径一致。

## 6. 用户可见标识：ID → 登录名

用户的原话：

> 将用户这边所有需要用到用户ID的地方改为使用用户账户，即登录名。
> 用户ID只用作服务器的唯一性检验等不面向用户的地方。

落地成三条硬规矩（已写进 `00` §7 第 11 条、`01` FR-26、`16` N-15）：

1. 界面上**显示**的人一律用 `displayName`，没有时回落到 `loginName`；
2. 界面上**输入**的查询键是 `loginName`，**不是** uid；
3. uid 只在提交参数、日志与唯一性约束里出现。

为此服务端做了三件事：
- 新增 `GET /users/by-login-name/{loginName}`（**精确匹配**）。不做模糊匹配：模糊匹配
  等于把「谁能被搜到」做成了一个功能，可以拿来枚举用户名录。找不到时统一 404 +
  同一句话，避免用提示语的差别探测账号是否存在。
- `BindingResponse` 补 `guardianLoginName/protecteeLoginName/guardianName/protecteeName`；
- `SessionResponse` 补 `initiatorLoginName/targetLoginName/initiatorName/targetName`。

第二条同时解决了一个 N+1：`20-待办` 里 UX-05 原本担心「选择器只能显示 UUID，
除非客户端对每条绑定再打一次 `GET /users/{id}`」。名字随绑定响应直接回来，就不用打了。
`BindingService.listMyBindings` 里的做法是**批量**载入账号与资料（一次 `selectBatchIds`
+ 一次 `selectList`），而不是逐条查。

## 7. 客户端按角色裁剪：做了什么、为什么

用户点名了两处，实际检查下来是四处：

| 位置 | 改前 | 改后 |
|---|---|---|
| 受护人端主页 | 有「公益活动」卡片 | **删除**（连带删掉布局里的卡片与代码里的绑定） |
| 两端「发起绑定」页 | 同时有「以监护人身份绑定受护人」和「以受护人身份申请监护人」 | 各自只留本角色那一个方向 |
| 两端会话页 | 手输「对方账号 ID」 | 下拉选已绑定的人 + 选通话方式 |
| 两端会话流程 | 接受 → 回列表 → 再点连接 | 点一次「接听」直接进会话 |

「公益活动」删掉之后 `ActivityListActivity` 在受护人端变成了没有入口的类。
第一版我把它留着，理由是「`client-web/protectee-web` 那边还有活动页」。这个理由不成立：
**没有入口的 Activity 不是「保留能力」，只是死代码** —— 它还在 manifest 里注册着，
还能被 `adb am start` 直接拉起来，还在 APK 里占资源，还在编译测试时消耗时间，
而用户永远点不到它。所以后来整条链路都删了：Activity、两个布局
（`activity_activity_list.xml`/`row_activity.xml`）、manifest 注册项、
`ActivityDtos`、`ApiService.listActivities`、`StatusLabels.activity`、
两个测试用例、以及 17 行 `activity_*` 字符串。

**Web 端保留活动页不构成矛盾**：`00` §4.3 与 `03` §4.5 里「公益活动 `R` 公开」是
按角色授予受护人的读权限。受护人**有权看**，只是这一轮的产品决定是把 Android 的
入口收掉（用户指出「受护人端意外有本不该有的公益活动入口」）。网页那侧不受影响。
如果以后要让 Android 重新给入口，正确的做法是重新加回这整条链路，
而不是让一个没入口的类躺在包里假装还在。

## 8. 会话流程简化：一次确认，且**不会无限等待**

原来接收方要「接受 → 状态变 ACTIVE → 回列表再点连接」。中间那一步对用户没有意义：
他已经表达了「我要接」。

### 8.1 中途发现的一个真缺口：发起方收不到「对方接了」

第一版只改了接收方：点一次「接听」就直接进会话。接收方那边确实一次点击就通了，
**但发起方什么都不知道** —— 他停在「已呼叫，等待对方接听」，只能等 60 秒超时。
也就是说「只需要对方点一次确认」这条需求，在发起方那一侧并没有成立。

根因不是客户端偷懒，而是服务端从来没有推送过状态变化：`accept`/`reject`/`end`
三个方法只改数据库就返回，一条控制帧都不发。而 `RealtimeEnvelope` 的注释里
却早就写着 `session.accept/reject/end` 属于「控制」类型 —— 契约写了，实现没做。

补的时候发现还有第二层问题：**发起方在 `REQUESTED` 阶段根本没连长连接**，
他只在自己点「接通」时才连。所以就算服务端发推送，也没有通道可发。
两处都得改，缺一条都不成立：

1. 服务端 `RealtimeSessionService` 注入 `ConnectionPool`，新增 `push()`，
   在 `accept`/`reject`/`end` 之后把 `session.accepted`/`session.rejected`/
   `session.ended` 发给**另一方**（动作发起者自己已经知道结果）。
2. 客户端创建会话成功后立刻 `socket.connect(...)`，收到 `session.accepted`
   再去 REST 取回完整会话对象并进会 —— 推送信封里只有会话 ID，
   拿它当完整对象去连会让媒体形态退化成纯文字。

顺带修掉一个自己挖的坑：`RealtimeSocket.connect()` 原本无条件先 `close()`，
于是「收推送时已连的那根连接」会在随后的连接流程里被自己关掉，
等待期收到的帧全丢。现在同一条会话已连时只换监听器，不动底层连接。

**这条仍然是「尽力而为」而不是保证**：对方不在线时 `ConnectionPool.send`
什么都不做。客户端不能因此认为状态只会通过推送到达，REST 列表查询始终是准的。

### 8.2 超时兜底

改完之后有一处必须自己兜底：**发起方不能一直转圈**。服务端不会替用户挂断一条没人接的
请求，所以客户端加了 60 秒计时，到点后：

1. 显示「对方没有接听。可以稍后再试，或改用语音留言。」
2. 顺手调 `endSession` 把那条会话推到终态。

第 2 步不是锦上添花：不结束的话，那条 `REQUESTED` 会话会永远留在列表里看起来还在响，
用户以后还会去点它。

同理，通话状态只说真话：`PeerConnectionState.CONNECTED` 才显示「已接通」，
`CONNECTING` 显示「正在接通…」，`FAILED` 明确说「无法建立连接，可能是网络受限」。

## 10. 真实库验证抓到的问题（单元测试全是绿的）

这一轮在收尾时把服务端真正跑起来、连真实 MySQL、用真实账号发真实请求。结果发现了
**四个单元测试一个都没抓到的缺陷**。它们共同的成因值得写下来：

> **单元测试把 mapper 全 mock 掉了，于是没有一条 SQL 真正落到 MySQL 上。**
> 而 CHECK 约束、`DEFAULT CURRENT_TIMESTAMP`、外键、字符集 —— 这些恰恰只存在于真实库里。
> mock 出来的对象永远「合法」，也永远没有数据库填的默认值。
> 全绿的 176 个测试并不能证明这套代码能在真库上跑起来。

### 10.1 `ck_notification_type` 不认 `VOICE_MESSAGE`（500）

V8 加了语音留言，投递时会写一条 `notification_type='VOICE_MESSAGE'` 的通知，
但**忘了同步扩展那个 V3 建的老 CHECK 约束**。于是真实上传直接 500：

```
Check constraint 'ck_notification_type' is violated.  (error 3819)
```

修法是追加 **V9**（V8 已应用，改它会校验和不匹配），`schema.sql` 同步。

**教训**：新增一个枚举值，要同时改三处 —— 代码常量、`schema.sql`、以及**已有的 CHECK 约束**。
只用 `grep` 代码是查不出来的，必须对着 `information_schema.CHECK_CONSTRAINTS` 核一遍。

### 10.2 / 10.3 / 10.4 三个「`createdAt` 是 null」

语音留言的投递响应、会话创建响应、报警创建响应，三处都直接把**刚 insert 完的内存对象**
拿去拼 DTO。而 `createdAt` 是数据库 `DEFAULT CURRENT_TIMESTAMP(3)` 填的，
内存对象里始终是 `null`。表现是：**同一条记录，创建接口里没有时间，列表接口里有时间**。

本来以为只有语音留言这一处，修完顺手去核另外两个创建接口，发现一模一样。
三处都改成 insert 后重读一次再拼响应。

报警那条尤其不能留：**报警恰恰是最不能缺时间戳的一条记录**。

三处各加了一条回归测试，断言 `createdAt` 非空。这些测试在修复前会失败，
在修复后通过 —— 但**注意它们能生效，是因为测试里给 `selectById` 打了桩**，
真实环境下这个桩就是那一次真实的回查。

### 10.5 真实验证还确认了这些（都是好消息）

- `session.accepted` / `session.ended` 通过真实 WebSocket **确实收到了**，
  发起方不再需要轮询才发现对方接了。
- 解绑后监护人取音频返回 **403**「双方绑定已解除，不能再取回该留言」，
  发起会话与投递新留言同样 403 —— 「解绑要收回能力」这条不是空话。
- 客户端传 `EMERGENCY` 返回 **403**；报警自动派发则真的建出了一条
  `EMERGENCY` 会话（受护人发起、监护人接收）。
- 留言全生命周期：上传 201 → 留言箱（含双方登录名/显示名/时间）→ 取音频 200 →
  标记已听 → 发送方标记已听被拒 403 → 删除 204 → 删除后取音频 404。
- 无令牌取音频 401。

## 11. 这一轮**没有**做的事

诚实列出来，避免下一个人以为它们已经做了：

- **TURN 服务器没有部署**。代码路径、凭据算法、客户端的诚实提示都到位了，但本机没有
  coturn，所以 `app.webrtc.turn-secret` 是空的，实际只能走 STUN 直连。跨网通话**现在
  连不上**，且界面会如实说「没有可用的中转服务器」。
- **语音留言没有端到端真机验证**。接口层已经在真实服务 + 真实库上验过（见 §10.5），
  但**录音 → 上传 → 取回 → 播放**这条链路涉及 Android 的录音权限、编码器、
  `MediaPlayer`，这些只在代码层面走通，没有在真机上按过一次。
- **`EMERGENCY` 会话的界面没有单独样式**。它按视频会话处理，没有额外的「这是紧急求助」
  视觉强调 —— 那需要设计，不该我自己发明。
- **系统级推送**仍然待办（见下一节）。
