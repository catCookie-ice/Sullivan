# SullivanMINI 开发日记：2026-11-01 —— 障碍预警阈值下调、碰撞时间预测与语速

**本次改动只碰受护人端（`client-android/client-protectee`）的 `vision/` 与首页设置，
服务端与 Web 端零改动。** 语音操控（UX-01）与声纹（UX-02）仍按
`20-待办-Android客户端体验与无障碍.md` 挂着，不在本篇范围内。

## 0. 这次要解决的四个问题

用户的原话拆成四件事：

1. **减小预警阈值**，让它能播报更小的障碍；
2. **对障碍的运动做预测**，只播报"可能撞上"的；
3. **加快播报语速**；
4. **能算出相遇时间时，按时间长短排优先级**；超过一定时间就认为"暂时不会撞到"。

第 5 件事（怎么提高识别准确性 + 训练集/测试集 + 训练代码）单独成篇：
[23-障碍识别准确性与训练方案](./23-障碍识别准确性与训练方案.md)。
训练代码在 `tools/vision-training/`。

改造前的状态，用一句话概括：**"近"是一个没有单位的几何猜测，而且所有提示的
优先级都只看"近不近"，不看"还剩多久"。** `§5` 记着一件更重要的事——
那些阈值是拍的，没在真机上标定过。

## 1. 阈值：让更小的障碍进入播报

### 1.1 三个阈值，各管一段路

改之前先把"阈值"这个词拆开，否则很容易改错地方：

| 阈值 | 位置 | 作用 | 本次 |
|---|---|---|---|
| 检测置信度 | `ProtecteeActivity.CONFIDENCE_THRESHOLD` | 模型输出 → 保留哪些框 | `0.35 → 0.28` |
| "小障碍"判据 | `ObstacleAdvisor.TINY_*` | 太小的框当噪声丢掉 | 面积判据 → **高度判据** |
| 测速门槛 | `TtcEstimator.MIN_HEIGHT` | 框太小就不估尺度变化率 | `0.03 → 0.024` |

只有第一个是"预警阈值"吗？不是。三者串在一条链上：**检测不出来的框谈不上播报，
进了决策层又被当噪声丢掉的框也谈不上播报。** 只降第一个，小障碍会死在第二关。

### 1.2 检测阈值 0.35 → 0.28

小障碍在画面里只有几十个像素，置信度天然偏低。0.35 会把它们整批挡掉，而它们
恰恰是最容易绊倒人的东西。**漏报的代价是摔倒，多报一句的代价只是多听一句。**

但降阈值必然放进噪声，所以同时加了两道闸（不是"什么都不管"）：

1. `ObjectTracker.MIN_HITS = 2`：只出现一帧的框不确认。这一条本来就有，
   现在它承担更多——单帧噪声进不了播报。
2. 新增 `ObstacleAdvisor.LOW_SCORE = 0.45f` 与 `LOW_SCORE_BOTTOM = 0.68f`：
   置信度低于 0.45 的框，**只有底边落在画面下部时才保留**。远处的低分框仍然丢掉。
   理由是"虚"和"近"在画面里有相关性：贴着地面的低分框大概率是远处小目标长大了，
   而画面中上部的低分框多半是背景纹理。

### 1.3 "小障碍"从面积判据改成高度判据

改造前：

```java
// 面积 < 0.0015 且 底边 < 0.60 → 当噪声丢掉
private static final float TINY_AREA_RATIO = 0.0015f;
```

问题在于**面积对小障碍的惩罚过重**。一个 15 厘米高的路锥在 1.5 米处，宽约 0.03、
高约 0.04，面积 0.0012 —— 刚好在阈值下方，被当噪声扔掉。它不显眼，但它会绊人。

改成按高度判：

```java
private static final float TINY_HEIGHT_RATIO = 0.06f;   // 归一化高度 < 6%（约 38 px）
private static final float TINY_BOTTOM_RATIO = 0.55f;   // 且底边在画面下半
```

语义更准确：**"高度小"才是它离得远的证据，"面积小"可能只是因为它细**
（隔离柱、栏杆、路缘石都是又细又长）。同时把"靠下"的门限从 0.60 收到 0.55，
因为 0.55 以上才是真正的地面区域（`CorridorCoverage.CORRIDOR_TOP = 0.55`）。

### 1.4 测速门槛 0.03 → 0.024

`TtcEstimator` 靠拟合 `ln(框高)` 随时间的变化估尺度变化率。框太小时一个像素的
抖动就能翻转斜率符号，所以原来要求高度 ≥ 0.03（约 19 px）。

矮而薄的目标（路缘石、减速带、躺倒的共享单车）在 3 米处往往只有十几像素高，
按旧门槛永远拿不到"时间结论"，只能退回距离播报。降到 0.024（约 15 px）让它们
进入测速通道，代价交给已有的两道统计门去接：`MAX_RESIDUAL_RMS_LOG = 0.08`
（拟合不干净的样本不给结论）与 `MIN_SIGNIFICANCE = 1.5`（变化不显著的不算靠近）。

## 2. 运动预测：一个小孔成像公式就够了

### 2.1 三个量

新增 `vision/assist/CollisionModel.java`（纯函数、无状态、可在 JVM 上单测）。
它只做一件事：把"几何"和"运动"折算成同一个量——**秒**。

- `Z`：目标距离（米）。有深度模型时来自 `DistancePolicy`，没有时是 NaN。
- `λ = d(ln h)/dt`：框高的对数变化率（1/s）。`TtcEstimator` 已经在算。
- `v_ego`：用户自己的步速（m/s）。见 §2.3。

### 2.2 相遇时间：`t = Z / (v_ego + λ·Z)`

推导只有两行。小孔成像 `h = f·H/Z`，两边取对数再求导：

```
λ = d(ln h)/dt = −d(ln Z)/dt = −(dZ/dt)/Z
```

`dZ/dt` 是"目标相对我"的距离变化率，它由两件事叠加：我在走向它（`−v_ego`）、
它在走向我（自己的 `dZ/dt`）。而后者正是 `−λ·Z`。于是

```
dZ/dt = −(v_ego + λ·Z)          ⟹  t = Z / (v_ego + λ·Z)
```

这个式子好在**退化成两个已知结论**：

- 目标不动（`λ = 0`）→ `t = Z / v_ego`，即"走过去要多久"；
- 我站着不动（`v_ego = 0`）→ `t = 1/λ`，即 `TtcEstimator` 一直在算的那个 TTC。

也就是说，它不是一套新算法，而是**把已有的两条估计统一到一个量纲里**。
实现里对闭合速度设了下限 `MIN_CLOSING_SPEED = 0.05`，低于它返回
`POSITIVE_INFINITY`（"不会相遇"），而不是一个巨大的秒数——后者会让"6 秒阈值"
这种判断在数值上勉强通过，语义上却是错的。

### 2.3 步速从深度里反推：`λ·Z = v_ego`

有深度图时，静止目标的 `λ·Z` 恒等于用户步速，与距离、类别都无关。于是一帧里
所有静止轨迹的 `rawRate × meters` 取**中位数**，就是步速（`EgoSample` +
`estimateEgoSpeed`）。取中位数而不是均值，因为迎面走来的人会把均值拽高。

四道防护：

1. 只收"没被画面裁切、距离有效、拟合成功"的轨迹（贴底目标的框高停止增长，
   用它算会系统性低估步速）；
2. 少于 2 个有效样本 → 返回 NaN；
3. 上限 `MAX_EGO_SPEED_MPS = 2.6`（快走上限，超过只可能是关联错了）；
4. NaN 时退回 `DEFAULT_EGO_SPEED_MPS = 1.2`。

**为什么默认取 1.2 而不是常见的 1.0–1.1？** 因为步速被低估会让相遇时间被高估，
把"马上要撞"算成"还有时间"。宁可在站着不动时略微高估步速（多报几句），
也不要走着的时候少报一句。方向选错过一次就够贵了。

### 2.4 横向扫掠：它会不会经过我的行走线

只有"迎面靠近"还不够：从身边擦过去的人流不该一直报。判据是
`sweepsWalkingLine(centerX, halfWidth, lateralRate, horizon, meters)`：

1. 取观测窗口 `[0, min(horizon, 6)]`，把中心横坐标按 `centerX + rate·t` 外推
   （`lateralRate` 来自 `TtcEstimator` 的横向拟合，NaN 时当作静止）；
2. 体宽半宽按"人在一米处的真实角宽"折算：`BODY_HALF_WIDTH_M = 0.30` 米，
   归一化半宽 = `0.30 / (2·Z·tan(hfov/2))`，`tan(hfov/2) = 0.62`，
   夹在 `[0.02, 0.25]`；
3. 区间 `[min(x) − halfWidth, max(x) + halfWidth]` **包含 0.5** 才算会扫到。

窗口取 6 秒是因为阈值就是 6 秒；再远的外推没有统计意义（横向速度在 6 秒尺度上
早就不是常数了）。`MAX_PATH_MARGIN = 0.25` 是给"距离未知"用的：不知道多远时
宁可把路判宽一点。

### 2.5 判据表：只在"能证明安全"时才静音

| 情况 | 结论 | 播报 |
|---|---|---|
| 有 Z 或 TTC，且 `t > 6 s` | 暂时不会撞到 | **不报** |
| 有 Z 或 TTC，且 `t ≤ 6 s` | 会撞上 | 报，带秒数 |
| 有横向速度，且窗口内扫不到中线 | 会从旁边过去 | **不报** |
| 算不出时间（无深度、无 TTC、无横向速度） | 不知道 | **报**（退回旧几何判据） |

第四行是这次最关键的**保守性**约定：**预测只用来"删掉能证明安全的目标"，
绝不用来"删掉算不出来的目标"。** 一个没有深度的设备不该因为"算不出时间"而
变得沉默——那会把一次改造变成一次功能倒退。

**一处必须说清的近似。** 有深度、但尺度变化率还没拟合出来（轨迹刚建立，不到
5 帧/800 ms）时，`timeOf` 会按"目标静止"算：`t = Z / v_ego`。这对外来的目标
是**高估**（它其实在靠近），于是理论上可能被 6 秒阈值误剔除。

为什么接受这个窗口：追踪器给不出 `relativeRate` 的时间窗不超过 1 秒，而 9 米外
的目标即便以 2 m/s 闭合也需要 4.5 秒才到跟前——**误剔除只能发生在"还很远"
的那 1 秒里**，等率一到位它就会被正确报出。反过来，若在率未知时直接返回 NaN，
每一辆刚进画面的远处车都会先说一句"9米处有汽车"，那正是本次要消掉的噪声。

代价与收益的方向在这里是明确的：**晚报 1 秒** vs **每帧多报一句**。
前者的风险已经被"距离还很远"抵消，后者会直接让用户关掉语音。

还有一处容易被忽略的诚实性修正：`freeRatio`（"前方通畅度"）是从**所有**相关障碍
算的，不是只从"威胁"算的。否则"通畅"会在画面里明明有人、只是判定为擦身而过时
说出一个偏高的数。

## 3. 只报可能撞上的，并按时间排序

### 3.1 `Advice` 新增 `timeToImpact`

`ObstacleAdvisor` 重写为两级入口：

```java
adviseTracked(List<Obstacle>, int maxReported, float egoSpeed)   // 新：带测速量
advise(List<Detection>, int, DepthMap, Letterbox)                // 旧签名，内部委托
```

`Obstacle` 是一个薄包装：`Detection box` + `meters` + `ttc` + `relativeRate` +
`lateralRate` + `trackId`。这样决策层不必知道深度图和 letterbox 的存在。

流程：过滤出相关障碍 → 按距离排序 → 算 `freeRatio` → 逐个算 `timeOf` →
过滤掉已被证明安全的 → **按时间重排** → 分组 → 生成一句话。

最后那次"按时间重排"是这里唯一一个我第一版写错的地方：`kept` 还是距离序，
`groups.get(0)` 拿到的不是最急的那条。修法是在分组前插一次比较器排序
（NaN 排最后），并且用单测钉住「六米外的车 vs 一米五外的人」。

### 3.2 去重键要带上紧急度

原来静态提示的键是 `static:中央:person:1:true`。问题很实际：**一个目标从 6 秒
变成 1 秒时，键没变，`AnnouncementPolicy` 的同一句话冷却会把它当成"刚说过"**，
于是升级成"停"的那句话被吞掉。

所以键尾追加紧急度：`:d`（DANGER）或 `:c`（CAUTION）。同级重复仍然被冷却压住，
**升级一定说得出来**。这是"安全 > 少废话"的选择，代价是升级那一瞬间可能连说两句。

### 3.3 两条通道谁先说：比时间，不比等级

`SceneAnalyzer.Decision` 原来写着"有动态结论就压掉静态"。那等于假设"动态永远更急"。
现在静态通道也能给出 `timeToImpact` 了，这个假设不再成立：

```java
return dynamicTime <= staticTime + 0.2f;   // 都有时间时比时间
```

- 动态算不出时间（横穿通道的 NaN）→ 退回旧行为（动态优先），因为动态通道自带
  滞回，本来就是为"会动的东西"做的判据；
- 两边都算不出 → 静态说（避免无谓的沉默）；
- `+0.2` 是抖动容差：两条通道时间接近时每帧来回切换会让文案抖。

### 3.4 横穿目标也有个"多久之后"

横穿的人面积不变，尺度通道 TTC 恒为 NaN。新增
`DynamicAdvisor.timeToEnterCorridor(centerX, rate)`：匀速外推它跨过走廊边界
（`CORRIDOR_LEFT/RIGHT = 0.20/0.80`）的时刻；已在走廊里返回 0。这个量填进
`Alert.timeToImpact`，于是横穿告警也能参与 §3.3 的比较，而不是永远靠"动态优先"。

### 3.5 文案：句子必须比它描述的时间短

| 预计时间 | 文案 | 长度（按 5 字/秒） |
|---|---|---|
| ≤ 1.8 s | `停，中央行人` | 6 字 ≈ 1.2 s |
| 1.8–6 s | `中央行人，2秒` | 7 字 ≈ 1.4 s |
| 全部被过滤 | `前方有目标，暂时不会撞上` | 12 字 ≈ 2.4 s（只在"变安全"时说一次） |

紧急句不含"秒"字，因为它描述的时间比念完它还要短——报出秒数是自相矛盾的。

秒数一律**向下取整**（`wholeSeconds`）：2.5 秒说成"2秒"是稍早预告，说成"3秒"是
骗人。报晚了的代价是用户以为还有时间。

第三行的 `CLEAR` 只在"之前报过有障碍、现在都证明安全了"时才出声
（`AnnouncementPolicy.obstacleAnnounced` 的既有规则），不会变成新的唠叨源。

## 4. 语速

### 4.1 为什么默认就得比系统快

一句中文提示按 5 字/秒念，`中央行人较近，注意` 要 1.7 秒——而它描述的危险
可能只剩 1.8 秒。**语速不是"悦耳度"的偏好，它直接决定这句话还来不来得及起作用。**
改造前用的是平台默认（1.0），这个账从来没算过。

新增 `SpeechPace`：`SLOW 0.85 / STANDARD 1.15 / FAST 1.45`，**默认 STANDARD，
已比平台默认快 15%**。

### 4.2 紧急时再加速一次

`DANGER` 句在用户档位之上再乘 `URGENT_BOOST = 1.25`（1.15 × 1.25 ≈ 1.44）。
两者不合并成一个系数，因为它们是两种不同的东西：档位是用户的长期偏好，
紧急加速是"这件事本身的要求"。

上限压在 1.45（`MAX_RATE = 2.0` 是引擎接受范围的上限，不是我们的）。再快，
中文的声调会被合成器吃掉，而受护人主体是老年人，听辨会更差。**宁可把句子缩短
（§3.5），不要一味加速。**

### 4.3 看门狗按语速折算

`PromptAnnouncer` 的看门狗是按字数估"这句话念完了没有"（防第三方引擎不回调
`onDone`）。语速提到 1.45 后，同一句话念完得早，看门狗却还按 1.0× 等满——
那几秒里所有提示都被当成"正在播报"挡掉。所以把每字时长除以实际语速：

```java
long perChar = Math.max(80L, Math.round(WATCHDOG_PER_CHAR_MS / rate));
```

### 4.4 界面

首页加了一个 `pace_button`（与 `rate_button` 分开的整行）。为什么不做成
"多/少"一个旋钮：用户可能想要**说得勤但每句都短**（频率高、语速快），
也可能想**说得稀但每句听得清**。合并成一个会强迫用户二选一。

点一下切一档，并用 `speakNow` 念一遍新档位名——这既是确认音，也是用户
**试听**新语速的唯一机会（看不见屏幕，按钮文字帮不上忙）。

## 5. 一个我担心但没完全解决的问题：站着不动时会喊"停"

有深度时，若场景里没有可用的静止目标（比如眼前空无一物），步速退回默认 1.2 m/s。
于是**站在电线杆正前方 1 米处不动**，会算出 `t = 1/1.2 ≈ 0.8 s`，反复播报
"停，中央行人"。

现状判断：

- 频率没有变化。改造前它也会每 4 秒说一次"1.0米处中央行人，注意"，
  `AnnouncementPolicy` 的同一句话冷却一直在管这件事；变的只是措辞更急。
- 从"该不该说"看，1 米内正前方有障碍物，说"停"是对的——用户下一步迈出去就撞上。

但措辞的强度确实超出必要。**待办里记了一条**（§8）：站着不动超过 N 秒且
深度读数稳定时，把 DANGER 降为 CAUTION 并换成"前方有障碍，很近"。这一条需要
真机数据才能定 N，现在拍一个数只会变成下一个"没标定过的阈值"。

## 6. 准确性还能怎么提高

分类整理在 `23` 号文档 §2/§3：不训练的十个办法、要训练的七个办法，以及一个
"别只看 mAP"的评估协议。这里只补一句**这次没做、但最该做**的：

> 把 `ObstacleAdvisor` 的判据表放到 `SceneSnapshot` 的回放数据上做**端到端**评估，
> 而不是只看检测 mAP。mAP 提升 2 个点，可能一句提示都没变；而"误报次数/分钟"
> 才是用户真正感知的指标。

`SceneSnapshot` 是不可变的、可 JSON 序列化的，`logcat` 每帧都会打一行
`scene {...}`，回放评估的原料已经是现成的。

### 9.2 推送：8 次失败，第 9 次成功

`git push` 前 8 次全部失败，两种错误交替出现：

       Recv failure: Connection was reset

第一反应容易怀疑凭据或远端地址，**两者都不是**。用两条命令就能分清：

| 探测 | 结果 | 说明 |
|---|---|---|
| `curl https://github.com/` | `200`，0.68 s | 到 GitHub 的 HTTPS 通 |
| `curl "https://github.com/catCookie-ice/Sullivan.git/info/refs?service=git-receive-pack"` | 20 s 超时（`http_code=000`） | **到 git 端点的那条连接被打断** |

边缘节点）。与仓库配置无关——`git remote -v` 指向的地址正是项目一直在用的那个，
上一次成功推送就是 `163b700`。

补充探测（值得记下来）：`ssh -T -p 443 git@ssh.github.com` 能完成 SSH 握手并返回
`Permission denied (publickey)` —— 说明 **SSH 通道（443 端口）是通的**，被阻断的
只有 HTTPS 的 git 端点。本机没有 `~/.ssh` 目录（没有钥匙），所以这条路当时也没走通；
但它是一条**备用出口**：真需要时生成密钥、把公钥加进 GitHub 账户即可。

### 9.4 三条经验

**先探端点，再猜原因。** `fatal: unable to access` 这句话对"网络不通"和
"认证失败"一视同仁，而两者的处置完全不同。一个 `curl` 就能分开：
拿到 `401` 才是认证问题，拿到 `000`/超时就是网络问题。

**间歇性阻断就重试，别急着改配置。** 这次 8 次失败之后第 9 次就通了。
在"网络抖动"上动 `insteadOf`、换协议、改 remote，只会把一次等待变成一堆状态。

**提交信息别用 PowerShell 的重定向写。** `Out-File -Encoding utf8` 会带
BOM，结果提交标题变成 `﻿docs: ...`（那个不可见字符会留在 `git log` 里，
也会让按 `type:` 前缀做的过滤失效）。用编辑器写文件、或直接用 `git commit -m`。
本篇补记用过两次 `--amend` 修错字与 BOM——**没推送的提交可以放心 amend，
推送过的不行**（推送之后就只能追加提交，这次就是这么处理的）。
