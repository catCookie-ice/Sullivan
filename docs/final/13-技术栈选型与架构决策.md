## 1. 核心决策

项目后端只划分为 Java、Python 两个部分：

1. Java 负责稳定的事务业务：账号、角色、权限、绑定、位置、报警、公益、管理和通知。
2. Python 负责 AI/CV：模型加载、图像预处理、全景分割、空间分析和导航引导文本。
3. Java 采用模块化单体，不拆成多个独立服务。
4. 两个进程之间不共享 ORM 实体，不做内部业务 RPC；只共享 JWT 约定和导航接口契约。
5. 数据库为一个 `sullivan`，迁移由 Java 统一执行，Python 只访问导航表。

## 3. 为什么 Java 与 Python 分工

### Java

绑定确认、报警路由、机构审核、申请状态机和名额并发都要求事务、乐观锁、权限收窄和审计。把这些能力放在同一个 Java 进程和同一个数据库事务中，减少网络失败、分布式事务和重复鉴权带来的风险。

### Python

模型训练、预处理、OpenCV/NumPy 空间分析和 ONNX Runtime 的工具链都以 Python 为主。在线推理与离线评测使用同一语言，能避免 Java 重新实现 resize、通道顺序和归一化造成的精度漂移。Python 进程因此只保留导航计算，不扩张为通用业务后端。

## 4. 不采用的技术

| 技术/方案 | 决策 | 原因 |
|---|---|---|
| Spring Cloud Gateway | 不采用 | Java 应用本身就是统一入口 |
| Spring Cloud Alibaba/Nacos | 不采用 | 只有两个固定进程，不需要发现和配置中心 |
| OpenFeign | 不采用 | Java 模块内直接调用；Python 无业务 RPC 需求 |
| Java 多服务 | 不采用 | 单人毕业设计维护成本高，且会引入跨服务一致性问题 |
| 四个 MySQL schema | 不采用 | 简化迁移、查询、备份和本地启动 |
| RabbitMQ/Kafka | 不采用 | 异步场景局限在 Java 内部，outbox 足够 |
| 全 Java 推理 | 不采用 | 预处理和 CV 生态不如 Python，存在一致性风险 |
| 全 Python 业务 | 不采用 | Java/Spring 的事务与授权实现更适合当前业务模型 |
| LLM 生成导航文本 | 不采用 | 违反范围约束，且安全关键路径不可预测 |

## 5. 接口约定

- Java 对外提供 `/api/v1/**` REST 接口。
- Python 仅提供 `/api/v1/navigation/**` REST 与导航 WebSocket。
- JWT 使用同一 `JWT_SECRET`、发行方和时钟约定；两端都校验签名，不通过明文用户 ID 授权。
- 导航帧使用 `session_id` 与递增 `sample_seq`，服务端丢弃乱序帧。
- Java 与 Python 的接口模型写入 `docs/final/api/openapi.yaml`；不要复制 Java 实体到 Python。

## 6. 非功能约束

- Java 关键写操作使用 `WHERE id = ? AND version = ? AND status = ?`，影响行数为 0 返回 `409`。
- 报警先落库，再由 outbox + `@Scheduled` 投递和重试；推送失败不能改变路由规则。
- Python 服务端单帧 `P95 <= 150 ms`，端到端引导 `P95 <= 500 ms`，目标有效处理不低于 10 FPS。
- 导航失败、断网或低置信度时只能返回 `UNKNOWN`/保守提示，不能复用旧的安全结论。
- 所有时间使用 UTC；敏感字段不写入普通日志；导航原始帧和 TTS 音频不落库。
