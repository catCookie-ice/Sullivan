## 0. 先说清楚"系统级"指什么

这条待办说的是**手机系统级的推送**，判断标准只有一条：

> **用户不用打开 App，通知也能从系统通知栏弹出来。**

具体到本项目的场景：受护人按下求助，监护人此刻可能正在打电话、看视频、
手机放在口袋里、屏幕锁着，**应用从未启动或早已被系统回收**——
这些情况下监护人仍然要被叫醒。

下面这张表划清它和现有几种"提醒"的界限，避免把它做成另一个东西：

| 名称 | 用户要打开 App 吗 | 应用进程死了还能收到吗 | 本项目现状 |
|---|---|---|---|
| **系统级推送**（本条待办） | **不用** | **能** | 未实现 |
| 站内通知 `notification` 表 | 要（进应用才看得到） | 不适用 | 已实现 |
| 前台服务自建通知 | 不用，但**服务必须活着** | **不能** | 已实现（当前主路径） |
| WebSocket 实时会话 | 要 | 不能 | 已实现（通话过程用） |

区别的关键在第三列：现在监护人端靠**自己维持一个前台服务**去轮询、再本地
`NotificationCompat` 弹通知。一旦那个服务被系统杀掉（国产 ROM 的常态），
通知就**再也不会出现**——因为"发通知的人"已经不在了。

系统级推送把"发通知的人"从手机端搬到了厂商的推送服务器：
消息由服务端经长连接递到设备，由**系统**负责弹出通知，
应用进程在不在都不影响。这就是它比现状强的地方，也是它唯一值得做的理由。

## 0.1 现状与差距

一句话：**把「监护人必须打开应用才能收到求助」变成「提醒由系统送达」。**

当前实现（见 `17-开发日记-2026-10-24-报警自动呼叫与深度测距` 的 §3C.2 与 §3D.4）
靠的是**监护人端自己维持一个前台服务**，在里面每 5 秒轮询一次
`GET /realtime/sessions`：

| 现状 | 后果 |
|---|---|
| 服务退到后台后，靠 `AlarmManager` 每 15 分钟拉一次 watchdog | 服务被杀到 watchdog 生效之间，**最长可能静默 15 分钟** |
| 国产 ROM（小米/华为/OPPO/vivo）主动杀前台服务，且不受 `START_STICKY` 约束 | 用户在系统设置里不给「自启动/后台运行」白名单，**功能直接失效** |
| 只靠 5 秒轮询，没有服务端主动下发 | 熄屏、省电模式、Doze 下轮询被推迟，**时延不可控** |
| 通知由客户端本地 `NotificationCompat` 构建 | 应用被彻底杀掉或卸载/重装后，**什么都不会发生** |

这不是实现没写好，而是**机制选错了**：把一个「必须送达」的告警，
托付给一个「尽力而为、随时可能被系统回收」的进程。

**系统级推送正好补的就是这一段**：由厂商的长连接通道把消息递到设备，
应用不在运行也能收到，并能在通知栏点亮屏幕。

## 1. 为什么现在不做

按 `00` §8，这是**基线变更**，不是随手加的功能。把它记成待办而不是立刻做，
有四个实际理由：

1. **需要第三方账号与 AppKey。** 极光（JPush）、个推、华为/小米/OPPO/vivo
   厂商通道，都需要注册开发者账号、实名、创建应用、拿到 AppKey/AppSecret。
   这属于外部依赖，不是代码能自给自足的。
2. **国内 Android 的推送是「一主多辅」。** 只接极光而不接厂商通道，
   在国产 ROM 上熄屏后仍可能收不到——厂商通道（华为 HMS、小米 Push、
   OPPO/vivo Push）才是真正的系统级路径。这件事的工作量主要在**多渠道适配**，
   不在「发一条推送」。
3. **毕设范围。** `00` §6.2 第 1 条要求 MINI 的启动、测试和运行不依赖
   `[FULL]` 服务。把推送接进来会让「报警能否送达」依赖外部商业服务，
   需要在文档里明确这是**增强**而不是**前提**。
4. **当前实现可用。** 前台服务 + watchdog 在大多数设备上能工作，
   先保证主链路正确，再把可靠性交给推送，是更稳的顺序。

## 2. 落地时必须守的既有裁决

这部分是本文最重要的内容。推送很容易把已有设计弄乱，以下每条都有出处。

### 2.1 走 `outbox_message`，不要新开一条通道

`14` §3 已经把这件事定好了：**报警先写入 `alert`，再由同库 `outbox_message`
触发路由和通知重试**，由 `@Scheduled` 领取并重试，状态机是

```sql
UPDATE outbox_message
SET status = 'PROCESSING', version = version + 1
WHERE id = :id AND version = :version AND status = 'PENDING';
```

所以第三方推送**不是**在 `AlertService` 里加一行 HTTP 调用，
而是给 `outbox_message` 增加一种**投递渠道**。

> **红线：** 不要在报警的事务里同步调推送 API。推送服务超时会把报警的
> 数据库事务拖死——而这正是 outbox 模式要解决的问题。

### 2.2 `notification` 表不是聊天表，也不是推送日志

`05` §6 与 `16` §2 的 **N-04** 写明：不得复用 `notification` 表作为聊天消息表。
同样地，`notification` 记录的是「站内通知」这件事本身，
**投递尝试**要落在 `notification_delivery_attempt`（`05` §2 已登记这张表）。

两者分工：

| 表 | 回答的问题 |
|---|---|
| `notification` | 有没有这条通知、收件人是谁、读没读 |
| `notification_delivery_attempt` | 通过哪个渠道、第几次、成功没有、失败原因 |

> **红线：** 不要把推送的 registrationId / deviceToken 写进 `notification`。
> 设备令牌属于**设备**，不属于**通知**。

### 2.3 设备令牌需要自己的落点，且必须先登记

推送需要知道「这个账号对应哪台设备的哪个 token」。这需要一张新表，
而 `05` §6 与 `16` §2 的 **N-02** 明确禁止无语义占位字段：
新字段必须写明未来业务主体、数据来源、读写服务、数据分类、启用版本、迁移回滚方案。

建议形状（**仅为建议，落地前须回 `05` 与 `14` 正式登记**）：

| 列 | 说明 |
|---|---|
| `principal_type` / `principal_id` | 谁（与现有 `notification` 的双条件一致） |
| `channel` | `JPUSH` / `HMS` / `MIPUSH` / `OPPO` / `VIVO` |
| `device_token` | 渠道返回的设备标识 |
| `app_version` / `os_version` | 排查用；渠道对版本敏感 |
| `last_seen_at` | 用于清理长期不活跃的令牌 |
| `status` | `ACTIVE` / `INVALID` / `UNBOUND` |

一个账号可能有多台设备（换机、平板），**必须是一对多**。

### 2.4 推送只送「唤醒」，内容最小化

`03` 与 `14` 都强调位置是敏感信息，读取位置要过
`bindingService.hasActiveGuardianship` 的检查（见 `AlertService.get`）。

**推送正文不要带完整坐标。** 理由有两条：

1. 推送会经过第三方服务器（极光、厂商通道），链路在系统之外；
2. 通知栏内容在锁屏上可见，旁人也能看到。

建议推送只带：报警类型、一句"受护人发出求助"、以及一个由服务端签发的
**短期一次性 token**（不是 JWT access token）。客户端收到后用 token 回调
`GET /alerts/{id}` 取详情——**位置仍然经过既有鉴权**。

> **红线：** 不要在推送 payload 里放经纬度、手机号、账号 ID 之类的东西。
> 推送通道把它当作不透明的字符串，不代表它不敏感。

### 2.5 报警状态机不受影响

`02` 的状态机是既成事实。推送成功/失败**不改变 `alert.status`**，
只写 `notification_delivery_attempt`。报警是否送达，
仍然由 `alert_delivery.status` 表达。

> **红线：** 不要让「推送失败」把报警置成 `DISPATCH_FAILED`。
> 推送只是众多渠道之一，它失败不代表没有别的渠道到达。

### 2.6 判定「系统级」是否真的成立：三条验收

这一条待办的价值全在"进程死了也能收到"。所以验收不能只看"通知弹出来了"
（那是前台服务也能做到的），必须满足：

1. **杀掉应用后仍能收到。** 从最近任务里划掉，或
   `adb shell am force-stop com.sullivan.android`，然后让受护人报警——
   通知必须出现。`force-stop` 比"划掉"更严格：它会让应用进入 stopped 状态，
   连广播都收不到，是真正的极限场景。
2. **熄屏 + 省电模式下仍能收到。** 锁屏放置 10 分钟以上再试，
   避开 Doze 白名单带来的假通过。
3. **从未启动过的新装应用也能收到。** 装完不打开，直接让受护人报警。

> 如果某条渠道做不到第 1 条，那它就不是"系统级推送"，
> 只是"更省电的轮询"——价值完全不同，不要当成做完了。

### 2.7 只接极光，可能达不到第 1 条

这点必须在动手前就知道，否则做完会发现没解决问题：

极光这类聚合推送有自己的长连接。但在国产 ROM 上，
**熄屏或应用被杀后，聚合通道的连接同样会被断开**——
厂商只保活自己的系统通道。所以：

- 极光的价值主要是**统一的接入层与后台**（一次对接，多个渠道）；
- 真正让"进程死了也能收到"成立的，是**华为 HMS / 小米 Push /
  OPPO Push / vivo Push 这些厂商通道**；
- 极光可以代发厂商通道，但每个厂商的 AppKey 仍要单独申请。

结论：**这一项的工作量在厂商通道适配，不在发一条推送。** 详见 §3 第三步。

## 3. 建议的实施顺序

分四步，每步都能独立验证，不要一次全上。

### 第一步：把 outbox 通道抽象出来（无外部依赖）

现在 `outbox_message` 只在设计文档里，代码里还没落地。
先把「投递渠道」做成接口：

```
NotificationChannel（接口）
├── InAppChannel      // 写 notification 表（现有行为）
└── PushChannel       // 未来接极光/厂商通道
```

这一步**不引入任何第三方 SDK**，只把现有站内通知改造成走接口。
好处：接推送时不用改 `AlertService`，也不用改报警事务。

> 这是唯一一步能在当前 `[MINI]` 范围内做、且不违反 `00` §6.2 的工作。

### 第二步：接一个渠道，先跑通闭环

选极光（JPush）单渠道。理由：文档全、有免费额度、Android 集成简单。
验收标准是：**应用被杀掉后，通知栏仍能收到**。

### 第三步：加厂商通道（工作量主要在这里）

国内 ROM 真正可靠的是厂商通道。极光本身支持「厂商通道下发」，
但每个厂商都要单独申请、单独配 AppKey。

| 渠道 | 必要性 |
|---|---|
| 华为 HMS | 高（华为/荣耀存量很大） |
| 小米 Push | 高 |
| OPPO / vivo Push | 中 |
| FCM | 低（国内不可用） |

### 第四步：把前台服务降级为兜底

推送跑通后，监护人端的 5 秒轮询前台服务应当**降级**为兜底手段，
而不是主路径。这样能省电，也让「没开自启动白名单」的用户仍有机会收到。

> **注意：** 降级不等于删除。推送在弱网、离线、渠道故障时也会失败，
> 两条路径并存才是可靠的做法。

## 4. 风险与注意

1. **外部依赖会变成新的单点。** 推送服务不可用时，报警的「送达」能力下降。
   必须保证：推送失败不影响站内通知与实时会话，这两条要独立可用。
2. **AppKey / AppSecret 不能进仓库。** 与现状一致——`application.properties`
   用的是 `${DB_PASSWORD}` 这类占位符，推送密钥也照此办理，
   走环境变量或本地配置文件，且**确认 `.gitignore` 已覆盖**。
3. **合规。** 推送会采集设备标识（OAID/IMEI 视渠道而定）。
   毕设场景下要在文档里说明用途与范围，不做超出提醒用途的采集。
4. **不要用推送替代长连接。** 实时会话的 WebSocket 通道（`/ws/realtime`）
   负责通话过程，推送只负责「把人叫醒」。两者职责不同。
5. **测试成本。** 推送无法用单元测试覆盖，只能真机验证；
   而且必须测**应用被彻底杀掉**这种场景——这是它唯一比现状强的地方。

## 6. 一句话总结

> 现在的提醒是「应用自己盯着」——服务一被杀，求助就送不到。
> 系统级推送能把它变成「由系统和厂商通道替你盯着」，
> 应用没打开、进程被杀掉，通知照样能弹出来。
>
> 值得做，但要接在 outbox 上、只送唤醒不送坐标，
> 并且让推送失败不拖垮报警本身。
