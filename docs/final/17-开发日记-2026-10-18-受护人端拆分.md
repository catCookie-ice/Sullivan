## 1. 今日目标

原 `client-android/client-ward` 一个 APK 里装了三种角色：受护人、监护人、志愿者。
这三者**在部署形态上是两类东西**：

- 受护人端是**装在一台专用设备上、离线可用的无障碍工具**：相机 + 端侧 ONNX 推理
  （12.8 MB 的 `yolov8n.onnx`）+ 本地 TTS + 振动 + 陀螺仪，要 CAMERA / VIBRATE 权限；
  真实场景是「装到受护人的手机上，只留这一个入口」。
- 监护人 / 志愿者端是一个**需要联网的账号应用**：没有相机推理、没有设备能力需求。

混装的三重代价：

1. 装到受护人手机上就**同时装了监护人功能**，权限、入口、图标都不对；
2. 受护人端被迫带上高德定位、创建受护人、志愿者申请、注册 / 找回密码（与它无关）；
3. **监护人端为 ONNX Runtime 和 12.8 MB 模型买单**，而它永远用不到 ——
   拆分前实测 debug APK **97,940,145 字节（≈93 MB）**。

本次目标：**两个 APK 各司其职**，而非「再加一个构建变体」。

已确认的口径（用户选定）：

| 问题 | 结论 |
|---|---|
| 项目形态 | **独立项目目录** `client-android/client-protectee/`，自带 gradle wrapper，与旧工程平级；共用代码**各存一份**（不建多模块、不建 composite build） |
| 旧端处理 | **删除**受护人代码（相机页、扫码登录、绑定码、`vision/` 包） |
| 新端功能 | **与现在完全一致**：端侧检测 + 免登录主页 + 扫码登录 + 我的绑定码 + 绑定管理 + 公益活动 + 实时会话 |
| 包名 | `com.sullivan.protectee`（目录 `client-protectee`），与旧端可同机共存 |
| 旧端改名 | `client-ward` → **`client-android/client-guardian/`**，包名 `com.sullivan.android` 不变 |
| 应用名 | 受护人端 **「Sullivan 守护」**；监护人端保持 **「Sullivan」** |

## 3. 与既有文档的偏离 / 决策

### 3.1 `client-ward` 改名 `client-guardian`

`client-ward` 这一项当初就是按「ward = 受护人」立的（根 `.gitignore:40` 的注释、
`17-开发日记-2026-10-11` §2.8 都这么写）。受护人拆走后，那个名字会**指向错误的东西**：
剩下的代码里一个受护人页面都没有。因此本次顺带改名。

- `rootProject.name` 一并由 `SullivanAndroid` 改为 `SullivanGuardian`；
- **`applicationId` / `namespace` / 包名 `com.sullivan.android` 一律不变**，
  已装在旧设备上的监护人端不受影响；
- git 把它识别为 159 个文件的 **R100 纯改名**（零内容变化），历史可追。

### 3.2 受护人端没有角色入口页

`ProtecteeHomeActivity` 直接作 LAUNCHER。这是**有意的行为变化**：这个应用里没有第二个
角色可切，摆一个只有一个选项的角色页只是多一次点击。`activity_role_entry.xml` 与
`RoleEntryActivity` 都不搬。

### 3.3 应用名与包名/目录名不同源

- 目录 `client-protectee`、包名 `com.sullivan.protectee`；
- 应用名（`strings.xml` 的 `app_name`、图标下的文字）**「Sullivan 守护」**。

这是**用户明确选定**的：产品名取「守护」，技术标识保留 `protectee`。
**不要事后把哪一边「改回来」对齐。** 监护人端保持「Sullivan」，两端靠应用名区分。

### 3.4 两份 `strings.xml` 刻意保留同名键

`activity_protectee_home.xml` 借用了 `guardian_action_bindings` / `_activities` / `_realtime`
与 `guardian_account` 这几个**值本身是角色中性**的字符串键。两边保留同名，是为了让两份
`strings.xml` 长期可逐字 diff。键名带 `guardian_` 是既有小瑕疵，登记为遗留项，不在这里改。

### 3.5 不逐 token 剔骨 `colors.xml` / `styles.xml`

裁剪一律按「整文件」或「整块」进行。单个 token 要逐条追引用、收益是几百字节，
风险是把配色表改坏。因此 guardian 侧仍留有若干无人引用的 `an_*` 与骨架期的
`sullivan_*` 定义（原注释已说明是为避免旧引用断链）；protectee 侧同样如此。
复核范围按计划限定为「每条 `strings.xml` 是否还有引用」「每个 layout / drawable 是否还有引用」。

### 4.3 未验证的部分（**本节是本次最需要注意的地方**）

**本次仍无模拟器、无真机，界面一页都没有被真正点开过。** 具体地：

- 两个 APK 没有装进任何设备，**没有验证过它们能同机共存**、图标下分别显示
  「Sullivan」与「Sullivan 守护」、互不覆盖 —— 这是本次改动最核心的用户可见效果，
  却只由「`applicationId` 不同」这一条推断出来，**未实测**；
- 受护人端相机页的浮层位置、提示字号、TTS 播报、振动、晃动报警在搬迁后**没有跑过一次**。
  这些代码是整块搬的、编译通过，但**「编译通过」与「浮层还画在对的位置」是两回事**
  （布局里的全限定 View 名改对了、`level_*` 颜色搬齐了，都只是必要条件）；
- 扫码登录、绑定码、长连接握手在真机上的表现同样未验；
- 新工程 `local.properties` 里的 `serverBaseUrl` 是照抄本机内网地址的，
  **从未连过一次真实后端**。

也就是说：**「构建绿 + 单测绿」不等于迁移无遗留。** 与 10-18 那次同样的欠账，
如实记在这里。

## 5. 已知风险

- **两侧会各自漂移**：`data/api/**`、`SessionStore`、`qr/QrPayload`、`ui/common/**`、
  `res/values/**` 各存一份，`ApiService` 的差别从 4 个方法开始只会越拉越大。
  本次刻意不抽共享模块（用户已选「各存一份」），**代价是改一处要同步两处**。
  典型例子：`RealtimeSocket` 的 `ws://` 明文长连接现在**有两份**（已登记 `19` §7）；
  DTO 的 proguard keep 规则也是**两条、包名不同**，漏改一条会让那一侧的 release
  静默把字段解成 `null`。
- **`local.properties` 是工程级、不继承**：新工程必须自己有一份。缺了它
  `assembleDebug` 照样成功，但 `SessionStore.baseUrl()` 一调用就抛异常 ——
  **构建绿不代表能登录**。
- **`yolov8n.onnx` 不在仓库里**（被根 `.gitignore` 的 `*.onnx` 排除），
  换机要本地从旧工程复制到 `client-protectee/app/src/main/assets/`，否则检测页起不来。
- **guardian 的既有欠账原样留着**：`RECORD_AUDIO`、两个定位权限、高德 SDK 与
  `AMAP_API_KEY` placeholder 在代码里都没有任何引用（`AudioRecord` / `MediaRecorder` /
  `amap` Java 调用零命中），只有 manifest 与依赖在空转。是否删取决于「附近的协助请求」
  要不要真做，**单独决策**，本次不顺手改（改了会把「拆分」和「清理死依赖」两件事
  混在一个 diff 里）。
- **`client-android/client-ward/` 空壳目录还在**：里面只剩一个被 `.idea/` 规则忽略的
  `.idea/`，被 Android Studio 占着句柄删不掉。它**不在 git 里**（untracked + ignored），
  不影响仓库；关掉 Studio 后手动删即可。
