# SullivanMINI 术语、枚举与状态机

**文档版本:** v1.0  
**基线日期:** 2026-07-26  
**适用范围:** SullivanMINI `[MINI]`

## 1. 使用规则

本文是业务术语、API 枚举和状态转换的唯一口径。API 使用大写英文字符串值，数据库可使用表中数字编码，但必须在领域层转换，禁止在业务代码中散落魔法数字。

- 状态只能通过本文列出的命令转换，不允许通用 CRUD 接口直接覆盖 `status`。
- 每次转换必须校验操作者、当前状态、业务条件和资源版本。
- 非法转换返回 `409 CONFLICT`；权限不足返回 `403 FORBIDDEN`。
- 定时转换使用服务器时间，时间存储为 UTC。
- `[FULL]` 枚举不得加入 MINI 的可选项或可达状态。

## 2. 核心术语

| 术语 | 英文/标识 | 定义 |
|---|---|---|
| SullivanMINI | `MINI` | 当前开发和验收的公益版本 |
| Sullivan 完整版 | `[FULL]` | 未来商业及扩展能力，不在当前验收 |
| 受护人 | `PROTECTEE` | 由监护人创建、可接受多个监护关系的视障用户 |
| 监护人 | `GUARDIAN` | 可创建受护人并经受护人确认后协助其的用户 |
| 志愿者 | `VOLUNTEER` | 可报名活动并可开启附近求助接收的用户；可与监护人角色并存 |
| 公益机构 | `ORGANIZATION` | 经平台认证后提供免费服务和公益活动的主体 |
| 主监护人 | `PRIMARY_GUARDIAN` | 生效绑定中的首要联系人；不拥有排他报警权 |
| 绑定请求 | `GUARDIAN_BINDING` | 监护人或受护人一方发起、由另一方确认后才生效的关系请求；方向见 `REQUESTED_BY` |
| 生效绑定 | `ACTIVE_BINDING` | 状态为 `ACTIVE` 的绑定，是监护权限的必要条件 |
| 绑定码 | `BIND_CODE` | 受护人登录后在设备上出示的一次性扫码凭据；监护人扫码即完成绑定（见 §4.4） |
| 登录票据 | `QR_LOGIN_TICKET` | 受护人未登录时在登录页出示的扫码凭据；监护人确认授权后由出示设备换取令牌（见 §4.5） |
| 公益服务项目 | `WELFARE_SERVICE` | 机构发布、供受护人免费申请的服务目录 |
| 服务申请 | `SERVICE_APPLICATION` | 受护人本人或监护人代受护人提交的服务请求 |
| 公益活动 | `VOLUNTEER_ACTIVITY` | 机构发布、由志愿者报名参与的免费活动 |
| 报警 | `ALERT` | 受护人主动或设备触发的紧急求助业务记录 |
| 报警投递 | `ALERT_DELIVERY` | 一次报警面向一个接收人的独立通知和确认记录 |
| 附近志愿者 | `NEARBY_VOLUNTEER` | 可服务开启、位置新鲜且位于配置半径内的志愿者 |
| 位置新鲜 | `FRESH_LOCATION` | 采集时间距当前不超过 30 秒的位置 |
| 业务关联 | `ENTITY_REFERENCE` | 单库中的关联 ID；由物理约束保护完整性，并由应用层校验角色、状态和数据权限 |
| 角色关系 | `USER_ROLE` | 自然人与业务角色的关系；监护人兼任志愿者时新增 `VOLUNTEER` 行 |
| 永久初始绑定 | `PERMANENT_BINDING` | 由监护人创建受护人时产生的不可解除 `ACTIVE` 绑定 |
| 绑定/会话发起方 | `REQUESTED_BY` | 绑定或实时会话的发起账号 ID；决定谁可取消，方向由与 `guardian_uid/protectee_uid` 比较得出 |
| 志愿者兼任申请 | `VOLUNTEER_APPLICATION` | 监护人提交、由具备 `VOLUNTEER_REVIEW` 权限的管理员审批的志愿者兼任申请 |
| 实时会话 | `REALTIME_SESSION` | 监护人与受护人基于长连接建立的实时会话记录（消息中继 + 语音/视频/摄像头会话，媒体流走 WebRTC） |
| 语音留言 | `VOICE_MESSAGE` | 会话参与人留给他人的一段语音，对方无需在线、无需接通即可稍后收听 |
| 管理员注册码 | `ADMIN_REGISTRATION_CODE` | 映射初始管理员角色和权限的一次性哈希凭证 |
| 引导文本 | `GUIDE_TEXT` | 导航服务返回、由 Android 本地 TTS 播报的短文本 |
| 幂等键 | `IDEMPOTENCY_KEY` | 标识一次客户端业务意图、用于去重的唯一键 |

### 3.4 账号状态 `AccountStatus`

| API 值 | 编码 | 含义 |
|---|---:|---|
| `DISABLED` | 0 | 禁止登录和业务写操作 |
| `ENABLED` | 1 | 可按角色登录和操作 |

| 当前 | 命令 | 目标 | 操作者 |
|---|---|---|---|
| `ENABLED` | 禁用账号 | `DISABLED` | 有用户治理权限的管理员 |
| `DISABLED` | 启用账号 | `ENABLED` | 有用户治理权限的管理员 |

账号状态转换必须记录原因。禁用不会删除历史业务记录。

## 4. 绑定状态机

### 4.1 绑定状态 `BindingStatus`

| API 值 | 编码 | 含义 | 是否赋权 |
|---|---:|---|---|
| `PENDING` | 0 | 等待目标受护人确认 | 否 |
| `ACTIVE` | 1 | 已确认并生效 | 是 |
| `REJECTED` | 2 | 受护人拒绝 | 否，终态 |
| `CANCELLED` | 3 | 发起人在确认前取消 | 否，终态 |
| `EXPIRED` | 4 | 创建 7 天仍未处理 | 否，终态 |
| `TERMINATED` | 5 | 生效关系被任一方解除 | 否，终态 |

每条绑定记录必须保存发起方 `requested_by`（监护人或受护人的账号 ID）。方向由 `requested_by` 与 `guardian_uid`/`protectee_uid` 比较得出：`requested_by = guardian_uid` 表示监护人发起；`requested_by = protectee_uid` 表示受护人发起。接收方为发起方的另一方，只有接收方可确认或拒绝。

### 4.2 转换表

| 当前 | 事件 | 目标 | 操作者/条件 |
|---|---|---|---|
| 无 | `REQUEST_BINDING` | `PENDING` | 监护人或受护人（发起方）；发起方角色与目标角色互补（发起 `GUARDIAN` 目标须 `PROTECTEE`，反之亦然）；双方账号可用；无 `PENDING/ACTIVE` 重复关系 |
| `PENDING` | `ACCEPT_BINDING` | `ACTIVE` | 接收方（非发起方）本人；请求未过期 |
| `PENDING` | `REJECT_BINDING` | `REJECTED` | 接收方（非发起方）本人 |
| `PENDING` | `CANCEL_BINDING` | `CANCELLED` | 发起方本人 |
| `PENDING` | `EXPIRE_BINDING` | `EXPIRED` | 系统；`created_at + 7d <= now` |
| `ACTIVE` | `TERMINATE_BINDING` | `TERMINATED` | 关系中的监护人或受护人；`permanent_flag=true` 的永久绑定不可解除 |

### 4.3 主监护规则

1. `is_primary` 仅对 `ACTIVE` 关系有效。
2. 受护人第一条转为 `ACTIVE` 的关系在同一事务中设为主监护。
3. 新增后续关系不自动替换主监护。
4. 主监护关系终止后，按 `activated_at ASC, id ASC` 将最早的其他 `ACTIVE` 关系提升为主监护。
5. 受护人由监护人创建，创建者永久绑定并成为主监护；不得通过自主注册绕过该关系。
6. 报警接收人为全部 `ACTIVE` 监护人，主监护标志不参与过滤。
7. `permanent_flag=true` 的初始绑定只能保持 `ACTIVE`，应用不提供解除接口。

### 4.4 绑定码状态 `BindCodeStatus`

绑定码是受护人**登录后**在设备上出示的短随机串（`sullivan://bind?code=...`），
监护人在自己的设备上扫码后**即刻建立绑定**，语义记为「受护人发起 + 监护人扫码确认」。
它**不新增绑定状态转换**：受护人出示码视为发起方为受护人（§4.2 的 `REQUEST_BINDING`），
监护人扫码视为接收方确认（`ACCEPT_BINDING`），整体落在 `PENDING -> ACTIVE` 之内。

| API 值 | 编码 | 含义 | 可被扫 |
|---|---:|---|---|
| `ACTIVE` | 0 | 出示中，等待监护人扫描 | 是 |
| `REVOKED` | 1 | 被同一受护人的新码替换，终态 | 否 |
| `EXPIRED` | 2 | 超过 TTL，终态 | 否 |

| 当前 | 事件 | 目标 | 操作者/条件 |
|---|---|---|---|
| 无 | 出示绑定码 | `ACTIVE` | 受护人本人且账号 `ENABLED`；同一受护人已有 `ACTIVE` 码时先把旧码置 `REVOKED` |
| `ACTIVE` | 重新出示 | `REVOKED` | 受护人本人签发新码 |
| `ACTIVE` | 超时 | `EXPIRED` | 系统；`expires_at <= now` |

约束：

1. **每位受护人同时最多一张 `ACTIVE` 码**，由 `protectee_bind_code.active_code_key`
   生成列上的唯一约束保证，不靠应用层自觉。
2. 绑定码**只在登录后可展示**：签发接口要求受护人 Bearer 令牌。未登录的设备只能出示登录票据（§4.5）。
3. TTL 默认 120 秒（`app.qr.bind-code-ttl-seconds`），过期由定时任务扫成 `EXPIRED`，读路径不改状态。
4. 码本身**不含任何身份信息**；出示人与扫码人身份一律取自各自令牌的已认证主体。
5. 同一监护人重复扫同一码是**幂等**的（返回"已绑定"而不是 `409`）；不同监护人在 TTL 内分别扫到，
   各自建立一条独立关系——这是「扫码加好友」的字面语义，风险由短 TTL 与受护人可随时解除来缓解。
6. 扫码建立绑定**不代替对方确认**：若该对关系已存在由监护人发起的 `PENDING`，
   扫码返回 `409` 冲突而不是把它升级为 `ACTIVE`（§4.2：只有接收方能 `ACCEPT`）。
7. 扫码路径建立的新绑定显式写 `is_primary=false`，不参与 §4.3 的"首条即主"隐式逻辑。

### 4.5 登录票据状态 `QrLoginTicketStatus`

登录票据是受护人**未登录**时在登录页出示的扫码凭据（`sullivan://login?ticket=...`）。
监护人在自己的设备上扫码、从自己**生效绑定**的受护人中选一位并确认，随后**出示票据的那台设备**
以该受护人的身份登录。监护人的设备身份不变。

| API 值 | 编码 | 含义 |
|---|---:|---|
| `PENDING` | 0 | 已签发，等待监护人扫描 |
| `SCANNED` | 1 | 已被某监护人扫描，等待其选择受护人并确认 |
| `CONFIRMED` | 2 | 监护人已授权某受护人；等待出示设备兑换令牌 |
| `CONSUMED` | 3 | 令牌已兑换，终态（一次性） |
| `EXPIRED` | 4 | 超过 TTL，终态 |

| 当前 | 事件 | 目标 | 操作者/条件 |
|---|---|---|---|
| 无 | 创建票据 | `PENDING` | 公开接口（出示设备尚未登录）；客户端只上传 `clientSecret` 的 SHA-256 |
| `PENDING` | 扫描 | `SCANNED` | 已认证监护人；票据未过期；他人抢扫同一票据返回 `409` |
| `SCANNED` | 授权确认 | `CONFIRMED` | **扫描该票据的同一监护人**；服务端在同一事务内复核其与该受护人存在 `ACTIVE` 绑定；未绑定返回 `403` |
| `CONFIRMED` | 兑换令牌 | `CONSUMED` | 出示设备；`clientSecret` 明文哈希与 `exchange_code` **同时**匹配；不匹配 `403` |
| `PENDING/SCANNED` | 超时 | `EXPIRED` | 系统；`expires_at <= now` |

约束：

1. 唯一的**真授权点**是监护人的确认，且必须服务端复核 `ACTIVE` 绑定，绝不信任客户端传来的候选列表。
2. 令牌**绝不出现在轮询响应**里，只经一次性的兑换接口下发；兑换后票据 `CONSUMED`，再查按不存在处理。
3. `secret_hash` 是 `clientSecret` 的 SHA-256；明文只留在出示设备上，服务端不保存，因此
   服务器即使被读库也无法替出示设备兑换令牌。
4. `CONFIRMED` 之后**不再受 TTL 约束**，否则出示设备还没轮询到就白扫了；`CONSUMED` 不可回退。
5. 确认是**幂等**的：同一监护人对同一票据重复确认返回当前状态而不报错。
6. 未与扫票监护人存在 `ACTIVE` 绑定的受护人**不能**被授权（`403`）。
7. 票据 TTL 默认 120 秒（`app.qr.login-ticket-ttl-seconds`）。创建接口公开可调用且无限流，
   属已知缺口（见 `17-开发日记-2026-10-16`）。

## 5. 机构状态机

### 5.1 机构状态 `OrganizationStatus`

| API 值 | 编码 | 含义 |
|---|---:|---|
| `PENDING` | 0 | 待审核 |
| `APPROVED` | 1 | 已认证，可发布 |
| `REJECTED` | 2 | 审核拒绝，可查看原因并重新提交资料 |
| `DISABLED` | 3 | 管理员禁用，不可执行业务写操作 |

| 当前 | 事件 | 目标 | 条件 |
|---|---|---|---|
| 无 | 注册 | `PENDING` | 注册资料校验通过 |
| `PENDING` | 审核通过 | `APPROVED` | 机构审核权限；有审核意见 |
| `PENDING` | 审核拒绝 | `REJECTED` | 机构审核权限；拒绝原因必填 |
| `REJECTED` | 重新提交 | `PENDING` | 机构修改必要资料 |
| `APPROVED` | 禁用 | `DISABLED` | 治理权限；原因必填 |
| `PENDING/REJECTED` | 禁用 | `DISABLED` | 治理权限；原因必填 |
| `DISABLED` | 恢复 | `PENDING` | 管理员；必须重新审核 |

`DISABLED` 不直接恢复为 `APPROVED`。机构被禁用后，其开放项目停止接受新申请，招募中活动停止接受新报名；历史记录保留。

## 6. 公益服务状态机

### 6.1 项目状态 `WelfareServiceStatus`

| API 值 | 编码 | 含义 |
|---|---:|---|
| `PAUSED` | 0 | 暂停新申请，可再次开放 |
| `OPEN` | 1 | 可浏览和申请 |
| `CLOSED` | 2 | 永久关闭，终态 |

| 当前 | 事件 | 目标 | 条件 |
|---|---|---|---|
| 无 | 发布 | `OPEN` | 所属机构 `APPROVED`，资料合法 |
| `OPEN` | 暂停 | `PAUSED` | 所属机构 |
| `PAUSED` | 开放 | `OPEN` | 所属机构仍为 `APPROVED` |
| `OPEN/PAUSED` | 关闭 | `CLOSED` | 所属机构；不删除历史申请 |

### 6.2 申请状态 `ServiceApplicationStatus`

| API 值 | 编码 | 名额占用 | 含义 |
|---|---:|---|---|
| `PENDING` | 0 | 否 | 等待机构处理 |
| `APPROVED` | 1 | 是 | 已批准，等待服务 |
| `COMPLETED` | 2 | 是 | 服务已完成，终态 |
| `REJECTED` | 3 | 否 | 机构拒绝，终态 |
| `CANCELLED` | 4 | 否 | 申请人取消，终态 |

| 当前 | 事件 | 目标 | 操作者/条件 |
|---|---|---|---|
| 无 | 提交申请 | `PENDING` | 受护人本人或生效监护人；项目 `OPEN` |
| `PENDING` | 批准 | `APPROVED` | 项目所属机构；原子校验剩余名额 |
| `PENDING` | 拒绝 | `REJECTED` | 项目所属机构；原因必填 |
| `PENDING` | 取消 | `CANCELLED` | 原申请人 |
| `APPROVED` | 完成 | `COMPLETED` | 项目所属机构 |
| `APPROVED` | 取消 | `CANCELLED` | 不在 MINI 常规流程；仅管理员纠错并审计 |

名额占用数为该项目 `APPROVED + COMPLETED` 的申请数。有限名额批准必须使用锁或条件更新，不能仅先查询后写入。

## 7. 志愿活动状态机

### 7.1 活动状态 `ActivityStatus`

| API 值 | 编码 | 含义 |
|---|---:|---|
| `RECRUITING` | 0 | 招募中，可报名 |
| `IN_PROGRESS` | 1 | 进行中，不再报名 |
| `ENDED` | 2 | 已结束，终态 |
| `CANCELLED` | 3 | 已取消，终态 |

| 当前 | 事件 | 目标 | 条件 |
|---|---|---|---|
| 无 | 发布 | `RECRUITING` | 机构 `APPROVED`；开始时间晚于当前时间；报名窗口合法（`registration_starts_at <= registration_ends_at <= starts_at`） |
| `RECRUITING` | 到达开始时间 | `IN_PROGRESS` | 系统定时任务 |
| `RECRUITING` | 取消 | `CANCELLED` | 所属机构；开始前 |
| `IN_PROGRESS` | 到达结束时间 | `ENDED` | 系统定时任务 |
| `IN_PROGRESS` | 紧急取消 | `CANCELLED` | 所属机构；原因必填并通知参与者 |

活动字段除标题、说明、地点、开始/结束时间、人数上限外，还包含报名开始/结束时间与高德经纬度（`location_lng`/`location_lat`，可与 `location_text` 同空或同非空）。活动结束或取消不创建群聊。`[FULL]` 活动群与聊天状态不属于本状态机。

### 7.2 报名状态 `EnrollmentStatus`

| API 值 | 编码 | 占用活动名额 | 含义 |
|---|---:|---|---|
| `PENDING` | 0 | 否 | 待机构审核 |
| `APPROVED` | 1 | 是 | 已通过 |
| `REJECTED` | 2 | 否 | 已拒绝，终态 |
| `CANCELLED` | 3 | 否 | 志愿者取消，终态 |

| 当前 | 事件 | 目标 | 操作者/条件 |
|---|---|---|---|
| 无 | 报名 | `PENDING` | 志愿者；活动 `RECRUITING` |
| `PENDING` | 审核通过 | `APPROVED` | 所属机构；原子校验人数上限 |
| `PENDING` | 审核拒绝 | `REJECTED` | 所属机构；可填写原因 |
| `PENDING/APPROVED` | 取消报名 | `CANCELLED` | 报名志愿者；活动尚未开始 |

批准人数为 `APPROVED` 报名数，不得超过 `max_volunteers`。

### 7.3 志愿者兼任申请状态 `VolunteerApplicationStatus`

| API 值 | 编码 | 含义 |
|---|---|---|
| `PENDING` | 0 | 待审核 |
| `APPROVED` | 1 | 已通过并追加 `VOLUNTEER` 角色，终态 |
| `REJECTED` | 2 | 已拒绝，终态 |
| `CANCELLED` | 3 | 申请人撤销，终态 |

| 当前 | 事件 | 目标 | 操作者/条件 |
|---|---|---|---|
| 无 | 提交申请 | `PENDING` | 持有 `GUARDIAN` 角色的自然人；账号可用；注册时间满配置天数；当前不持有生效 `VOLUNTEER` 角色 |
| `PENDING` | 审核通过 | `APPROVED` | 具备 `VOLUNTEER_REVIEW` 权限的管理员；事务内追加 `VOLUNTEER` 角色；再次校验注册时间/角色/账号状态 |
| `PENDING` | 审核拒绝 | `REJECTED` | 具备 `VOLUNTEER_REVIEW` 权限的管理员；拒绝原因必填 |
| `PENDING` | 撤销 | `CANCELLED` | 申请人本人 |

同一申请人同时最多一条 `PENDING`（或已通过的 `APPROVED`）申请，由 `effective_key` 唯一约束兜底。审核结果生成申请人的 `APPLICATION_RESULT` 通知（通知模块接入后生效）。审核通过后申请人须重新登录以刷新 JWT 中的 `VOLUNTEER` 角色。

## 8. 实时会话状态机

### 8.1 会话状态 `RealtimeSessionStatus`

实时会话是监护人与受护人之间基于长连接（WebSocket）建立的双向通道，用于消息中继；语音、视频与摄像头会话复用本会话，媒体流走 WebRTC、信令经本长连接中继（见 §8.2）。

> **接受即进入**：接收方点一次「接听」（`REQUESTED -> ACTIVE`）后双方直接进入媒体就绪状态，发起方**不需要**再执行第二次操作。状态机没有新增中间态。

| API 值 | 编码 | 含义 |
|---|---|---|
| `REQUESTED` | 0 | 已发起，等待接收方接受 |
| `ACTIVE` | 1 | 已接受，双方可在会话内中继消息 |
| `REJECTED` | 2 | 接收方拒绝，终态 |
| `ENDED` | 3 | 任一方结束，终态 |

| 当前 | 事件 | 目标 | 操作者/条件 |
|---|---|---|---|
| 无 | 发起 | `REQUESTED` | 双方为自然人的监护人/受护人；存在 `ACTIVE` 绑定 |
| `REQUESTED` | 接受 | `ACTIVE` | 接收方（非发起方）本人 |
| `REQUESTED` | 拒绝 | `REJECTED` | 接收方（非发起方）本人 |
| `ACTIVE` | 结束 | `ENDED` | 会话任一方参与人 |

**状态变化的推送（长连接控制信封，`payload` 为空）**：

| 信封 `type` | 触发 | 收件人 |
|---|---|---|
| `session.joined` | 任一方长连接建立 | 另一方 |
| `session.accepted` | `REQUESTED -> ACTIVE` | **发起方** |
| `session.rejected` | `REQUESTED -> REJECTED` | 发起方 |
| `session.ended` | `-> ENDED` | 另一方 |

> **发起方必须在 `REQUESTED` 阶段就连上长连接**。`session.accepted` 走的是同一条连接，发起方若等到「已接通」才连，就永远收不到这条通知，只能轮询列表 —— 那样「点一次确认即可通话」在发起方那一侧并不成立。推送是**加速**而非唯一通道：对方不在线时什么都不会发生，状态仍以 `GET /realtime/sessions` 为准。

### 8.2 会话类型 `RealtimeSessionType`

| API 值 | 说明 | 媒体形态 |
|---|---|---|
| `BASIC` | 基础消息中继 | 无媒体，仅文本 |
| `VOICE` | 语音会话 | 双向音频 |
| `VIDEO` | 视频通话 | 双向音频 + 双向视频 |
| `CAMERA` | 监护人查看受护人摄像头画面 | 双向音频 + 受护人单向上行视频 |
| `EMERGENCY` | 紧急会话 | 同 `VIDEO`，由报警自动呼叫路径创建 |

`session_type` 的 `CHECK` 允许上述五个值（`V8` 扩展）。`LOCATION` 仍为 `[FULL]` 预留，不加入可达值。

约束：

1. `EMERGENCY` 只能由服务端报警派发创建（`RealtimeAlertDispatcher`），客户端创建请求传 `EMERGENCY` 返回 `403`。
2. `CAMERA` 的视频方向恒为「受护人上行、监护人下行」；监护人侧不得上行摄像头画面。
3. 媒体流不落库。信令经既有信封 `signal` 类型中继，服务端不解析 SDP 与 ICE 候选内容。
4. 会话类型在创建时确定，`ACTIVE` 之后不可变更；需要换类型须结束当前会话并重新发起。

## 9. 报警与通知状态机

### 9.1 报警类型 `AlertType`

| API 值 | 编码 | 说明 |
|---|---:|---|
| `MANUAL` | 0 | 按钮触发 |
| `FALL_DETECTED` | 1 | 设备检测触发；MINI 可选硬件输入 |
| `VOICE_HELP` | 2 | 语音指令触发 |

### 9.2 报警状态 `AlertStatus`

| API 值 | 编码 | 含义 |
|---|---:|---|
| `CREATED` | 0 | 已持久化，等待路由 |
| `DISPATCHING` | 1 | 正在固化接收人和创建投递 |
| `DISPATCHED` | 2 | 至少一条投递已进入发送流程 |
| `ACKNOWLEDGED` | 3 | 至少一个接收人已确认 |
| `RESOLVED` | 4 | 受护人已解决，终态 |
| `NO_RECIPIENT` | 5 | 无生效监护人且无合格附近志愿者 |
| `DISPATCH_FAILED` | 6 | 已选择接收人但投递均最终失败 |

| 当前 | 事件 | 目标 | 条件 |
|---|---|---|---|
| 无 | 创建 | `CREATED` | 报警先持久化；位置可为空 |
| `CREATED` | 开始路由 | `DISPATCHING` | 异步任务获取处理权 |
| `DISPATCHING` | 创建投递 | `DISPATCHED` | 接收人集合非空 |
| `DISPATCHING` | 无接收人 | `NO_RECIPIENT` | 无生效监护人且无合格志愿者 |
| `DISPATCHED` | 接收人确认 | `ACKNOWLEDGED` | 任一独立投递确认 |
| `DISPATCHED` | 全部最终失败 | `DISPATCH_FAILED` | 所有投递达到重试上限 |
| 非 `RESOLVED` | 解决报警 | `RESOLVED` | 报警所属受护人 |

报警聚合状态不替代逐接收人状态。已解决也必须保留投递历史。

### 9.3 接收人路由 `AlertRouteType`

| API 值 | 编码 | 选择条件 |
|---|---:|---|
| `ALL_GUARDIANS` | 0 | 报警创建时至少一条 `ACTIVE` 绑定；选择全部生效监护人 |
| `NEARBY_VOLUNTEERS` | 1 | 生效监护人数量为 0；选择附近且可服务志愿者 |
| `NONE` | 2 | 生效监护人数量为 0 且没有合格志愿者 |

三种路由互斥。有监护人但推送失败仍保持 `ALL_GUARDIANS`，不得切换为 `NEARBY_VOLUNTEERS`。

### 9.4 投递状态 `DeliveryStatus`

| API 值 | 编码 | 含义 |
|---|---:|---|
| `PENDING` | 0 | 已创建待发送 |
| `SENT` | 1 | 已提交推送通道 |
| `DELIVERED` | 2 | 通道确认送达 |
| `ACKNOWLEDGED` | 3 | 接收人主动确认，终态 |
| `FAILED` | 4 | 达到重试上限，终态 |

合法转换为 `PENDING -> SENT -> DELIVERED -> ACKNOWLEDGED`。发送错误可从 `PENDING/SENT` 重试，达到上限转 `FAILED`。每个报警和接收主体组合必须唯一。

### 9.5 通知类型与已读状态

`NotificationType` 值为 `BINDING_REQUEST`、`BINDING_RESULT`、`ALERT`、`APPLICATION_RESULT`、`ENROLLMENT_RESULT`、`ACTIVITY_CHANGE`、`ORG_REVIEW`、`SYSTEM`、`VOICE_MESSAGE`。

`ReadStatus` 仅有 `UNREAD=0` 和 `READ=1`，只允许 `UNREAD -> READ`，重复标记已读幂等。站内已读不等同报警确认。

### 9.6 语音留言状态 `VoiceMessageStatus`

| API 值 | 含义 |
|---|---|
| `SENT` | 已投递，等待接收方收听 |
| `LISTENED` | 接收方本人已标记收听 |
| `DELETED` | 发送方或接收方删除（软删除），不再出现在列表与通知中 |

| 当前 | 事件 | 目标 | 操作者/条件 |
|---|---|---|---|
| 无 | 投递 | `SENT` | 会话任一方；双方存在 `ACTIVE` 绑定；时长/大小/条数未超限 |
| `SENT` | 标记已听 | `LISTENED` | 接收方本人；重复标记幂等 |
| `SENT`/`LISTENED` | 删除 | `DELETED` | 投递双方任一方 |

`LISTENED` 不是终态（可继续删除）；`DELETED` 为终态。留言不随会话结束而失效，绑定解除后仅保留历史不可再听。

## 10. 导航枚举

### 10.1 导航会话 `NavigationSessionStatus`

| API 值 | 编码 | 含义 |
|---|---:|---|
| `ACTIVE` | 0 | 接受帧分析 |
| `STOPPED` | 1 | 用户正常停止，终态 |
| `FAILED` | 2 | 权限、设备或服务错误终止，终态 |
| `EXPIRED` | 3 | 长时间无帧自动结束，终态 |

只有 `ACTIVE` 接受普通帧。会话由所属受护人停止；服务可因超时转为 `EXPIRED`。

### 10.2 导航风险 `NavigationRiskLevel`

| API 值 | 优先级 | 播报规则 |
|---|---:|---|
| `SAFE` | 0 | 可配置关闭，不能在结果过期时复用 |
| `CAUTION` | 1 | 普通提醒，相同场景至少间隔 2 秒 |
| `DANGER` | 2 | 立即播报，可打断低级别提示 |
| `UNKNOWN` | 3 | 分析不可靠，使用保守降级提示 |

`UNKNOWN` 表示系统不确定，不表示风险低。置信度低、帧过期、模型失败或上下文不足时不得返回 `SAFE`。

## 11. 通用布尔值和时间口径

- API 布尔值使用 JSON `true/false`，数据库可映射为 `1/0`。
- `volunteer.is_available` 默认 `false`，只有志愿者本人可开启或关闭。
- 位置 `captured_at` 超过 30 秒为过期；UI 必须展示最后更新时间。
- 绑定过期时间为创建后 7 个自然日，以服务端时间计算。
- 列表排序必须有稳定次序；相同业务时间时以主键升序作为第二排序键。
