### 2.2 修复 client-android 骨架的构建阻断（7 处）

骨架此前**从未构建成功过**，以下问题与移植内容本身无关，但不修就无法验证移植结果。其中 1–5 是通读工程时看出来的，6–7 只有真正跑构建才会暴露——**"看起来配好了"和"能构建"之间的距离，这里量化为 2 个缺陷**。

| # | 位置 | 问题 | 处理 |
| --- | --- | --- | --- |

| 6 | `gradle/libs.versions.toml` | 高德定位写成 `com.amap.api:location:10.0.0`——**该 artifact 根本没有 10.x 版本**（10.x 是 `com.amap.api:3dmap` 的号段），永远解析不到；且 AMap 不在 `google()`/`mavenCentral()` 上，仓库也没配 | 版本改 `11.3.000`（当前 release），`settings.gradle.kts` 加 `maven.aliyun.com/repository/public` |

### 2.7 让 Android Studio 能直接打开并调试

移植完成后，工程在 Android Studio 里打开是**一片红、显示"没有配置"**，而命令行构建却完全正常。
根因不在工程：Studio 2026.1 默认拿它自带的 **JBR 25** 去跑 Gradle，而 Gradle 8.9 只支持到 Java 22。

与其让人去 IDE 设置里手动改 Gradle JDK（换个人、换台机器就得再说一遍），改成由工程自己声明：

| 文件 | 内容 | 作用 |
| --- | --- | --- |
| `gradle/gradle-daemon-jvm.properties`（新增） | `toolchainVersion=17` | Gradle 8.8+ 的守护进程 JVM 要求：不管 IDE 选的是哪个 JDK，守护进程都得起在 17 上 |
| `gradle.properties` | `org.gradle.java.installations.paths=C:/Program Files/Java/jdk-17.0.10` | 告诉 Gradle 本机 JDK 17 装在哪（Gradle 自己扫不到 `Program Files\Java` 下的 JDK） |

两项**缺一不可**，且这一点是实测出来的：只加 `gradle-daemon-jvm.properties` 时 Gradle 直接报
`Cannot find a Java installation ... Compatible with Java 17`；补上 `installations.paths` 才通。

验证方式是**照着 Studio 的处境复现**：把 `JAVA_HOME` 指到 Studio 那个 JBR 25 再构建，
用 init script 从构建内部打印守护进程的 JVM —— 结果是 `java.home=C:\Program Files\Java\jdk-17.0.10
java.version=17.0.10`，证明它确实没在用 25。此时 `assembleDebug` + `testDebugUnitTest` 全部通过。

> 一个自我纠正：中途我先只加了 `toolchainVersion=17` 就跑了一次，看到构建成功便以为生效了。
> 实际上那次是**复用了一个先前用 JDK 17 起的旧守护进程**（`--stop` 之后就立刻失败了）。
> 所以上面那个"从构建内部打印守护进程 JVM"的验证才是有效的证据，单看"构建成功"会得出错误结论。

`org.gradle.java.installations.paths` 是**本机专用**的绝对路径，已在配置里写明；
换机器要改这一行，且路径写错时 Gradle 会**直接报错而不是静默退化**。

### 2.9 接通调试目标：无线 ADB 的配对端口与连接端口

工程能在 Studio 里打开之后，最后卡住「能调试」的是**没有目标设备**。本机盘点：

- `Sdk/emulator/emulator.exe` 已安装，但 `Sdk/system-images` **不存在** —— 一个系统镜像都没有，因此建不了 AVD；
- `adb devices` 为空，未连接任何设备。

于是改走实体手机 + 无线调试。首次 `adb pair` 失败：

```
$ adb pair 10.0.0.228:34895
Enter pairing code: 969483
error: protocol fault (couldn't read status message): No error
```

报的是**协议错**而不是网络错，看着莫名其妙。根因是 Android 无线调试同时开了**两个不同的端口**，
而这里用的是连接端口：

| 端口 | 在哪看 | 给谁用 | 说什么协议 |
| --- | --- | --- | --- |
| **配对端口** | 点「使用配对码配对设备」后弹窗里显示 | `adb pair` | 配对协议 |
| **连接端口** | 无线调试主界面显示 | `adb connect` | 标准 ADB TLS 协议 |

对着连接端口发配对协议，那边的 adbd 等的是标准握手，收到对不上的字节便直接断开连接 →
adb 读不到状态消息。**配对端口每次打开弹窗都会变，且只在弹窗开着时监听。**

定位过程用的是证据而非推测：

- `adb mdns services` → `adb-10CF4X0RLS002H9-Xs5D8t  _adb-tls-connect._tcp  10.0.0.228:34895`
  —— 明确标出 34895 是**连接**端口，且列表里**没有** `_adb-tls-pairing._tcp` 条目（说明弹窗当时是关的）；
- 本机 10.0.0.211 与手机 10.0.0.228 同网段，`ping` 0% 丢包，TCP 34895 可连通 → 排除网络问题；
- `adb connect 10.0.0.228:34895` → `failed to connect`，符合「尚未配对、无互信密钥」的预期；
- `adb version` 为 37.0.1 且 PATH 上只有这一个 adb → 排除工具链版本问题。

正解：

1. 手机「开发者选项 → 无线调试 → **使用配对码配对设备**」，弹窗里有 6 位配对码与一个**另配的**端口；
2. **弹窗别关、屏幕别锁**，执行 `adb pair <ip>:<弹窗里的端口>` 并输入该配对码；
3. 配对成功后关掉弹窗，用主界面的连接端口 `adb connect <ip>:<连接端口>`。

省去手抄端口的办法：弹窗开着时在电脑上跑 `adb mdns services`，多出来那行的 `_adb-tls-pairing._tcp`
就是配对端口，直接照抄不会拿错。

**截至写日记时配对尚未成功**，设备仍未接上，见 §5。

## 3. 与既有文档的偏离（架构）

3. 受护人导航是安全关键路径，端侧不依赖服务可用性。

### 4.3 中文路径导致测试无法运行：已定位并修复

本机 `sun.jnu.encoding=GBK`。Gradle 在测试 classpath 过长时改用 `@argfile` 传参，报
`ClassNotFoundException: worker.org.gradle.process.internal.worker.GradleWorkerMain`。
参考1 的 README 只给了"绕开"方案（改用 `javac` + JUnit 手跑），本次进一步定位到可直接修好的层次：

**实测结论**：同一份含中文路径的 argfile，用 UTF-8 写必然失败、用 GBK 写正常——
JVM 按 `sun.jnu.encoding`（GBK）解码 argfile，而 Gradle 用 daemon 的默认编码去写，
两边不一致就会把中文路径解成乱码。

**修复**：`gradle.properties` 里 daemon 的 `-Dfile.encoding` 由 `UTF-8` 改为平台默认（GBK），
并在 `app/build.gradle.kts` 的 `compileOptions` 显式写 `encoding = "UTF-8"`——
否则 javac 会跟着用 GBK 读源码，中文字符串字面量（播报文案）会编译成乱码。
两处必须成对改：改一处就会要么测试跑不起来、要么文案变乱码。

`assembleDebug` 不受此问题影响（编译在 daemon 内完成，不 fork worker），
所以这个坑只在跑测试时才会暴露。

同时也确认：改用 `@argfile` 的根因（`services.gradle.org` 在本机被限速到约 17 KB/s）
属于环境问题，与工程无关；换用国内镜像可达 12.6 MB/s。

**构建环境（三个坑，换机器复现时先看这里）**

1. 必须用 **JDK 17**。命令行下 `JAVA_HOME` 指向 JDK 17；本机 machine 级 `JAVA_HOME` 是 JDK 25、
   PATH 上的 `java` 也是 JDK 25，直接跑会用错版本（用户级 `JAVA_HOME` 已是 17，优先级更高）。
2. **JDK 25 会让 Studio 打不开工程 —— 已用两项配置消除，不用手动改 IDE 设置**。
   Studio 2026.1（AI-261）默认把 Gradle JDK 设成自带的 JBR 25，而 Gradle 8.9 跑不了 JDK 25
   （只支持到 Java 22）、AGP 8.5.2 也不支持。症状是工程打开后"没有配置"、代码全红，
   而**命令行构建却完全正常**（命令行走 `JAVA_HOME`=17，Studio 走它自己那个设置）。
   该失败在 Gradle 侧只报一行 `* What went wrong: 25.0.2`，极难反推。
   现在由两处配置兜住，见 §2.7：`gradle/gradle-daemon-jvm.properties` 声明"守护进程要 JDK 17"，
   `gradle.properties` 的 `org.gradle.java.installations.paths` 告诉 Gradle JDK 17 装在哪。
   实测有效：把 `JAVA_HOME` 指到 Studio 那个 JBR 25 再构建，守护进程依然起在 JDK 17 上。
   若哪台机器上仍报 `Cannot find a Java installation ... Compatible with Java 17`，
   说明那台机器的 `installations.paths` 没指对，改 `gradle.properties` 那一行即可。
3. 首次构建要联网下载 AGP / Kotlin / Compose / CameraX / ONNX Runtime 等全部依赖，约 500 MB 级。
   若 `services.gradle.org` 被限速（本机实测仅约 17 KB/s），wrapper 的 Gradle 发行包会下不下来，
   换国内镜像；Maven/Google 仓库本身本机速度正常，无需换源。
