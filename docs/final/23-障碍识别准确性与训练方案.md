# 障碍识别准确性：瓶颈、可行的提升手段、数据集与训练方案

**适用对象：** 受护人端（`client-android/client-protectee`）的端侧障碍检测链路
**结论一句话：** 现在限制体验的不是"模型不够大"，而是**训练数据与使用场景不匹配**
（COCO 里没有台阶、路缘石，也没有贴地低视角），以及**评估指标选错了**
（mAP 对几十像素的小目标几乎不敏感）。

配套代码在 [`tools/vision-training/`](../../tools/vision-training/README.md)。
本次已落地的阈值与预测改动见
[17-开发日记-2026-11-01](./17-开发日记-2026-11-01-障碍预警与碰撞预测.md)。

---

## 1. 先把"准确性"拆开：四层，四种失败

"识别不准"是用户的主观描述。落到代码里，它可能发生在四个完全不同的地方，
而**只有第一层是模型问题**：

| 层 | 代码 | 典型失败 | 可观测指标 |
|---|---|---|---|
| 1 检测 | `Yolo26Detector` | 小目标/夜间/逆光漏检；背景纹理误检 | mAP、小目标召回、每图预测数 |
| 2 追踪 | `ObjectTracker` + `TtcEstimator` | 漏帧导致轨迹断、尺度拟合被噪声带偏 | 轨迹平均存活帧数、拟合残差 RMS |
| 3 判定 | `ObstacleAdvisor` + `DynamicAdvisor` | 该报的没报、报了不该报的 | 误报次数/分钟、首报提前量 |
| 4 播报 | `AnnouncementPolicy` + `PromptAnnouncer` | 句子比危险长、去重把升级吞掉 | 出声时延、被丢弃比例 |

**一个真实例子说明为什么必须分层看。** 本次把检测阈值从 0.35 降到 0.28，
第 1 层的召回会上升、每图预测数也会上升（噪声变多）；但如果第 3 层的
`LOW_SCORE` 位置闸和小障碍判据没同步调，这些新增的框会全部死在决策层——
**用户一个字都听不到，而 mAP 却看不出任何变化**。

所以：**任何一次"提高准确性"的改动，都要给出四层里至少一层的指标变化，
并且说明另外三层为什么不受影响。**

## 2. 不改模型就能做的（按性价比排序）

| # | 手段 | 效果 | 成本 | 本次 |
|---|---|---|---|---|
| 1 | 降检测阈值 + 多帧确认兜底 | 小目标召回↑ | 极低 | **已做**（0.35→0.28） |
| 2 | 小障碍判据从面积改高度 | 细长障碍召回↑ | 极低 | **已做** |
| 3 | 低分框按"是否贴地"二次筛选 | 噪声↓、近处召回不变 | 极低 | **已做** |
| 4 | 只推理画面下部 ROI | 等效分辨率↑、耗时↓ | 低 | 未做（见 §2.1） |
| 5 | 检测输入 640 → 960 | 小目标召回明显↑ | 中（速度↓约 2×） | 未做（见 §2.1） |
| 6 | 深度图做"离地过滤" | 误检↓（把墙上纹理当障碍） | 中 | 未做 |
| 7 | 类别白名单收敛 | 奇怪播报↓ | 极低 | 部分（`CocoLabels.isObstacle`） |
| 8 | FP16 推理 | 速度↑，换取更高分辨率 | 低 | 未做 |
| 9 | 框尺寸 EMA 平滑 | 播报抖动↓ | 极低 | 已有最小二乘 |
| 10 | 夜间自动曝光/降噪 | 夜间召回↑ | 中（相机参数） | 未做 |

### 2.1 关于 4/5/8 的取舍：这是唯一真正的"速度 vs 召回"预算

端侧当前的上限是**每帧推理耗时**，不是算力。三者不能同时要：

```
更高分辨率 (960) + FP16  ≈ 与 640 全精度同耗时，但召回更高   ← 最划算
更高分辨率 (960) + 全精度 ≈ 耗时翻倍，帧率掉到 3–4 FPS，追踪会断
ROI 裁剪 + 640            ≈ 耗时降一半，等效分辨率 ×1.3，但只能看下方 2/3
```

**建议路线：先 FP16 + 960（保持 640 的耗时预算），不要先加 ROI**——ROI 会砍掉
上半画面的远处目标，而"远处正在接近的人"是预测通道的主要输入。

### 2.2 关于 6（深度图离地过滤）

深度模型已经在跑（`yolo26n-depth.onnx`）。可以用它做一件与检测无关的事：
把检测框下沿的深度与外框中心的深度比较，**离地高度异常大的框判为"挂在墙上"
或"贴在头顶"**，与"挡路"无关。这比再训练一个分类器便宜得多，且不需要标注。

实现位置应在 `assist/`（阈值只在 `assist/` 里），而不是 `track/` 或 `scene/`——
那两层的职责是"只输出测量值"。

## 3. 需要训练的（按预期收益排序）

1. **领域微调（收益最大）**：5k–20k 张自采人行道/街道图，含台阶、路缘石、路锥、
   共享单车、施工围挡。COCO 预训练 → 微调，通常小目标召回能涨 10–20 个点。
2. **类别重构**：从 COCO 80 类收敛到 `dataset.yaml` 里的 24 类，并补上 COCO 没有的
   `step`/`curb`/`pothole`。**这一步不是"删类别"，是让"台阶"第一次有资格被检出来。**
3. **训练分辨率 > 推理分辨率**（`imgsz=960` 训练，640 导出）：让小目标特征在
   训练时被看见。配 `copy_paste` 增强，是唯一不花钱就增加小样本量的办法。
4. **针对性增强**：低视角俯仰、逆光、夜间、运动模糊、雨雾。
5. **负样本**：井盖、影子、地砖缝、广告贴纸——这些是"误报"的主要来源，
   单独凑 1k 张负样本图（无标注或标注为空）能显著降误报。
6. **更大模型**（`yolo26s/m`）：召回↑、耗时↑。只在确认"640+FP16 也不够"之后再上。
7. **多任务**（检测 + 深度联合）：理论上共享特征，工程复杂度高，**不建议在毕设周期内做**。

### 4.3 COCO 里没有、必须自采的三类

| 类别 | 为什么必须自采 | 采集要点 |
|---|---|---|
| `step`（单级台阶/门槛） | COCO 无此类；室内外都可能突然出现 | 胸前高度、下俯 20°–40°、含阴影；白天/夜间各半 |
| `curb`（路缘石高差） | 高差只有 10–15 cm，边界靠纹理与光照判断 | 顺光/逆光/湿地面；含"刷成斜坡"的误判负样本 |
| `bollard`（隔离柱） | 细长、贴地、与背景对比低 | 至少 500 实例；含被遮挡一半的情形 |

每类建议 ≥ 500 实例，且**同一条街不要超过 20% 的样本**——否则模型学到的是
"这条街的地砖纹理"。

## 5. 训练代码怎么跑

见 [`tools/vision-training/README.md`](../../tools/vision-training/README.md)。四步：

```bash
pip install -r tools/vision-training/requirements.txt

python tools/vision-training/train.py  --data dataset.yaml --epochs 120
python tools/vision-training/eval.py   --weights runs/sullivan-hazard/weights/best.pt --data dataset.yaml
python tools/vision-training/export_onnx.py --weights runs/sullivan-hazard/weights/best.pt \
       --imgsz 640 --copy-to <assets 目录>/yolo26n.onnx
python tools/vision-training/check_export.py <assets 目录>/yolo26n.onnx
```

三个脚本各自解决一个具体的坑，值得单独说明：

- `train.py` 的默认参数里写死了"**上下不翻转**"（人行道没有倒过来的图）、
  "**mosaic 最后 20 轮关掉**"（拼接缝在真实画面里不存在）、
  "`copy_paste` 0.3"（小目标只能靠复制粘贴扩样本）。
- `eval.py` 不看 mAP 就下结论是不行的，只看 mAP 更不行：它额外算**小目标召回**
  （归一化高度 ≤ 0.06，与端侧 `TINY_HEIGHT_RATIO` 同一个数）和**置信度扫描**
  （0.28 / 0.35 / 0.50 的召回 vs 每图预测数）。端侧取 0.28 的依据就是这张表，
  换数据集必须重跑。
- `export_onnx.py` 导出后立刻调 `check_export.py` 校验形状，**导出成功 ≠ 能装进 App**。
  仓库内两份资产已实测（`logits[None,300,80] + pred_boxes[None,300,4]`）。

## 6. 评估协议（建议直接当验收标准）

### 6.1 分层指标

| 层 | 指标 | 建议门槛 | 现状 |
|---|---|---|---|
| 检测 | 小目标召回（h ≤ 0.06，conf 0.28，IoU 0.5） | ≥ 0.75 | **未测**（缺自建验证集） |
| 检测 | 夜间子集小目标召回 | ≥ 0.60 | 未测 |
| 检测 | 每图预测数（站定场景） | ≤ 15 | 未测 |
| 追踪 | 轨迹平均存活时长 | ≥ 1.2 s | 未测 |
| 判定 | 站定 60 s 的播报次数 | ≤ 3 次 | 未测 |
| 判定 | 真实碰撞前 ≥ 2.0 s 出声的比例 | ≥ 0.90 | 未测 |
| 播报 | 句子时长 < 其描述的剩余时间 | 100% | 设计保证（§3.5） |

"未测"不是懒，是因为**没有自建验证集**。这也正是本次把训练流水线补齐的原因：
先有数据与指标，才有资格说"准确性提高了"。

### 6.2 端到端回放（最值得做的一件事）

`SceneSnapshot` 是不可变、可 JSON 序列化的；`logcat` 每帧都打一行 `scene {...}`。
于是可以：

1. 真机走一段路，抓 logcat；
2. 把每行 JSON 喂回 `SceneAnalyzer` 的决策层（纯 JVM，无需 Android）；
3. 统计"如果当时用新阈值，会多说几句、少说几句"。

这条链路能回答一个 mAP 永远回答不了的问题：**这次改动让用户多听了多少句、
少听了多少句。** 建议在实现 OB-03 时把它做成 `vision/` 下的一个测试装置。

## 7. 风险与合规

1. **路人隐私**：自采数据必然拍到人脸。入库前做人脸模糊，或只保留"下肢 + 地面"
   的裁剪区域。受护人端的实时视频不出设备（`SceneSnapshot` 只存框，不存像素），
   这一点在 `08-非功能需求` 里已有约束。
2. **数据许可**：见 §4.2 的提醒。Roboflow 社区数据出处要写进 README。
3. **不要让"准确"变成"更多话"**：每次降阈值/加类别，都要复核 §6.1 的
   "站定 60 s 播报次数"。用户会因为烦而关掉语音——那时准确性归零。
4. **模型的 sha256 要留档**：同一份 `yolo26n.onnx` 在不同设备上跑出不同结果时，
   第一件要确认的事是"跑的是哪一版权重"。

## 8. 一页纸的行动顺序

1. 采 3 类自建数据（step / curb / bollard），每类 ≥ 500 实例 → `dataset.yaml`；
2. 用 COCO 预训练的 `yolo26n.pt` 微调，`imgsz=960`，`copy_paste=0.3`；
3. `eval.py` 出小目标召回 + 置信度扫描，确定端侧阈值（现在是 0.28）；
4. `export_onnx.py` 导出并 `check_export.py` 校验，替换 assets；
5. 真机夜路 + 台阶 + 站定 60 s 三件事，用 `scene {...}` 回放统计误报/提前量；
6. 把结果回填到 §6.1 的表格，并更新 `17` 号开发日记的待办（OB-01/OB-03）。
