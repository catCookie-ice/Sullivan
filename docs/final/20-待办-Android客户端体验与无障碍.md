| UX-05 | P1 | 发起通话时直接选人，而不是手输 ID | 用户点「发起会话」时，应当**列出已绑定的对象供选择**（可多选或逐条选择），而不是让他输入对方的账号 ID —— 服务端本来就要求 `targetUid` 必须与当前用户存在 ACTIVE 绑定（`realtime/sessions` 会校验），所以「能选的人」与「合法的人」是同一个集合，手输只是把服务端的校验搬给了用户。**这条可以独立于 UX-03 先做**：`GET /bindings` 已经拿得到对方的 id。但有个硬依赖：`BindingResponse` 只有 `guardianId`/`protecteeId`，**不带任何姓名**，只靠它做出来的选择器只能显示一串 UUID —— 所以要么服务端给绑定响应补上对方的登录名/显示名，要么客户端对每条绑定再打一次 `GET /users/{id}`（N+1，不推荐）。同一处应当一并覆盖「绑定管理 → 发起绑定」 | 待办 |

## 说明

- 优先级：P1 影响可用性 / 无障碍合规，P2 为需要先立规矩的扩展。
- **UX-03 与 UX-05 是两件事**：UX-05 是「别再让用户手输」，UX-03 是「把 ID 从所有给人看的
  位置换掉」。UX-05 做完 UX-03 仍然要做（查找账号页、绑定行的「对方」、会话行的「与 X 的会话」
  都还在显示 ID）。
- **UX-01 与 UX-02 也是两件事**：前者是 MINI 的欠账（FR-10 已写进需求），后者是 `[FULL]` 扩展。
- 涉及接口契约的两项（UX-03、UX-05 的姓名依赖）落地时要同步 `api/openapi.yaml`、
  `docs/final/05-数据模型与数据字典.md`，以及 `client-web` 四端 —— 用户可见标识是跨端口径，
  只在 Android 改会造成「网页显示姓名、手机显示 UUID」的分裂。

## 风险与注意

| 风险 | 说明 |
|---|---|
| 语音指令的误触发 | FR-10 已写明「识别不确定时要求确认，不执行猜测出的高风险操作」。受护人端做语音时，**报警**这一类意图必须走确认，且不能因为「朗读提示」而压过原有的按钮路径 |
| 声纹把人锁在门外 | 声纹校验失败时的降级路径必须是「回落到按钮 / 回落到手输」而不是「拒绝服务」。受护人可能感冒、可能临时失声 |
| 按登录名查找等于开放搜索 | 允许别人用登录名搜到用户，就要回答「谁能搜到谁」「搜不到时要不要给一致的提示以免枚举账号」。这与 `19` §7 的限流是同一类问题，需要一起定 |
| 拆分页面的成本 | UX-04 会新增 Activity，而两端的会话页都锁了竖屏并绑在 Activity 生命周期上（长连接随页面销毁断开）。拆页时**不能把长连接留在列表页**，否则用户进会话页时连接已被销毁 |
| 两端要一起改 | UX-03/UX-04/UX-05 都是两端共有的页面（`BindingListActivity`、`RealtimeActivity` 两侧各一份）。按 `17-开发日记-2026-10-18-受护人端拆分.md` §5 的约定，**改一处要同步两处**，且受护人端的无障碍要求更严（字号下限、触控目标） |
