# SullivanMINI 开发日记：2026-10-26（数据库重构与 Python 端移除）

**开发主题:** 破坏性更新 —— 数据库基线重构 + Python 服务端整体移除，版本 0.x → **v1.0.0**
**适用范围:** SullivanMINI `[MINI]`
**变更类型:** **破坏性（Breaking）**：数据库需重建、服务端部署单元减少、导航链路架构变更
**关联文档:** `00-范围基线与演进路线.md` §8 基线变更 / `05-数据模型与数据字典.md` / `06-系统架构设计.md` / `13-技术栈选型与架构决策.md` / `14-数据库设计补充与迁移修正.md` / `16-扩展点登记表.md` N-06

## 1. 为什么是破坏性更新

本轮同时做了两件影响基线的事，任一件都足以构成破坏性变更：

1. **数据库基线重构**：Flyway 迁移历史 V1–V11 压缩为单个 `V1__baseline.sql`，
   并大量收紧约束（唯一键、NOT NULL、默认值、状态机 CHECK、外键）。
   迁移历史重置，**旧库数据不保留**，必须重建数据库。
2. **Python 端整体移除**：`server-python/`（FastAPI 导航推理服务）、`sullivan-vision/`
   （离线模型评测与 ONNX 导出）、`deploy/navigation/`（导航容器编排）全部删除。
   导航/障碍检测能力由受护人端**端侧 ONNX Runtime** 承担（该能力早在
   `17-开发日记-2026-10-11.md` 已落地真机），服务端推理进程自始至终没有承担过
   生产流量，删除不影响任何现有接口。

因此版本号从 0.0.1-SNAPSHOT / 0.1.0 大幅提升到 **1.0.0**（全部模块统一）。

## 2. 数据库重构（V1–V11 → 单 V1 基线）

### 2.1 范围决策

- **只保留 Java 代码实际使用的 26 张表**。设计文档中从未实现的表
  （`welfare_service` / `service_quota` / `service_application` / `organization_review` /
  `auth_refresh_token` / `volunteer_availability` / `alert_broadcast` / `alert_broadcast_response` /
  `notification_delivery_attempt` / `outbox_message` / `admin_audit_log`）不再建空表，
  消除「文档有、库里无、代码不认」的三重态。
- **导航三表（`model_version` / `navigation_session` / `navigation_sample_event`）不建**：
  原 Python 端依赖它们，但 Flyway 从未建过，Python 首次部署即会崩 —— 这个缺口随
  Python 移除一并消失。
- 旧的 `db/migration/` 四目录（user/navigation/welfare/admin 四库版 baseline）是
  单库化之前的遗留物，与活库 schema 冲突（如 `guardian_binding` 缺列、`organization`
  缺登录列），已整体删除。
- 权限/角色种子数据不进 SQL：`AdminSeedInitializer` 启动时幂等播种，数据库保持纯 DDL。

### 2.2 约束收紧清单（全部先核对过 Java 写入路径再上约束）

**唯一性（最重要的一条）**：

- `guardian_binding` 在活库中**从来没有配对唯一约束**（旧四库版和设计文档都有，
  Flyway 建表时漏了），重复绑定纯靠应用层查重。本版恢复生成列 + UNIQUE：
  - `uq_guardian_binding_active_pair`：同一对（监护人，受护人）同时至多一条
    PENDING/ACTIVE（TERMINATED/REJECTED/CANCELLED/EXPIRED 不占键，可重新申请）；
  - `uq_guardian_binding_primary`：每位受护人至多一位主监护人。
  并发窗口下即使应用层查重失效，数据库也是最后一道兜底 —— 双主监护这种数据损坏
  从「静默发生」变成「直接报错」。

**非空与默认值**：

- `guardian_binding.requested_by` 升为 NOT NULL（两条插入路径均显式设置）；
- `location_authorization.status` 补默认值 `'GRANTED'`（原来无默认值非空，插行必炸）；
- `user_role` 补齐全库统一的 `updated_at` / `version` 审计列（实体未映射，DB 默认值
  兜底，代码零改动）；
- `alert.status` 从 VARCHAR(20) 统一为 VARCHAR(16)（最长值 `DISPATCH_FAILED` 15 字符，
  与全库 16 对齐）。

**状态机 CHECK（19 条新增，全部为单向约束：状态推进到位则时间戳必填，回退不强清）**：

| 表 | 约束语义 |
|---|---|
| `guardian_binding` | ACTIVE ⇒ `confirmed_at` 非空；`is_primary` 仅 ACTIVE 可为 TRUE |
| `organization` | `reviewed_by_admin_id` 与 `reviewed_at` 成对出现（要么都有要么都无） |
| `admin_registration_code` | 非 USED 状态不得带使用痕迹（**单向**：`claimFromDb` 存在"先置 USED、管理员落库后再回填使用人"的中间态，双向约束会打断它） |
| `protectee_bind_code` | REVOKED ⇒ `revoked_at` 非空 |
| `qr_login_ticket` | SCANNED ⇒ 扫描人+时间；CONFIRMED ⇒ 受护人+换牌凭据+时间；CONSUMED ⇒ 核销时间 |
| `location_authorization` | GRANTED ⇒ `granted_at`；REVOKED ⇒ `revoked_at` |
| `alert` | RESOLVED ⇒ `resolved_at` |
| `alert_delivery` | ACKNOWLEDGED ⇒ `acknowledged_at`；FAILED ⇒ `failure_reason`；`dispatch_order ≥ 1` |
| `notification` | READ ⇔ `read_at` 双向一致 |
| `realtime_session` | ACTIVE ⇒ `accepted_at`；ENDED ⇒ `ended_at`（**见 §2.4 的语义修正**） |
| `voice_message` | LISTENED ⇒ `listened_at`；`duration_ms > 0`；`size_bytes > 0` |
| `volunteer_application` / `activity_enrollment` | APPROVED/REJECTED ⇒ 审核时间（+审核人）非空 |
| `account_recovery` | `prefix` 长度 1–4 字符 |
| `volunteer_activity` | 经纬度成对出现或成对为空 |

**外键补全 4 处**：`organization.reviewed_by_admin_id` → admin_account；
`activity_enrollment.volunteer_uid` → user_account；`alert_delivery.session_id` 与
`voice_message.session_id` → realtime_session（报警自动呼叫与留言的来源会话从
"字符串引用"变成数据库兜底）。

**可读性**：约束命名统一 `pk_/uq_/fk_/ck_<表>_<含义>`、索引 `ix_<表>_<含义>`；
26 张表全部带中文 COMMENT，按外键依赖分 8 节排序建表；`docs/final/db/schema.sql`
重写为与 Flyway 基线逐字同步（此前文档与活库双向漂移：文档缺 `user_role` 等
7 张活表，活库缺文档里的导航表）。

### 2.3 约束逼出来的两个真实代码缺陷（重构的核心收益）

没有数据库约束兜底，这两处 bug 在原库里静默存在：

1. **`volunteer_application.decided_by_admin_id` 从未落库**。
   `conditionalUpdate` 只写 `status` + `decided_at`，审核人只在内存对象上赋值用于拼
   响应 —— 数据库里这一列永远是 NULL。新 CHECK `ck_vol_app_decided` 要求
   APPROVED/REJECTED 行必须同时有审核人与审核时间，直接把这个存量缺陷暴露出来。
   已修复：`conditionalUpdate` 增加 `decidedByAdminId` 参数并随 UPDATE 落库。
2. **`voice_message.session_id` 是客户端自由传入且不校验的**。加外键
   `fk_voice_message_session` 后，伪造会话 ID 会从"静默存下悬空引用"变成外键违例
   500。已在 `VoiceMessageService.create` 补归属校验（来源会话必须存在且双方正是
   留言双方，否则 404），并在测试中补 2 例。

### 2.4 一条约束的语义修正（约束也要接受写路径检验）

第一版把 `realtime_session` 的 CHECK 写成"ENDED ⇒ `accepted_at` 非空"，真库复测时
发现 `end()` 允许**直接取消待接受的会话**（REQUESTED → ENDED，此时从未接通）——
这是合法业务路径，约束写错了而不是代码错。已放宽为 `ACTIVE ⇒ accepted_at`
（REQUESTED 被直接结束时可不填），并用 6 例真库用例钉住：取消放行、ACTIVE 缺
`accepted_at` 拦截、全链路、缺 `ended_at` 拦截、结束人外键拦截。

方法论沉淀：**每条新约束上库前，先 grep 出全部写入路径逐个核对；上库后，在真实
MySQL 上对"合法路径放行 + 非法路径拦截"两侧都做冒烟**。本次全部约束都过了这个
流程（真库验证 26 表 / 135 约束 / 冒烟 20+6 例全绿；Java 全量测试通过）。

### 2.5 升级指引（必读）

```sql
-- 旧库含 V1–V11 的 Flyway 历史与旧 checksum，直接启动新代码会校验失败。

```

`HighestAdminBootstrap` 自动播种权限/角色与首个最高管理员。

## 3. Python 端整体移除

### 3.1 删除内容

| 删除项 | 原用途 | 说明 |
|---|---|---|
| `server-python/`（24 文件） | FastAPI 导航推理服务（ONNX 引擎、空间分析、引导规则、WebSocket 采样） | 骨架代码，从未进入生产链路 |
| `sullivan-vision/`（5 文件） | 离线模型评测与 ONNX 导出（PyTorch + Ultralytics） | 一次性工具，模型早已换成端侧 YOLO26 + 深度模型 |
| `deploy/navigation/Dockerfile` | 导航容器编排 | 随服务一并失去意义 |

### 3.2 同步清理的引用

- `docker-compose.yml`：删除 server-python GPU 编排注释块，改为移除说明；
- `.env.example`：删除 `NAV_MODEL_PATH` / `NAV_DEVICE` / `NAV_PRECISION`；
- `.gitignore`：删除 Python 段（`__pycache__`/`*.py[cod]`/`.venv` 等）与训练产物段
  （`*.engine` / `*.pt` / `*.pth` / `model-training/`）；**保留 `*.onnx`** ——
  受护人端的 `yolo26n.onnx` / `yolo26n-depth.onnx` 仍按"不入库、本地放置"策略分发；
- 根 `README.md`：结构表、端口表、写入方描述同步更新。

### 3.3 刻意保留的"ONNX"（避免误伤）

- **Android 端侧 ONNX Runtime 不受影响**：`client-protectee` 的障碍检测
  （CameraX → 端侧 ONNX YOLO26 + 深度模型）是端内能力，帧不出设备，与服务端
  Python 无关，保持原样；
- `client-guardian` 里关于"onnx 依赖已随受护人端拆走"的历史注释保持原样（它们
  记录的是拆分决策，不是活引用）。

### 3.4 架构影响

- 部署单元从「Java + Python + MySQL + Redis」缩减为「**Java + MySQL + Redis**」，
  GPU 依赖彻底移出服务端；
- `06`/`13`/`05`/`03` 等设计文档中的 Java/Python 双应用章节已标注历史注记，
  文档正文不重写（它们记录的是当时的正确设计）；`16` 的 N-06（媒体不入库）
  等由 Python 语境引出的禁令依然有效，只是执行主体只剩 Java；
- 导航能力归属：**端侧（client-protectee）为唯一实现**，服务端导航 API
  （`NAV-01` 预留点）随 Python 移除一并撤销。
