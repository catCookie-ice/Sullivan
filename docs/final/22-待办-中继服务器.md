## 0. 这条待办是什么

语音 / 视频 / 摄像头会话的媒体走 WebRTC。判断中继服务器是否必要，只看一条：

> **受护人与监护人不在同一个局域网时，通话能不能建立。**

两端在同一 Wi-Fi 下时，靠主机候选（host candidate）就能直连，不需要任何服务器。
但真实场景是：受护人在家、监护人在公司或路上，中间隔着运营商 NAT 与防火墙，
**打洞（STUN）并不总能成功**——对称型 NAT、双重 NAT、部分企业网络下必然失败。

TURN 就是那个「打不通时帮忙转发」的角色：双方把媒体推给中继，中继再转给对方。
它不改变媒体本身的加密（WebRTC 媒体是 SRTP），只负责转发字节。

| 名称 | 作用 | 本项目现状 |
|---|---|---|
| **STUN** | 告诉设备「你在公网上长什么样」，用于打洞 | 有（默认公共 STUN） |
| **TURN 中继**（本条待办） | 打洞失败时**转发**媒体 | **没有** |

## 0.1 现状与差距

后端的**凭据侧已经做完了**，缺的只是那台服务器本身。具体：

| 项 | 现状 | 位置 |
|---|---|---|
| 临时凭据签发 | **已实现** | `IceServerService`：`username = <过期时间戳>:<账号ID>`，`password = base64(HMAC-SHA1(secret, username))` |
| 下发给客户端 | **已实现** | `GET /api/v1/realtime/ice-servers` |
| 配置项 | **已就位但为空** | `app.webrtc.turn-urls` / `app.webrtc.turn-secret` |
| 中继服务器 | **没有** | — |
| 客户端的诚实提示 | **已实现** | 没有 TURN 时如实提示「没有可用的中转服务器」，不假装已接通 |

也就是说：**空的是 `WEBRTC_TURN_URLS` 与 `WEBRTC_TURN_SECRET` 这两个值，以及它们指向的那台机器。**

当前的实际能力边界：同网段可通话；**跨网不可用**，且用户会看到明确提示而不是假成功。

## 1. 已经勘察到的环境事实

这些是实测得到的，不是推测。落地时直接受影响，先记下来避免重复踩：

| 事实 | 影响 |
|---|---|
| 已有一台阿里云 ECS，系统为 **Windows Server 2025**（2 vCPU / 2 GiB） | 决定实现路线，见 §2 |
| 该机 Docker 为 **Windows 容器模式**（`OSType: windows`） | **跑不了 coturn**（coturn 只有 Linux 镜像） |
| `Hyper-V 功能不可用`；WSL / VirtualMachinePlatform 均 `Disabled`；`VirtualizationFirmwareEnabled=False`、`SecondLevelAddressTranslation=False` | 阿里云普通实例**未开放嵌套虚拟化**，因此 WSL2 / Hyper-V 隔离都走不通，无法在该机运行 Linux 容器 |
| 安全组**未放行** 3478 / 5349（外部探测为 filtered），系统防火墙本身是关闭的 | 端口必须在**安全组**放行，改服务器本地防火墙无效 |
| 公网带宽为 **1 Mbps 固定带宽** | 中继是双向流量，一路视频约 1–2 Mbps，**带不动视频**；语音（约 50–100 kbps）可以 |
| ECS 公网 IP 为 NAT 映射，网卡上只有私网地址 | 中继必须显式通告对外地址，否则会把一个客户端连不上的私网地址发出去，且**不报任何错** |

> 公网 IP、登录账号与口令等敏感信息**不写入仓库**，只在部署时由运维提供。

## 2. 两条候选路线

### 路线 A：换成 Linux + coturn（业界标准）

把实例系统盘更换为 Ubuntu 22.04，按标准方式跑 coturn。

- 优点：coturn 成熟、配置项齐全、与后端已有的 REST 凭据算法天然匹配；
  社区资料多，出问题好查。
- 代价：需要重装系统（实例当前为空，不丢数据）；运维需要熟悉 Linux。
- 适用：这台机器可以交给 Linux，或后续还要跑 `server-java`。

### 路线 B：Windows 原生实现（Go + pion/turn）

用 Go 写一个 TURN 服务，交叉编译成 Windows 可执行文件，注册为 Windows 服务。

- 优点：不动系统；单个 exe，无运行时依赖；`pion/turn` 已是成熟实现，
  且其 `LongTermTURNRESTAuthHandler` 的算法与后端 `IceServerService` **逐条一致**
  （`<过期时间戳>:<用户>`、HMAC-SHA1、base64、MD5 长凭据键）。
- 代价：多一个需要自己维护的组件；Windows 服务化、日志与升级要自己想清楚。
- 适用：必须保留 Windows，或短期内不想重装系统。

> **路线已定：A（coturn）。** 2026-10-26 由项目负责人确认——后续愿意使用 coturn 开发
> 中继服务器，因此**不采用**路线 B 的 Windows 原生实现。
>
> 这条决定带来一个前置条件：**当前这台 ECS 是 Windows Server，跑不了 coturn**
> （见 §1 的容器与虚拟化事实）。所以开工第一步不是写配置，而是把该实例的系统盘
> 更换为 Linux（实例为空，不丢数据），或者另开一台 Linux ECS。这一步没做之前，
> 后面的配置、端口、验证都无从谈起。
>
> 原文的路线 B 保留在下面，仅作为「当时为什么考虑过它」的记录，不再是当前选择。

## 3. 两条路线共同的约束（红线）

1. **凭据不得写进客户端、不得进仓库。** 只能由后端按 TTL 临时签发。
   长期固定的 TURN 账号一旦发出去就撤不回，反编译即得。
2. **必须禁止中继到内网段**（`10/8`、`172.16/12`、`192.168/16`、`127/8`、`169.254/16`、IPv6 本地段）。
   没有这条，任何拿到临时凭据的人都能把这台中继当成**跳板**去探测同 VPC 的其它主机。
3. **对外地址必须显式配置**（公网 IP / 私网网卡 IP 两段）。漏了不会报错，
   只会让所有媒体连接静默超时。
4. **中继端口段必须整段放行**。只开 3478 的典型症状是：握手成功、日志正常、
   一开始传媒体就断。
5. **带宽要按「双向」估算**。1 Mbps 带不动视频，必须先提升带宽（建议按使用流量计费）。
6. **secret 强度**不少于 32 字节随机值；怀疑泄露时立即更换（在途凭据随之失效）。

## 4. 验收标准

做到下面全部算完成，缺一条都不算：

| # | 验收项 | 判定方式 |
|---|---|---|
| 1 | `GET /api/v1/realtime/ice-servers` 返回的 `urls` 同时含 `stun:` 与 `turn:` | 接口返回 |
| 2 | 同一接口返回的 `username` / `credential` 非空，且 `ttlSeconds` 与配置一致 | 接口返回 |
| 3 | 用**后端签发**的凭据能从中继拿到 relay 候选 | 服务日志出现 relay 地址 |
| 4 | relay 地址是**公网 IP**，不是私网地址 | 检查中继分配日志 |
| 5 | 两端处于**不同网络**（如一方 4G、一方宽带）能建立通话 | 实际通话 |
| 6 | 该通话选中的候选对类型为 `relay` | `chrome://webrtc-internals` 或 Android 侧等价信息 |
| 7 | **过期**凭据被拒绝 | 用已过期 username 请求，应被拒 |
| 8 | **错误** secret 算出的凭据被拒绝 | 用错 secret 请求，应被拒 |
| 9 | 中继**不能**访问内网段 | 尝试以 `10.x` / `192.168.x` 为 peer，应被拒 |
| 10 | 服务开机自启、日志可查、可停止与重启 | 重启实例后验证 |

第 5–6 项是这条待办的**真正目的**；前三项只是「配置生效」，不代表跨网可用。

## 5. 开工前要先确认的三件事

1. **系统路线**：A 还是 B（见 §2）。
2. **安全组**：谁来放行 `3478/udp`、`3478/tcp` 与中继端口段（UDP）。
   实例内没有 RAM 角色时，我无法调用 ECS API 改安全组，必须由运维在控制台操作，
   或提供具备 ECS 权限的 RAM 凭据。
3. **带宽**：是否已改为按使用流量计费或提升固定带宽。这一项不解决，验收第 5 项过不了。
