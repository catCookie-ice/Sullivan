# SullivanMINI 开发日记：2026-10-24（下午）—— YOLO26 + 深度测距 + 报警自动呼叫

**本文接上午那篇 `17-开发日记-2026-10-24.md`**（登录角色改判）。同一日期两篇，

## 0. 这次要解决的两件事

1. **距离估算不准确**。原来的"近"是一个纯几何启发式：框下沿够低、或框面积够大，就算近。
   它没有单位，说不出"多远"，只是在猜"是不是该提醒了"。
2. **报警之后没人管**。报警仅仅被记录成一条数据库行，没有任何东西会主动去叫人。
   受护人摔倒了、手机掉在地上，监护人那边什么动静都没有。

对应到功能项是 FR-06（位置）与 FR-11~FR-13（报警、通知、实时会话）。

## 1. 端侧模型换成 YOLO26，并接入深度模型

### 1.1 为什么是 YOLO26，以及一个**我一开始记错了**的结论

用户要求换成"同等级的 YOLO26"。做了实测确认（不是查文档，是真跑了一遍）：

| 模型 | 输入 | 输出 | 说明 |
|---|---|---|---|
| `yolo26n.onnx`（**官方默认**，`end2end=True`） | `[1,3,640,640]` | `logits [1,300,80]` + `pred_boxes [1,300,4]` | **两个**张量，自带 NMS |
| `yolo26n-depth.onnx` | **`[1,3,768,768]`** | `[1,1,768,768]` float32 | 逐像素，单位是**米** |

**注意上表里两个输入尺寸不一样，这是实测出来的，不是笔误。**

**我这次的错误值得记下来。** 上午我导出的那份是 `end2end=False`，看到 `[1,84,8400]`
就下了结论"YOLO26 与 YOLOv8 输出布局完全相同，解码器一行都不用改"。
这个结论**对一半**：它只对"我特意关掉 end2end 的那份导出"成立。
用户从官方 release 下载的默认权重是 **`end2end=True`**，输出是两个张量，
于是换上之后检测**完全失效** —— 不是权重坏了，是解码器读错了张量
（把 300 个 4 维框当成 8400 个 84 维候选）。

教训很直接：**"我导出的那份"不等于"用户会拿到的那份"**。默认值属于接口的一部分，
验证形状时必须验默认导出的形状，而不是自己顺手改过的参数。

### 1.2 只支持 YOLO26，不再兼容 YOLOv8

按用户指示（"只用适配较新的 26n 版本，不用适配 8n"），把旧的
`[1,84,8400]` 解码路径与自制 NMS **整段删掉**了，不是留着不用。

为什么删而不是留：两条解码路径同时存在，意味着"同一份画面走哪条路"取决于用户
放了哪个文件；出问题时先要猜走的是哪条。而本应用的模型是随包固定分发的，
不需要这种灵活性 —— 放错模型时**明确报错**（`checkEndToEndLayout` 会抛出带实际
形状的异常）比"能跑但结果对不上"好得多。

顺带做了两处清理，避免名不副实：

- 类名 `YoloV8Detector` → **`Yolo26Detector`**（文件名一并改）。
- 构造参数去掉 `iouThreshold`：end2end 自带 NMS，留着这个参数只会让人
  误以为它还在生效。
- `DepthMap` 的 `inputSize` 字段与 `fromTensor` 的同名参数一并删除。它是
  "共用张量"时代的遗留物，public 且**没有任何地方读**。留着它的危险在于：
  名字看起来正是"把归一化坐标换成像素"要用的东西，而那样换算是**错的**
  （必须先加回灰边偏移）。唯一正确的入口是 `distanceAtFootprint`，
  它强制调用方传入**深度自己的** `Letterbox`。删掉诱饵比写注释更有效。

`end2end` 解码的三条语义，每条都是拿 `bus.jpg` 实测出来的：

1. **分数要过 sigmoid**。这里是原始 logits，不是概率。实测 bus 得 `2.517`、
   person 得 `2.378`，sigmoid 后是 `0.925` / `0.915`，与 ultralytics 自己的结果一致。
   **不过 sigmoid 就会"什么都检测不到"** —— 因为阈值远高于 logits 里的
   真实低分，而高分项又因为被当成"概率"而意义不对。
2. **框是 `cx,cy,w,h` 归一化到 640×640 输入**（含灰边），不是内容区。
   所以乘 `inputSize` 得像素、再减 `pad` 才回到内容区。这一点和 §1.4 那个
   内容区/整图的坑是同一类问题，只是方向相反。
3. **不要再跑 NMS**。end2end 导出里已经做过（300 个槽位按分数排好）。
   二次抑制会让小目标消失。

实测输出的最终结果（`bus.jpg`，阈值 0.35）：

```
bus     0.925   → 1 个
person  0.915 / 0.899 / 0.860 / 0.525 → 4 个
合计 5 个检测
```

`bus.jpg` 的真实内容就是 1 辆公交 + 4 个行人。坐标换算也验证过：
bus 的 `left=0.007`（贴左缘）、`right=0.996`（几乎到右缘）、`top=0.212`、
`bottom=0.694`（贴地），与画面相符。

### 1.3 深度是独立模型：而且**输入尺寸不一样**

这是这次最容易误解、我也确实先误解了一次的一点。YOLO26 把深度做成了另一条
任务线（`task=depth`），权重名带 `-depth` 后缀，检测模型**不会**顺带输出深度。

**第一版的设计是"共用一份预处理张量"**，理由是"两个模型看逐像素相同的画面，
分开 letterbox 会引入系统性偏移"。这个理由本身没错，但它建立在一个**错误前提**上：
我以为两个模型都是 640 输入。

实测官方权重后：

```
检测 yolo26n.onnx        输入 [1,3,640,640]
深度 yolo26n-depth.onnx  输入 [1,3,768,768]    ← 768，不是 640
```

拿 640 的张量喂 768 的模型，ONNX Runtime 直接拒绝：

```
Got invalid dimensions for input: images for the following indices
 index: 2 Got: 640 Expected: 768
```

**所以必须各做各的 letterbox。** 代价是多一次缩放（相对 85 ms 的推理可忽略），
换来的是两个模型都拿到符合自己期望的输入。至于"系统性偏移"那个担忧，
正确的对策不是"共用张量"，而是**把各自的几何参数显式传下去**：

```java
Yolo26Detector.Prepared prepared = current.preprocess(frame);  // 640
detections = current.detect(prepared);                          // 第一遍
depth      = currentDepth.predict(frame);                       // 第二遍，768，自己的 letterbox
Letterbox depthGeometry = currentDepth.letterboxOf(frame);      // 768 的几何
```

于是产生一个新的、更隐蔽的风险：检测框是在 **640** 的几何下归一化到内容区的，
而深度图是 **768** 的几何。把框换算成深度像素时**必须用深度那一份参数**。
用错不会崩，只会静静地采样到旁边几十像素处 —— 通常是背景地面，
读出来是"几米开外的地面"，表现得像"深度模型不准"。

这条风险有两个用例钉着（`DepthGeometryTest`）：

- `detectAndDepthUseDifferentLetterboxGeometry`：断言 640 与 768 的 padY
  分别是 140 与 168，**必须不同**。谁把两者"统一"成 640，这条立刻红。
- `usingDetectLetterboxForDepthReadsWrongPixel`：造一个沿 y 单调递增的深度场，
  断言两种几何读出的米数不同、且方向符合预期。若相等，说明 letterbox
  根本没参与换算。

### 1.3A 深度隔帧跑（7.8 FPS 是不能用的）

实测真实权重的推理耗时（桌面 CPU，i5-13500HX）：

| 模型 | 输入 | p50 |
|---|---|---|
| 检测 | 640 | 43.1 ms |
| 深度 | 768 | 84.6 ms |
| 合计 | | **127.7 ms/帧 → 7.8 FPS 上限** |

而这是**桌面机**，手机只会更慢。所以深度改为**隔 2 帧跑一次**
（`DEPTH_INTERVAL_FRAMES`），检测仍然每帧跑：

- 隔帧的代价是米数最多滞后一个深度周期 —— 对"1.5 米处有人"这种提示完全可接受。
- 帧率掉下去的代价是**立刻能感觉到的卡顿**，而卡顿会直接毁掉避障体验。

复用旧深度图时**必须校验几何没变**（`sameGeometry`）：转屏或换分辨率后，
旧图的像素坐标与新一帧对不上，硬用会读出错误的距离。这一点如果漏了，
表现为"横屏之后距离突然全错"。

（`DepthMap.fromTensor` 把数据拷进了自己的 `float[]`，所以跨帧持有是安全的 ——
如果它只是 ORT 缓冲的视图，下一次推理就会把上一帧的值覆盖掉。）

### 1.4 一个真实的 bug：坐标空间没对上

**这段是本次最值得读的部分**，因为第一版写错了，而且错得很隐蔽。

`Yolo26Detector` 的解码把模型输出的框换算成：

```java
float left = (centerX - width * 0.5f - letterbox.padX) / letterbox.contentWidth;
```

注意它**减了 pad、除了 content**。也就是说 `Detection` 的坐标是相对
「**正立画面的内容区**」归一化的，不是相对「整张 640×640 letterbox 输入」。

而深度图是整张 letterbox 输入（含灰边，且**是 768 而不是 640**）。

我的第一版直接拿归一化坐标乘 `inputSize` 去索引深度图：

```java
int centerX = Math.round((left + right) * 0.5f * inputSize);   // ← 错
```

后果：采样点朝左上角偏，偏移量正好是 pad。16:9 画面上下各 140 px（768 下是 168 px），
采样点会落到背景地面上，读回来的距离是"几米开外的地面"而不是"眼前这个人"。

修法是把 `Letterbox` 一路传进 `DepthMap.distanceAtFootprint`：

```java
float centerX = (left + right) * 0.5f * letterbox.contentWidth + letterbox.padX;
float footY   = bottom * letterbox.contentHeight + letterbox.padY - boxHeightPx * FOOT_LIFT_RATIO;
```

并且专门补了一个用例 `footprintAccountsForLetterboxPadding`：算出"正确"与
"忽略灰边"两种算法的采样行，把分割线放在两者中间，断言必须取到正确那一侧。
它现在盯着的就是这个回归。

### 1.5 采样点为什么在框下沿往上 15%

框中心取到的是"胸口"，那是人身体离相机最近的点之一，会把距离系统性地报近。
真正决定"会不会撞上"的是**脚与地面的接触点**，也就是框下沿。
但下沿正好是框与地面的边界，框稍有偏差就会踩到地面像素（那是几米外的背景）。
所以往上抬 15% 个框高，取一个折中位置。

窗口取 **7×7 中位数**，不是最小值：最小值的抗噪能力是零，一个孤立的错误像素
（地面反光、玻璃、窗外的天空）就能把"4 米"变成"10 厘米"，进而触发一次误报警。
中位数只要求窗口内**多数**像素正确。

### 1.6 深度读数不可信时怎么办

`00` §7.5 明确要求：拿不到可信深度时**不得**给出自信的米数。
所以 `DistancePolicy.metersOf` 在无深度、动态维度、超出 `[0.05, 80]` 米范围时
一律返回 `NaN`，然后：

- `ObstacleAdvisor.describe` 在 `NaN` 时**完全不提米数**，退回改造前的措辞；
- 判"近"退回原来的几何启发式（`NEAR_BOTTOM_RATIO` / `NEAR_AREA_RATIO`）。

这条降级路径是**逐字节兼容**的：没有深度模型时，行为与改造前完全一样。
不是"差不多一样"，是同一段代码。

### 1.7 米数放在句首

`"1.5 米处中央行人，注意"` 而不是 `"中央行人，1.5 米处，注意"`。
盲人用户的注意力集中在句子开头，而且 TTS 一开口的那一瞬间最容易被环境噪声盖住。
多目标簇**不报米数**：每个成员距离不同，报一个数必然是错的。

### 1.8 深度模型坏了不能拖垮障碍检测

`predict` 包在自己的 try/catch 里，失败只是这一帧没有米数，下一帧还会再试。
一次 OOM 之后恢复是很常见的；因为深度模型出问题就连障碍检测一起停掉，
是把增强功能的故障放大成主功能故障。

## 2. 报警 → 5 秒 → 依次呼叫监护人

### 2.1 为什么用定时任务，而不是 `Thread.sleep(5)`

这是本次第二个关键决定。直觉做法是在创建报警的请求线程里睡 5 秒再打电话。
它有两个硬伤：

1. **占着请求线程**。Tomcat 线程池是有限的，几个报警同时进来就会占满。
2. **重启即丢失**。服务重启、发布、崩溃，那 5 秒里的排期就没了 ——
   而报警恰恰是最不能丢的东西。

所以做成：创建时写 `auto_session_due_at = now + 5s`，
`AlertAutoDispatchJob` 每秒扫一次到期记录。重启后扫描自然接上。

**单赢家语义**用条件更新保证：

```sql
UPDATE alert SET auto_session_state='RUNNING'
WHERE id=? AND auto_session_state='SCHEDULED'
```

返回 0 行说明别人已经领走了，本次跳过。多实例部署下也不会重复呼叫。

### 2.2 "依次"是真依次，而且顺序是确定的

用户的原话是"依次发出会话请求"。这**不是**同时给所有监护人打电话 ——
那样每个人的手机一起响，谁接都尴尬，而且监护人会互相以为别人在处理。

顺序按 `confirmed_at ASC, id ASC`（绑定确认时间，同刻按 ID 兜底）。
选这个而不是"随机"或"按距离"：

- 它是**确定**的，同一个报警在任何一次重试、任何一个实例上都算出同样的顺序；
- 它对应一个真实的语义：**最早确认绑定的监护人，通常是最上心的那个人**；
- 顺序落库在 `alert_delivery.dispatch_order`，出问题能复盘。

### 2.3 两条独立的状态线

这是设计上刻意的解耦，容易看错：

| 线 | 取值 | 含义 |
|---|---|---|
| `alert.status` | `CREATED / DISPATCHED / NO_RECIPIENT / RESOLVED` | 报警本身的生命周期 |
| `alert.auto_session_state` | `NONE / SCHEDULED / RUNNING / SKIPPED / DONE` | 那通 5 秒后的自动电话 |

它们**会交错**：监护人可能在 t=3 秒主动回拨，把自动呼叫取消掉（`SKIPPED`）；
也可能报警已经 `RESOLVED` 了，而那通电话还在响。合成一个状态机就表达不了这些。

### 2.4 `openSession` 为什么不复用 `RealtimeSessionService.create`

`create` 在已存在活跃会话时返回 409。但对自动派发来说，**已存在活跃会话是好消息** ——
说明已经有人在打这通了。这时候应该复用并把投递标记成 `SENT`，而不是报错。

所以 `RealtimeAlertDispatcher.openSession` 自己实现了：
先找两个方向上任何一条 `REQUESTED/ACTIVE` 的会话，有就复用，没有才创建。

### 2.5 开关：默认开，且是服务端状态

用户要求"此功能可由用户手动关闭，默认开启"。

- 默认值是 **开**，实现方式是**"没有配置行 = 开"**，只有显式 `FALSE` 才关闭。
  写成"没有行 = 关"的话，新注册用户在数据库插入第一行之前行为是不确定的。
- 存在服务端而不是本机：换设备、重装应用，行为应当一致。
- 关闭时不仅影响**之后**的报警，还会把已经 `SCHEDULED` 的报警翻成 `SKIPPED` ——
  用户关开关的意思是"别再打过来了"，正在排期的那通也在其中。

### 2.6 客户端触发：手动 + 碰撞

用户要求"两者都要"。

- **手动**：屏幕底部一个整行高 72dp 的「紧急求助」按钮。位置必须在拇指自然落点，
  不是右上角那种"看得见的人才找得到"的地方。按下先弹确认 —— 手掌压到屏幕
  就把所有监护人叫起来的代价太高。
- **碰撞自动**：`ObstacleAdvisor.Level.DANGER` 触发，但不是"见到 DANGER 就报"。

自动触发有两个必须解决的问题，都在 `CollisionAlertGate` 里：

1. **DANGER 是电平信号，每帧都成立**。直接报警等于每秒发一次。
   所以取**上升沿**，并要求**持续 800ms**（单帧 DANGER 可能是误检）。
2. **一次出行会遇到好几次真危险**。所以有 **3 分钟冷却**。

冷却期（3 分钟）**刻意短于**幂等窗口（5 分钟）。这样冷却结束时的第二次触发
仍落在同一个幂等桶里，服务端返回**已有**那条报警而不是新建一条 ——
短时间内的第二次自动触发不该再骚扰一轮监护人。这个关系有测试盯着
（`cooldownShorterThanIdempotencyWindow`），因为把两个常数改反了不会崩，
只会让监护人的手机响个不停。

### 2.7 幂等键用时间桶，不用随机串

随机串无法判断"上一次的键还在不在窗口内"，于是每次调用都生成新键，幂等全部失效。
时间桶（`now / 5min`）天然满足"窗口内相同、窗口外不同"。

键里带 `alertType`：同时发生的 MANUAL 与 COLLISION 是两件事。

## 3. 位置：为什么平时一直上报，而不是报警时才定位

报警是紧急事件，那一刻才开 GPS，冷启动首次定位常要十几秒、室内还可能拿不到 ——
而那十几秒恰好是"人在哪"最值钱的时间。平时每 10 秒轻轻上报一次，
报警时就能立刻取到几秒前的位置。报警前还会再强制刷一次，把这个窗口压到最小。

用 `LocationManager` 而不是 FusedLocationProvider：后者要引入 Google Play Services，
而本模块刻意只用 AndroidX + CameraX，不绑定 GMS（国内设备普遍没有）。
代价是精度略差，所以 `accuracyM` 一起上报，让监护人自己判断可信度。

省电：只注册 `PASSIVE_PROVIDER`（系统在别的应用定位时顺带给我们），
不主动 `requestLocationUpdates`。本模块主任务是摄像头推理，再开一路主动定位
会明显加剧发热 —— 而受护人端本来就在耗电。

生命周期：只在主界面可见时跑，`onPause` 即停。位置不该在用户没在用守护功能时持续外发。

## 3A. 顺带修掉的两个问题（用户实测反馈）

### 3A.1 剧烈晃动判定过于宽松

用户原话："现在判定为剧烈晃动的条件太过于宽松。"

四个阈值全部收紧，逐个说清理由：

| 常量 | 原值 | 新值 | 理由 |
|---|---|---|---|
| `PEAK_RAD_PER_SEC` | 2.5 | **4.0** | 2.5 落进了**快速转身**区间（1.5–3.5）。转身是每天几十次的日常动作，算进摔倒等于误报率高到用户会关掉这个功能。4.0 高于转身上沿、低于真实撞击（3–8 偏上） |
| `MIN_JERK_RAD_PER_SEC2` | 20 | **30** | 峰值门限提高后这道门承担更多过滤；20 会被"走路时一次正常摆臂"（15–25）触碰 |
| `IRREGULARITY_RATIO` | 1.5 | **1.8** | 1.5 的余量是按 50 Hz 估的，实际设备常见 50–100 Hz 抖动，量化误差更大 |
| `TRIGGER_COOLDOWN_MS` | 6000 | **15000** | 一次真实摔倒会在数秒内反复满足条件（人还在挣扎、手机还在晃）；面板也需要用户阅读与反应的时间 |

**取舍原则写清楚了**：宁可漏报也不要多报。这是**求助**功能，不是安全认证 ——
漏报的代价是回到"没有这个功能"的状态（用户还能手动按求助），
而多报的代价是每次转身都给监护人打一通电话，那会让人直接卸载应用。

顺带修了一处**测试自身的错误**：`theCooldownSuppressesARepeat` 原本硬编码断言
"8 秒后再晃应当触发"，那正好落在新的 15 秒冷却期内。已改成按
`ShakeDetector.TRIGGER_COOLDOWN_MS` 推算，并补了一条"11 秒仍在冷却里"的断言。
新增两个用例：`aFastTurnDoesNotTrigger`（3.2 rad/s 转身不触发）与
`peakThresholdSitsAboveDailyMotionAndBelowImpact`（关系型断言，把"必须落在
3.5 与 6 之间"这件事钉死 —— 改回 2.5 这个测试会红）。

**诚实地说**：这四个值仍然是**工程估计，没有真机标定**。真正该做的是让用户
在不同动作下各走 2 分钟，看误报率与漏报率，再回来调。现在的收紧方向是对的，
但"4.0 这个具体数字"没有数据支撑。

### 3A.2 扫码登录后顶部不显示受护人账号

用户原话："扫描登录受护人账户后，登录名应该正常显示登录的受护人，而不像现在这一不显示。"

查下来是**两个问题叠加**，任何一个单独存在都会导致"看不到名字"：

1. **主界面根本没有显示账号的地方**。`ProtecteeActivity` 从来就没有这个控件 ——
   不是"显示了空字符串"，而是压根没渲染。
2. **扫码登录把名字丢了**。`QrLoginActivity` 兑换完令牌后调用
   `saveLogin(..., accountLabel = null)`，硬编码传 `null`。
   而轮询响应里其实**有** `protecteeName`（服务端在 `SCANNED` 和 `CONFIRMED`
   两个状态都填了），客户端读都没读。

修法：

- `QrLoginActivity` 在 `onStatus` 里把 `protecteeName` 存进字段 `signedInName`，
  兑换成功时传入 `saveLogin`。
- `ProtecteeActivity` 新增顶部「当前账号：%s」一行，三级兜底：
  登录名 → 显示名 → 「已登录」，**任何一级都不留空白**。

**为什么名字必须从轮询响应带过来**：兑换返回的 `TokenResponse` 只有 `principalId`，
没有名字；轮询响应有名字但没有登录名。两个响应拼起来才够显示 ——
不在中间接这一下，界面能显示的就只有一串 26 位 ID，等于没显示。

### 3A.3 监护人扫完登录码"什么都没发生"：401 没有出口

用户原话："监护人扫描受护人端的登录二维码后直接结束，既没有选择登录的受护人，
受护人端也没有任何登录完成。"随后用户自己定位到了根因：
"**监护人端的登录掉了，却没有踢下线，也没有明显提示**（提示在页面最末尾）。"

这是本轮最有价值的一个 bug，因为它**不是扫码逻辑坏了**，而是错误报告的位置错了。

#### 故障链

四件事叠在一起，缺任何一环都不会表现成"什么都没发生"：

1. 服务端在令牌过期后对 `/qr/login-tickets/{ticket}/scan` 返回 **401**。
2. `GuardianActivity` 的扫码回调里**没有任何 401 判断**，401 被当成普通错误，
   写进 `statusText`。
3. `statusText` 是页面**最末尾**那个 TextView。用户扫码时视线在自己手机上半部分
   或对方屏幕上，根本不会看那一行。
4. `SessionStore.isLoggedIn()` **只判断令牌字符串是否非空**，不存也不校验过期时间。
   令牌过期后本地仍然返回 `true` —— 于是应用一直"以为自己还登着"，
   既不踢下线，也不再尝试重新登录。这就是"掉了却没踢"的机制性原因。

结果是：用户看到的就是扫码页一闪而退，然后一片平静。

#### 修法：把 401 的判断收拢到唯一出口

一开始我只在 `GuardianActivity` 的四个回调里各加了一处 `handleUnauthorized`。
这能修掉本次现象，但**根因没动**：项目里 `handleUnauthorized` 被复制了五份
（`BindingListActivity`、`RealtimeActivity`、`VolunteerApplyActivity`、
`CreateProtecteeActivity`、`ActivityListActivity`），每份语义还不完全一样，
而 `GuardianActivity` 一份都没有。下一个新页面照样会漏。

所以改成在网络层拦截。`ApiClient.attachToken` 本来就在拦每一个请求，
在它返回前检查状态码即可覆盖**所有**接口：

- 新增 `ApiClient.LoginExpiredListener` 作为进程级观察点；
  收到 401 时先 `session.clearLogin()`，再通知订阅方。
- 新增纯函数 `AuthExpiry.shouldExpireSession(httpCode, sentToken)` 承载判断。
- `GuardianActivity` 订阅它：**任何**请求 401 都会立刻提示。

**为什么不能"见到 401 就清会话"**：登录接口自己在账号密码错误时也返回 401。
若无条件清会话，一个已登录的用户误输一次密码就会被顺手踢下线。
区别在于登录请求**没有带令牌**，而"令牌失效"的前提是我们确实带了一个令牌去 ——
这就是 `sentToken` 这个参数存在的全部理由。它被单测钉住了
（`AuthExpiryTest.unauthorizedWithoutTokenDoesNotExpireSession`）。

#### 提示为什么必须是对话框/Toast，而不是状态文字

这次故障的教训是：**错误提示的位置和错误本身一样重要**。
一个写在页面末尾的提示，在用户视线不在那里的时候，等于没有提示。
所以失效提示用不可取消的对话框，确认后直接回登录页 ——
此时用户已经没有有效身份，留在主页做任何操作都只会再得一次 401。

还有个容易忽略的细节：401 可能发生在**别的页面**上（用户从主页点进了
绑定列表，而主页只是 stopped 尚未 destroy）。此时直接 `Dialog.show()`
会弹到用户看不见的页面上，甚至触发 `WindowLeaked`。所以分两种处理：

- 主页在前台 → 弹对话框；
- 主页不在前台 → 先发一条 **Toast**（Toast 是系统级的，会显示在用户
  当前真正在看的那个页面上），并记下 `pendingSessionExpiredDialog`，
  等主页 `onResume` 时补弹对话框。

这样无论 401 从哪个页面冒出来，用户都会立刻知道。

#### 受护人端同一类问题的不同后果

受护人端**完全没有** 401 处理，而它的 401 后果比监护人端严重得多：
报警发不出去。`AlertClient.Callback.onFailed` 原来只回传 `String`，
状态码在那一层就被抹掉了，界面即使想分辨"网络不通"和"登录失效"也分辨不出来。

改动：

- `AlertClient.Callback.onFailed` 改收 `ApiException`（保留状态码）；
  本地无身份时构造 `401` 让界面走同一分支。
- `ProtecteeActivity` 对 401 单独给文案「登录已失效，报警没有发出」，
  与「求助发送失败」分开说 —— 前者意味着必须先去重新登录，
  在此之前每一次求助都不会被任何人看到。这是安全相关的差别，不能合并。

#### 一句话规则

> **令牌失效是一个跨页面的横切关注点，不该在每个 `onError` 里各写一遍。**
> 判断放在网络层唯一出口，提示放在用户视线所在处。

## 3C. 两个用户实测反馈的故障：拿不到位置、收不到来电

这两条都不是"某个函数写错了"，而是**整条链路上缺了一环**，
而且两条的缺法出乎意料地相似：功能都只在"正常路径"下成立，
一旦前提不满足就无声无息地什么都不做。

### 3C.1 没有办法获取地理位置

用户原话："没有办法获取地理位置。"

#### 根因：从来没有主动发起过一次定位

`LocationReporter` 的设计只用了两种位置来源：

1. `getLastKnownLocation`（读系统缓存的"最后已知位置"）
2. `PASSIVE_PROVIDER`（等**别的应用**定位时顺带给我们）

而 `reportOnce()` 在 `bestLastKnown()` 返回 null 时**直接 return**，
它是唯一的取位置入口。

于是有个致命空洞：设备刚开机、或用户从没用过任何定位应用时，
系统里根本没有缓存位置，被动更新也永远不会来 ——
**这个应用一次都没有主动请求过定位**。注释里那句
"不主动 requestLocationUpdates：会加剧发热与耗电"是对的，
但它没意识到"完全不主动"等于"可能永远拿不到"。

#### 修法

新增 `requestActiveFixIfStale()`：只在**手里没有新鲜位置**时才主动要一次，
优先 `NETWORK_PROVIDER`（室内可用、首次定位快、耗电低），
没有它再退 `GPS_PROVIDER`。拿到结果后立刻 `removeUpdates` 撤掉主动定位
（本模块的主任务是摄像头推理，GPS 长开会明显发热），
再补回被动更新。

`reportOnce()` 在拿不到位置时改为调用它，而不是默默 return。

#### 一个我自己加上去又必须处理的坑

主动请求在室内/地下室/用户关了精确定位时可能**一个回调都不来**。
那样 `activeFixRequested` 永远是 true，永远撤不掉、也永远不重试 ——
白白耗电却什么也拿不到。所以加了 30 秒超时（`ACTIVE_FIX_TIMEOUT_MS`），
超时后放弃这一轮，交给下一次周期任务重来。

**这不是"定位失败"的提示**，只是让下一次有机会成功。用户不该因为一次定位慢
就看到错误。

### 3C.2 受护人发起了紧急联系，监护人收不到通知

用户原话："即使受护人发起了紧急联系，监护人也收不到通知（服务器端已经建立了会话）。"

#### 根因：监护人端只在"用户主动点开那个页面"时才去查

服务端这一侧是通的 —— `AlertAutoDispatchJob` 在报警 5 秒后建会话、写
`realtime_session`、回填 `session_id`，这些都验过（§4.2）。
问题在客户端：

`GET /realtime/sessions` 这个接口在两个客户端里**只有一个调用点**：
`RealtimeActivity` 的列表刷新。也就是说，监护人必须**自己点开
「实时会话」页**，才会知道有人在呼叫他。

人不点，就永远不知道。而受护人按下紧急求助的那一刻，
监护人极可能正在做别的事、手机在口袋里锁着屏。

#### 修法：分两层，因为"应用开着"和"应用关着"是两件事

**第一层：主页在前台时轮询。**
`GuardianActivity` 在 `onResume`~`onPause` 之间每 5 秒拉一次列表，
用 `IncomingCallFilter.pending(...)` 挑出"状态 REQUESTED + 接收方是我 +
不是我自己发起的"那些，弹**不可取消的对话框**。
5 秒是对齐受护人端报警的 5 秒延迟：再短没意义（会话本身要 5 秒后才建），
再长就让受护人等太久。

**第二层：应用退到后台/锁屏时，靠前台服务。**
这是关键的一层。查下来监护人端**原本没有任何后台能力** ——
没有 Service、没有通知权限、没有通知代码。所以只加前台轮询只能覆盖
"应用正开着"这一种情形，而用户报的恰恰是另一种。

新增 `IncomingCallService`：常驻前台服务，同样 5 秒轮询，
发现来电就把通知升级成"有人正在呼叫你"（高优先级、响铃、震动），
点击进会话页。

#### 为什么是轮询，不是 WebSocket 推送

项目里已经有 `RealtimeSocket`，但它**必须绑定一个 `sessionId` 才能连**。
而这里恰恰是"我还不知道有哪些会话"的场景 —— 鸡生蛋问题。
要做真推送，得让服务端按账号开一条常驻通道（鉴权、心跳、重连、后台存活），
改动量是另一个量级。轮询 5 秒一次、最坏 10 秒可知，
对"报警后呼叫监护人"这个场景完全够用，且**不引入任何新依赖**。

#### 为什么是前台服务，不是 WorkManager

报警是**秒级**的事：5 秒延迟 + 轮询间隔就已经 10 秒。
而 WorkManager 的最小周期是 **15 分钟**，AlarmManager 在 Doze 下会被推迟到几十分钟。
唯一能稳定按秒级跑完的就是前台服务。代价是状态栏必须常驻一条通知 ——
这是 Android 的硬性规则。对"守护"这个定位来说反而合理：
用户随时能看到"我正在守着"。

#### 一个必须在文档里写明的平台约束

`targetSdk = 35`，而 **Android 14+ 对 `dataSync` 类型的前台服务限制每天 6 小时**，
超时系统会直接杀掉。对一个"全天候守着"的功能来说等于不可用。

所以类型用 `specialUse`（配 `PROPERTY_SPECIAL_USE_FGS_SUBTYPE`）而不是 `dataSync`。
`specialUse` 没有这个时限，代价是上架 Google Play 需要单独申报用途 ——
本项目是课程/毕业设计，不上架，故不受此限。**这条如果将来要上架，必须回来处理。**

#### 两个我自己写错又改掉的细节

1. **通知被自己覆盖**。第一版 `postNotification()` 先 `notify(来电内容)`
   再 `startForegroundCompat()`（守着内容），两者用同一个 notification id ——
   后写的把前者立刻覆盖。表现是"通知栏闪一下又变回『正在守着』"，
   用户反而错过。改成只调一次 `startForeground` 用来电内容。
2. **`setOnlyAlertOnce` 用反了**。它的语义是"同一个通知更新时不再响"。
   常驻状态该用它（别每分钟响一次），但**来电必须每次都响** ——
   否则第二次求助就变成静默的，而那正是这个功能存在的全部意义。
   写成 `.setOnlyAlertOnce(!isIncomingCall)`。

## 3D. 第二轮实测反馈：五个问题，两条根因

用户一次性报了五条。其中三条（位置、求助发不出、我没事崩回首页）其实是
**同一条链路上的相邻环节**，值得连起来看。

### 3D.1 日期格式：`T` vs 空格（位置上报失败的真因）

上一轮我给 `LocationReporter` 加了主动定位，以为修好了。**并没有。**
用户仍然拿不到位置。真正的根因在更下游：

服务端日志：
```
JSON parse error: Cannot deserialize value of type `java.time.LocalDateTime`
from String "2026-10-24T17:02:15":
Text '2026-10-24T17:02:15' could not be parsed at index 10
```

`index 10` 就是那个 `T`。服务端 `JacksonConfig` 把 `LocalDateTime` 全局钉成
`TimeUtil.PATTERN_DATETIME = "yyyy-MM-dd HH:mm:ss"`（**空格**分隔），
而客户端 `formatTimestamp` 发的是 `"yyyy-MM-dd'T'HH:mm:ss"`。

于是每一次 `PUT /me/location` 都是 400。查数据库确认：`latest_location` 表
**一条记录都没有** —— 这个功能从上线起就没成功过一次。

**为什么上一轮没发现**：上一轮验证的是"能不能拿到坐标"（定位 API 层面），
没有验证"发出去能不能被接受"。这是我自己造成的盲区：
修了上游就把下游当成通了。

**为什么这个坑特别容易踩**：`openapi.yaml` 里 `capturedAt` 的示例写的是
`2026-10-24T14:00:00`（ISO 格式），**与实现不一致**。
照抄文档写客户端必然踩。所以补了 `TimeFormatContractTest` 三条，
把"实现只接受空格、ISO 的 `T` 会被拒、带毫秒也会被拒"钉死。
将来有人想改成兼容 ISO，会先在测试里看到"有客户端依赖空格格式"。

### 3D.2 求助有时候发不出去：幂等键与"已结束"冲突

`AlertKeys` 只用 5 分钟时间桶。于是这个序列会失败：

1. 用户误触求助 → 生成键 K，报警建立；
2. 用户点「我没事」→ 报警变 `RESOLVED`；
3. 用户**真的**需要求助 → 仍在同一个 5 分钟桶里，算出的还是 K；
4. 服务端按 `(protecteeUid, idempotencyKey)` 唯一，判定为重复提交，
   返回**那条已结束的旧报警**。

界面上看就是"按了没反应"。这不是偶发，是**必然发生在误触之后的真实求助**上 ——
而那恰好是最危险的时刻。

修法：`AlertKeys.of(...)` 增加 `hasActiveAlert` 参数。手上还挂着未结束的报警
才复用键；没有则加后缀强制换新键（后缀用触发时刻毫秒，同一次点击重试仍命中同一条）。
`AlertKeysTest` 七条钉住这个区别。

### 3D.3 「我没事」崩回首页：`enqueue(null)` 必然 NPE

`AlertClient.resolve` 原样把 `callback` 透传给 `enqueue`：

```java
public void resolve(String alertId, ResultCallback<...> callback) {
    ApiClient.get(context).resolveAlert(alertId).enqueue(callback);
}
```

而 `dismissAlarm()` 调的是 `client.resolve(alertId, null)`。
Retrofit 在请求返回时会调 `callback.onResponse(...)` —— **在 null 上调用，
必然 NPE 崩溃**，进程重启，用户看到的就是"点击后异常返回首页"。

这个故障很有欺骗性：看起来像界面跳转 bug，实际是空指针。
而且它**只在报警真的存在时才触发**（`alertId != null` 才走进去），
所以手快的时候测不出来。

修法：`callback` 为 null 时用一个记日志的空实现。顺带
`resolve` 的失败也不再打扰用户 —— 面板已经收起了。

### 3D.4 监护人只在首页收到通知：服务在后台没活下来

上一轮加了常驻前台服务，但用户实测只有首页能收到。原因是我漏了两件事：

1. **`startForeground` 会抛异常，我没接。** 缺权限、类型不被某 ROM 支持、
   用户在系统设置里禁了通知，都会让它抛 `SecurityException` /
   `IllegalArgumentException`。不接的后果是**服务直接崩掉** ——
   而 Activity 里的前台轮询还活着，表现就是"只有首页能收到"。
   现在接住并退化为普通后台服务（没有前台态随时可能被杀，但好过立刻什么都不做）。
2. **Android 14 的 `specialUse` 在国产 ROM 上未必被认。** 小米/华为的后台管理
   会主动杀前台服务，且不受 `START_STICKY` 约束。加了 `AlarmManager`
   watchdog（15 分钟一次 `setAndAllowWhileIdle`）把服务重新拉起来，
   退出登录时取消（否则停了又会被拉回）。

另外修了一处**我自己引入的**崩溃风险：原来在 Android 10–13 分支上指定
`FOREGROUND_SERVICE_TYPE_DATA_SYNC`，但 manifest 声明的是 `specialUse`
且 `FOREGROUND_SERVICE_DATA_SYNC` 权限已被移除 ——
"声明与实现不一致"会被系统拒绝。现在 Android 13 及以下不指定类型。

还有个设计问题：服务与 Activity 前台轮询会**同时**发现同一个来电，
用户看到"通知栏响一次 + 页面弹一次"。加了进程级去重（`claimAlert`），
谁先发现谁提醒。去重记录带**时间戳**而不是只记 id —— 因为清理只在服务里做，
服务一旦被杀（正是它最容易被杀的时候），记录永远不清理，
**下一次真的来电**会被误判成"提醒过"而彻底静默。10 分钟自动失效。

### 3D.5 一句话总结这五条

> 一个功能"看起来实现了"和"端到端真的能用"之间，隔着：格式契约、
> 边界状态（已结束的报警）、空值路径、以及后台存活。

前三条都能被单测抓住（现在也被抓住了），第四条只能真机验证。

## 3E. 监护人应当看到受护人的位置

需求原话：「在监护人收到的紧急求助时，应该附带展示受护人发来的位置信息。」

### 3E.1 根因：监护人端从来就没有报警接口

查下来不是"位置没显示"，而是**监护人端连报警数据都拿不到**：
`client-guardian` 里没有 `AlertDtos`，`ApiService` 里没有任何 `alerts` 端点。
监护人收到的只有一条 `RealtimeDtos.SessionResponse` —— 它带 `id`、`targetUid`、
`status`，**不带位置，也不带 alertId**。所以哪怕服务端早就在报警里放了位置，
监护人这边也无从知晓。

服务端那边还有一个更隐蔽的问题：`AlertService.myAlerts(protecteeUid)` 只按
`protectee_uid = callerId` 查。监护人自己不是受护人，他调 `GET /alerts`
拿到的是**以他自己的 uid 作为受护人**的报警 —— 永远是空的。

值得注意的是同一个类里的 `get(callerId, alertId)` 早就正确允许生效监护人读取
（`bindingService.hasActiveGuardianship`）。也就是说**单个报警的权限判断是对的，
但"列出我能看的报警"这个入口漏了监护人这一类**。这类"详情对了、列表漏了"的
不一致很容易被忽略，因为手工测试时人往往会直接拿一个已知 alertId 去查详情。

### 3E.2 怎么把会话和报警连起来

会话响应没有 `alertId`。两者的关联在服务端是
`alert_delivery.session_id → realtime_session.id`。客户端能拿到的唯一线索是
报警详情里的 `deliveries` 数组（每个投递带着它为哪位监护人创建的 `sessionId`）。

所以客户端拉「投递给我的报警」列表，遍历所有报警的所有投递，找
`sessionId` 匹配的那一条。列表规模很小（一个监护人的报警记录），
比再加一个服务端接口划算。

这段查找抽成了 `AlertQuery`，因为有三处要用：来电对话框、常驻通知、会话页位置条。
三处各写一遍必然出现"某处忘了判空"或"某处只查第一条投递"的偏差，
而偏差的表现是"有时候有位置、有时候没有"——最难排查的一类问题。

### 3E.3 三处展示，一处不能少

| 位置 | 为什么必须有 |
| --- | --- |
| 来电对话框 | 监护人这一刻要判断的是"往哪儿去"；需要多点两下才看到，很多人就不看了 |
| 常驻通知 | 手机锁屏/没打开应用时唯一能看到的地方；用 `BigTextStyle` 让坐标不被截断 |
| 会话页位置条 | 点"打开"之后真正开始处理的地方，这里没有就前功尽弃 |

三处都遵守同一条规则：**没有位置时明确说"暂未收到受护人的位置"，而不是留白**。
留白会被理解成"还在加载"，而实际上可能永远等不到。

### 3E.4 几个刻意的取舍

- **新鲜度必须说出来。** 位置是受护人平时每 10 秒上报一次的缓存，报警时读的是
  "最近一条"。它可能是 3 秒前的，也可能是几分钟前的（受护人刚进电梯、
  或者一直没拿到定位）。两者对"人现在在哪"的价值完全不同，
  不说清楚会让监护人按一个过期坐标去找人。用服务端算好的 `ageSeconds`，
  不用客户端自己减 —— 两台设备时钟可能差好几分钟。
- **(0,0) 不可用。** 实践中它几乎总是"字段没填"的默认值，
  而不是真有人漂在几内亚湾。显示它会把监护人引到一个毫无意义的点。
- **位置失败不影响呼叫提醒。** 查不到报警/位置时照样弹窗、照样响铃 ——
  位置是增强，呼叫才是主功能。
- **切换会话时先清空位置。** 否则上一通会话的位置会短暂留在下一条会话上，
  那是**错误的信息**，会把人指向另一个地点。

### 3E.5 一个测试抓出来的设计问题

`myAlerts` 第一版用 SQL 的 `ne(protecteeUid, callerId)` 来排除
"自己发起又投递给自己"的重复。写测试时 mock 的返回值让这个假设失效，
结果出现了重复条目 —— 但真正的问题不是测试写错了，而是**用 SQL 过滤去重这件事
本身不可靠**：它依赖"投递永远不指向本人"这个数据形状假设。

改成内存里按 id 去重（`LinkedHashMap.putIfAbsent`），结构上就不可能出现重复，
不依赖数据形状。这类"测试逼出来的改进"是写测试的额外收益。

## 3F. 报警的位置必须是"此刻"，不是缓存

用户在看到 §3E 的实现后指出：**「报警时应该实时获取并上传位置」**。
这个纠正很关键——我上一轮把重点放在"把位置展示出来"，
却默认了位置的来源是可信的。它不是。

### 3F.1 数据给的证据

查库：

| 字段 | 值 |
| --- | --- |
| `alert.created_at` | `17:53:11` |
| `alert.location_captured_at` | `17:45:32` |
| `latest_location.received_at` | `17:53:20` |

三行放在一起说明两件事：

1. **位置是 8 分钟前的。** 服务端创建报警时只读 `latest_location` 缓存行，
   而那行是 17:45 落下的 —— 用户在室内一直没拿到新定位。
2. **位置比报警还晚到。** `received_at`(17:53:20) 晚于报警创建(17:53:11)，
   因为客户端是"先 `reportOnce()` 把位置发出去，再发报警"，
   **两次独立请求**，报警先到、位置后到，于是报警里根本没有位置。

第 2 点尤其说明问题：`reportOnce()` 是 fire-and-forget，它不等待、不回调，
调用方无从在报警请求里带上坐标。我上一轮在它上面加主动定位、
又修了时间格式，都是在校正"缓存这条路上的质量"，
但根子上**位置根本不该走缓存这条路**。

### 3F.2 修法：位置随报警请求一起上去

- 服务端 `AlertCreateRequest` 增加可选 `location`（纬度、经度、精度、采集时刻）。
- 创建报警时**优先用请求带来的位置**，只在没带时才回落到缓存。
  缓存回落保留给"客户端确实拿不到定位"（没权限、室内无信号）——
  此时几分钟前的坐标仍是比没有强的参考。
- 请求带了位置时**顺手写回 `latest_location`**：报警这一刻的位置是全系统最可信的
  一次采样，没有理由丢弃。写回失败只记日志，不影响报警本身。
- 客户端改成"先取位置、拿到后再发报警"，位置由同一次请求带上去。

### 3F.3 客户端怎么"取一次实时位置"

`LocationReporter` 新增 `requestLocationForAlert(callback)`。原来的 `reportOnce()`
只能"把手上的位置报出去"，无法满足"先拿到、再带着发"。

行为分四档：

1. 手上有 **20 秒内**的位置 → 立刻回调，不额外耗电（步行 20 秒约 25 米，
   对"到哪儿去找他"完全够用）；
2. 否则主动请求一次定位，最多等 **12 秒**；
3. 超时/失败 → 回调手上**任何一个**位置，哪怕很旧；
4. 什么都没有 → 回调 null，**报警照发**。

12 秒而不是常规的 30 秒，是因为**报警不该为了坐标而迟到**：
用户按了求助之后每秒都在等，而一个有坐标但晚 30 秒的报警，
还不如先发出去让监护人立刻打电话过来问。

两个容易漏的细节：

- **必须保证恰好回调一次。** 多调一次会发两条报警（幂等键能救回来，但浪费），
  少调一次则报警永远发不出去——那是最坏的后果。超时和真实定位可能几乎同时到达，
  所以用 `synchronized` + 置 null 来保证。
- **`stop()` 时必须结清等待中的回调。** 否则界面已销毁、几秒后回调回来
  会去碰一个死掉的 Activity。这里主动回调一次，让报警流程立刻往前走。

### 3F.4 为什么这些地方值得较真

位置这条链路上每一处偏差，后果都不是"少显示一点信息"，而是
**把监护人指向错误的地点**。8 分钟前的坐标可能已经是几公里外了。
一个没有坐标的报警，监护人至少知道「不知道在哪，先打电话」；
一个有错误坐标的报警，会让人往错的方向赶。

所以宁可：宁可报警晚 12 秒，宁可位置为空并明确说"暂未收到"，
也不给一个看起来很精确、实际早已失效的坐标。

## 3G. 底线：绝不因为拿不到位置而不报警

用户在我做完实时定位之后立刻加了一条约束：**不能因为没拿到位置就一直等待而不报警。**

这个提醒说明上一轮的实现有隐患。检查下来确实有两处：

### 3G.1 两个等待者会互相覆盖（真 bug）

我上一轮为了"多个等待者共享一次定位尝试"，用**单个字段**存等待中的回调：

```java
if (pendingAlertCallback != null) {
    pendingAlertCallback = callback;   // 覆盖！
    return;
}
pendingAlertCallback = callback;
```

注释里我还写了"换掉只是让它也收到结果"——**这是错的**。被覆盖的那个回调
永远收不到结果，而调用方是在收到回调之后才发报警请求的，
于是**那条报警永远发不出去**。

触发条件恰恰是最紧急的时刻：用户连点求助、或者手动求助与端面碰撞判定几乎同时命中。
一个人着急的时候会连按——这个 bug 会精确地在那时发作。

改成集合（`alertWaiters` 列表），所有等待者共享一次定位尝试，
拿到结果（或超时）时**一次性全部回调**。

### 3G.2 双重保险：AlertClient 自己的看门狗

即使 `LocationReporter` 保证"恰好回调一次"，报警也不该依赖这个保证。
`AlertClient.send` 现在另有一个 15 秒看门狗：如果位置回调因为任何原因没来，
它就直接不带坐标把报警发出去。

用 `AtomicBoolean` 做"只发一次"的闸门：

```java
if (!sent.compareAndSet(false, true)) return;
```

正常路径下位置回调先到、把闸门关上，看门狗到点发现闸门已关就什么也不做。
不管哪条路径先到，**报警恰好发一次**：不会漏发，也不会发两条。

### 3G.3 为什么值得为这条写七个测试

`AlertLocationWaiters` 这个类小到看起来不值得单独存在，但它守着一条不能破的底线：
**任何一个登记过的报警，最终都必须收到一次结果。** 它有两个互相冲突的要求——
「多个等待者共享一次尝试」和「谁都不能被漏掉」——而这正是单字段实现出错的地方。

抽出纯类（不碰 `LocationManager`）才能单测，于是有了 `AlertLocationWaitersTest` 七条：

| 测试 | 守的是什么 |
| --- | --- |
| `everyWaiterReceivesResult` | 后登记的不许挤掉先登记的 |
| `nullLocationIsStillDelivered` | **拿不到位置也要回调 null**，不许静默丢弃 |
| `drainClearsWaiters` | 结清后不复用，避免把结果发给下一批 |
| `drainWithNoWaitersIsNoOp` | 空转安全 |
| `throwingWaiterDoesNotBlockOthers` | 一个调用方写错了，不牵连别人的报警 |
| `registerDuringCallbackGoesToFreshBatch` | 回调里重新登记（连点）不会被本次吞掉 |

其中第二条是这一条约束的直接翻译：静默丢弃 = "一直在等待而不报警"。

### 3G.4 一句话

> 位置是"尽力而为"的增强，报警是"必须送达"的底线。
> 任何时候这两者冲突，报警优先，没有例外。

## 3B. 一个自己造成的故障：Flyway V7 校验和不匹配

写在这里是因为**这个错误比它看起来严重**，而原因纯粹是操作失误。

### 3B.1 现象

服务端起不来，`flywayInitializer` 在启动链上直接失败：

```
Migration checksum mismatch for migration version 7
-> Applied to database : -812154681
-> Resolved locally    : 1533442862
```

### 3B.2 原因

`V7__alert_dispatch_location.sql` 是**本轮新建、尚未提交**的迁移。
它被应用进开发库之后，我又回头给文件**加了几段注释**（补充三处与既有文档的偏差说明）。
Flyway 的校验和是**整文件**的，加一行注释也会改掉它 —— 于是库里的记录
（`-812154681`）与磁盘上的文件（`1533442862`）对不上，启动被拦下。

### 3B.3 为什么敢直接对齐校验和

修之前先证明"这次编辑只动了注释、没动 DDL"。做法是把 `V1→V7` 完整重放进
临时库 `sullivan_v7check`，再与开发库逐项对比：

| 对比项 | 结果 |
|---|---|
| 表数量 | 开发库 26（含 `flyway_schema_history`），重放库 25，其余一一对应 |
| V7 六张表的**列**（名称/类型/可空/默认值/注释） | **完全一致**（各 80 列） |
| 六张表的**索引**（含列顺序） | **完全一致**（各 18 条） |
| CHECK 约束 | 约束名与表达式一致；仅字面量的字符集前缀不同（`_gbk` vs `_utf8mb4`），属建库连接字符集差异，非语义差异 |

另外确认 V7 全文只有 6 条 `CREATE TABLE IF NOT EXISTS`，**完全幂等**，
即使被重跑也不会破坏数据。有了这三条，"把库里的校验和改成文件的值"才是安全的，
不存在"掩盖了一次真实结构漂移"的风险。

### 3B.4 教训

> **迁移文件一旦被应用，就再也不许改。** 要改结构，加 V8。

这次只是注释，所以对齐校验和就够了。但如果当时改的是 DDL，正确的做法**不是**
repair，而是写一个新的 `V8__*.sql` 做增量修正 —— repair 会把"库里和文件不一样"
这件事本身抹掉，此后没人知道真实结构到底是什么。

顺带一条：`V7` 至今**未提交**，只存在于这台开发机上，所以才能这样处理。
一旦它进了主干、别的环境也跑过，修法就只剩"写 V8"这一条路。

| `PUT /me/alert-setting {false}` 后再报警 | `autoSessionState=SKIPPED`，但 `status=DISPATCHED`（通知照发，只是不打电话） |
| 报警刚 `SCHEDULED`（400ms 内）就关开关 | **被翻成 `SKIPPED`** —— 关闭动作对在途排期生效 |
| `POST /alerts/{id}/resolve` | 200，`status=RESOLVED`，`resolvedAt` 回填 |

**5 秒这件事是实测的，不是推的**：

```
auto_session_due_at     = 15:06:20.484
auto_session_started_at = 15:06:20.897     ← 差 413 ms
```

`realtime_session` 里那条记录的方向也确认了：`initiator = 受护人`、
`target = 监护人`、`session_type = BASIC`、`status = REQUESTED`。
`alert_delivery` 的 `session_id` 回填成同一个 ID，说明"投递"与"会话"对得上。

`protectee_alert_setting` 在**一行都没有**的情况下，`GET /me/alert-setting`
如实返回 `{"autoSessionEnabled":true,"delaySeconds":5}` —— "缺行即默认开启"成立。

### 4.3 端到端过程中发现的一个既有 bug（已修）

跑 E2E 时手工构造登录请求，漏了 `principalType` 字段，服务端返回的是
**500 而不是 400/401**：

```
POST /api/v1/auth/login {"loginName":"x","password":"..."}
→ 500 {"status":500,"error":"Internal Server Error"}
```

根因：`AuthService.login` 写的是 `switch (request.principalType())`。
Java 的 `switch` 选择器为 `null` 时**直接抛 NPE**，不会走 `default`。
所以这个纯粹的前端疏忽被报成了"服务器内部错误"。

为什么值得修：前端看到 500 会去查服务端日志、怀疑数据库、怀疑部署，
而真正原因是它自己少传了一个字段。**错误码的语义正确性是可诊断性的一部分。**

修了两处（纵深防御）：

1. `LoginRequest.principalType` 加 `@NotNull` → 正常路径得到 400；
2. `AuthService.login` 显式判空后抛 401 → 即使校验被绕过也不抛 NPE。

新增 `AuthServiceLoginTests` 2 例钉住（`missingPrincipalTypeIsUnauthorizedNotNpe`、
`unknownPrincipalTypeIsUnauthorized`）。服务端测试数因此从 124 → 126。

### 4.4 深度测距的真实数值（本轮新增）

权重到齐之后，用**真实的**两份官方 ONNX 跑通了完整链路：检测 640 → 框换算回
内容区归一化 → 换算到 **768** 深度图的像素 → 7×7 中位数。`bus.jpg` 结果：

| 目标 | 置信度 | 采样点 (x,y) | 距离 |
|---|---|---|---|
| bus | 0.925 | (385, 477) | **4.08 m** |
| person | 0.915 | (197, 588) | 3.61 m |
| person | 0.899 | (298, 565) | 3.89 m |
| person | 0.860 | (622, 573) | 3.21 m |
| person | 0.525 | (119, 587) | 3.58 m |

这几个数**物理上自洽**：bus 最大最远（4.08 m），四个行人在 3.2–3.9 m 之间，
且越靠画面下方的采样点读数越小（越近）—— 与透视关系一致。深度图的全局分布
也合理：`min=1.18`、`median=3.68`、`max=13.95` 米。

**但这并不等于"测距准确"**：`bus.jpg` 里没有卷尺实测的基准距离，
所以上表只能证明"链路通了、量纲是米、数值量级合理"，**不能证明绝对精度**。
真正的精度标定需要拿卷尺量一个已知距离的物体，见 §5 与 §6。

1. ~~深度权重仍然没有~~ —— **已补齐**。`yolo26n-depth.onnx`（19.81 MB）已下载到

    前台服务的通知在国产 ROM 上会不会被杀（小米/华为的后台管理尤其激进，

13. **登录失效的提示没有真机验证过**（§3A.3）。`AuthExpiryTest` 只能证明

    需要真的让令牌过期（改系统时间或等服务端 TTL），再拿两部手机扫一次：
    要看到「登录已失效」对话框、确认后回到登录页、重新登录后再扫能正常选人。
    **另外，`ApiClient.setLoginExpiredListener` 目前只有 `GuardianActivity` 订阅了**。
    这是刻意的取舍而不是遗漏：`ApiClient` 是进程级单例，而监听器**只有一个槽位**，
    多个页面同时订阅会互相覆盖，且 Activity 销毁顺序不可控 —— 那会变成一个新的、
    更难查的 bug。所以让"登录失效的提示"固定由主页承担：网络层负责**清会话**（全局、
    任何页面都生效），主页负责**告诉用户**（它本来就在返回栈的最底部）。
    用户停在绑定列表页时收到 401，会话已经被清掉，只是要等他退回主页才看到提示。
    这条链路同样没在真机上走过。

### 5.1 一个我现在就知道的局限：第二通电话不会等第一通

当前实现里，自动调度对**每位**监护人都发一轮，`dispatch_order` 只决定**顺序**，
不决定**间隔**。也就是说两位监护人时，两通会话请求会相隔约 1 秒内先后发出，
而不是"第一通没人接 → 过 30 秒再打第二通"。

这不是 bug，是**范围决定**：真正的"升级拨打"需要会话超时、无人接听判定、
"当前该轮到谁"的状态机，以及一个可配置的重拨策略 —— 那是完整的呼叫中心逻辑。
本轮的"依次"只做到**有序、可复盘**，没有做到**有节奏**。

如果用户认为这不够，下一步应当给 `alert_delivery` 加 `next_attempt_at`，
并把调度改成"只派发当前 `dispatch_order` 最小且未终结的那一条"。

      「登录已失效」对话框（而不是页面底部一行字），确认后回到登录页；
    - 重新登录后再扫一次 → 能正常弹出受护人选择列表，受护人端能登录成功；
    - 受护人端令牌失效后点「紧急求助」→ 必须看到/听到
      「登录已失效，报警没有发出」，而不是笼统的「求助发送失败」。
