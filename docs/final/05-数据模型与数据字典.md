# SullivanMINI 数据模型与数据字典

**文档版本:** v2.0  
**基线日期:** 2026-08-04  
**适用范围:** SullivanMINI `[MINI]`

## 1. 设计边界

项目使用一个 MySQL 8.0 数据库 `sullivan`。Java 应用负责业务表的统一迁移和写入；Python 只负责导航表。数据库不按服务拆 schema，也不使用跨库逻辑外键作为架构前提。

所有时间以 UTC 保存，应用连接设置 `time_zone = '+00:00'`。ID 使用应用生成的 26 位 Crockford ULID。关键状态更新必须带 `id + version + 当前 status` 条件，申请、报名、报警、审核和审计记录不得物理删除。

## 2. 表目录

| 领域 | 表 |
|---|---|
| identity | `user_account`、`user_profile`、`user_role`、`auth_refresh_token`、`guardian_binding`（含发起方 `requested_by`）、`location_authorization`、`latest_location`、`volunteer_availability`、`account_recovery`、`account_recovery_reminder` |
| navigation | `model_version`、`navigation_session`、`navigation_sample_event` |
| welfare | `organization`、`organization_review`、`welfare_service`、`service_quota`、`service_application`、`volunteer_activity`（含报名窗口与经纬度）、`activity_enrollment`、`volunteer_application`、`alert`、`alert_delivery`、`alert_broadcast`、`alert_broadcast_response`、`notification`、`notification_delivery_attempt`、`outbox_message` |
| realtime | `realtime_session` |
| admin | `admin_account`、`admin_role`、`admin_permission`、`admin_role_permission`、`admin_account_role`、`admin_registration_code`、`admin_audit_log` |

所有表均位于 `sullivan`。表名按领域命名，领域包是代码组织方式，不代表独立服务或独立数据库。

## 3. 所有权与访问

| 数据 | 权威写入方 | Python 权限 |
|---|---|---|
| 账号、绑定、位置、公益、报警、通知、管理员 | Java | 不访问 |
| `model_version`、`navigation_session`、`navigation_sample_event` | Python（导航接口） | 仅导航表 |

Python 写导航会话前必须验证 JWT 的 `PROTECTEE` 角色，并确认 `navigation_session.protectee_uid` 等于令牌主体。Java 读取导航摘要时按普通行级权限处理，不读取原始帧。

同库表之间可以使用物理外键。关联自然人、机构和管理员时仍必须在应用层校验角色、账号状态和数据范围，物理外键不等于授权。

## 4. 关键业务规则

- `guardian_binding` 的 `PENDING/ACTIVE` 有效关系组合唯一；每位受护人最多一条 `ACTIVE + is_primary`。
- 每条绑定记录发起方 `requested_by`（监护人或受护人账号 ID）：监护人创建受护人时写入 `permanent_flag=true` 的 `ACTIVE + is_primary` 绑定；该绑定不能通过业务接口终止。
- 其它绑定只能通过 `PENDING -> ACTIVE` 确认流程建立：发起方为监护人或受护人，由接收方（非发起方）确认。
- `user_role` 是自然人角色关系表，监护人兼任志愿者时新增 `VOLUNTEER` 关系，不复制账号。
- `ACTIVE` 绑定才授权位置查看、代申请、报警接收和实时会话；撤销后立即失效。
- `volunteer_activity` 报名窗口必须满足 `registration_starts_at <= registration_ends_at <= starts_at`；`location_lng`/`location_lat` 与 `location_text` 同空或同非空（高德经纬度，供实时位置匹配）。
- `volunteer_application` 同一申请人最多一条 `PENDING`（`effective_key` 唯一约束）；审核通过事务内追加 `VOLUNTEER` 角色。
- `realtime_session` 创建与消息中继都必须存在双方 `ACTIVE` 绑定；`session_type` 仅 `BASIC`（`VOICE`/`CAMERA`/`LOCATION` 为 `[FULL]` 扩展）。
- 服务申请名额由 `APPROVED + COMPLETED` 占用，活动名额由 `APPROVED` 报名占用，均使用条件更新或行锁。
- 报警先写入 `alert`，再由同库 `outbox_message` 触发路由和通知重试。有生效监护人时只通知全部监护人；没有时才匹配志愿者。
- `notification` 使用接收主体类型和 ID 双条件；已读与报警确认是不同状态。
- `admin_registration_code.code_hash` 只保存注册码哈希；注册码核销使用 `status + version` 条件更新，只能使用一次。
- 导航采样只保存序号、摘要、尺寸、模型版本、风险、耗时和最小化结果 JSON，不保存原始帧、TTS 音频或逐帧视频。

## 5. 状态与约束

状态值以 `02-术语枚举与状态机.md` 为准，数据库用大写字符串和 `CHECK` 约束。禁止 Controller 或 Python 直接覆盖 status；所有状态命令在 Java 领域服务或 Python 导航会话服务中完成版本校验。

关键唯一约束包括：登录名、刷新令牌哈希、有效绑定关系、报警幂等键、有效申请/报名组合、单报警接收主体和通知去重键。

## 6. Redis 与对象存储

Redis 保存最新位置缓存、志愿者 Geo 索引、可服务状态、幂等键、短时权限缓存和令牌吊销标记。MySQL `latest_location` 是业务权威记录，Redis 缺失时监护人查询可回落 MySQL；附近匹配只接受 Redis 中的新鲜位置。

MinIO 保存机构材料、头像和公益项目图片，不保存导航原始帧和导航 TTS 音频。

## 7. 迁移规则

统一迁移目录为 `db/migration/`，由 Java Flyway 执行：

```text
db/migration/
  V1__registration_identity.sql
  V2__add_xxx.sql
```

当前 Java 身份与注册能力使用 `V1__registration_identity.sql`、找回联系方式使用 `V2__account_recovery.sql`。截至 2026-08-17，新增 `V3__welfare_activity_volunteer_realtime.sql`（绑定发起方 `requested_by`、活动报名窗口与经纬度、志愿者兼任申请、实时会话）。旧四个领域迁移目录仍待清理或合并；上线后只追加版本，不直接修改已执行迁移。

## 8. 保留与安全

| 数据 | 策略 |
|---|---|
| 最新位置 | 覆盖保存；授权撤销后按策略删除 |
| 导航采样 | 正常 30 天，故障样本最长 90 天 |
| 刷新令牌、通知投递、outbox | 按失效时间和完成状态清理 |
| 申请、报名、报警、审核、审计 | 至少 5 年，不物理删除 |

禁止在当前模型加入金额、币种、订单、支付、钱包、聊天、视频或 AI 客服字段。未来商业能力必须建立独立领域和独立迁移。
