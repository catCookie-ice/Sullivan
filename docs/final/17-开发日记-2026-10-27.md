## 1. 受护人代建即 500：`ck_guardian_binding_confirmed` 被违反

### 1.1 现象与定性

监护人代建受护人（`GuardianRegistrationController.registerProtectee` →
`RegistrationService.registerProtectee:84`）插入 `guardian_binding` 时，MySQL 抛出
`SQLException: Check constraint 'ck_guardian_binding_confirmed' is violated`（错误码 3819）。
整条事务回滚——受护人账号、资料、角色三张表一并回滚，接口表现为 500。

**定性：这是约束上线时漏核的一条写入路径，不是脏数据。** 同一个请求、合法入参、必现。

### 1.2 根因

v1.0.0 重构后的基线（`V1__baseline.sql:132`）：

```sql
CONSTRAINT ck_guardian_binding_confirmed CHECK (status <> 'ACTIVE' OR confirmed_at IS NOT NULL)
```

`registerProtectee` 把绑定直接插成 `ACTIVE`（该接口语义：监护人代受护人注册账号并当场建绑定），
却从未 `setConfirmedAt`。MyBatis-Plus 的 insert 只拼非空字段——报错 SQL 的列清单
（`id, status, guardian_uid, protectee_uid, is_primary, permanent_flag, requested_by`）里
根本没有 `confirmed_at`，于是落库为 NULL，撞上约束。

`guardian_binding` 共三条写入/转 ACTIVE 路径：`BindingService` 创建（PENDING，无需确认时间）、
`BindingService.confirm` 转 ACTIVE（**有** `.set(ConfirmedAt, now)`）、`registerProtectee` 直插
ACTIVE（**漏**）。重构当天「每条约束核对全部写入路径」的方法论在前两条上执行了，第三条漏网——
单元测试 mock 掉了 MyBatis-Plus 的字段拼装，天然看不见列清单，测试全绿但真库必炸，
与 `17-开发日记-2026-10-26-语音视频会话与语音留言.md` §10 记录的四个缺陷同一类成因。

### 1.3 修复

- `RegistrationService.registerProtectee` 补 `binding.setConfirmedAt(LocalDateTime.now())`：
  代建即当场确认。**不能改成插 PENDING**——`is_primary = true` 要求 `status = 'ACTIVE'`
  （`ck_guardian_binding_primary`），那样只是换成另一条约束报错；且既有测试本就断言
  代建产出 `ACTIVE` + 主监护人的绑定。
- 口径与 `BindingService.confirm` 对齐：**进入 ACTIVE 必写 `confirmed_at`**，全项目只此一条规则。
- `RegistrationServiceTests.guardianCreatesProtecteeWithPermanentActiveBinding`
  补断言 `getConfirmedAt()` 非空，把约束钉进测试。

### 1.4 环境注记（本机跑服务端单测的两个前置）

1. `JAVA_HOME` 默认指向 jdk-17，编译报「不支持发行版本 21」；本机装有
   `C:\Program Files\Java\jdk-21.0.10`，先切再跑。
2. Mockito 的 inline mock maker 在 JDK 21 下自挂载 agent 失败（`Could not self-attach`），
   surefire 需加
   `-DargLine=-Djdk.attach.allowAttachSelf=true -Xshare:off`。

## 2. 活动创建：时间与人数的前后端双向校验

### 2.1 规则口径（需求原文 → 实现）

| 规则 | 实现 |
|---|---|
| 结束时间不能早于开始时间 | 两组都管：活动结束 ≥ 活动开始，报名结束 ≥ 报名开始。「不能早于」按字面执行，**允许相等**（原来服务端要求严格晚于，本次放开为零时长边界） |
| 报名截止不能晚于活动开始 | 原有保留 |
| 报名开始不能晚于活动开始 | **新增**（原来只约束报名结束） |
| 人数必须是 > 0 的数字 | 后端原有 `@Min(1)` + 服务端兜底；前端补「清空后为 null」的拦截 |
| 12:00 规则 | 两个「开始时间」（活动开始、报名开始**都算**）不得早于：12:00 前创建 → 今天零点；12:00 及之后 → 明天零点。正好 12:00 整按「之后」处理（取更严格一侧，边界不留歧义） |
| 活动开始晚于当前时间 | 原有保留（60 秒时钟余量）。中午前它比日期下限更严；中午后「当天晚些时候」由日期下限拦下 |

### 2.2 服务端（唯一裁决方）

- `TimeUtil.earliestAllowedStart(now)`：12:00 规则的纯函数，前后端口径的唯一权威定义
  （前端那份是按它逐字镜像的副本，注释里互相指认）。
- `VolunteerActivityService.create` 每条规则独立报错、文案指名道姓
  （原来是三条并一条的「报名窗口必须满足：报名开始 <= 报名结束 <= 活动开始」，机构看不出到底哪项错）：
  人数 → 活动开始下限 → 报名开始下限 → 活动开始晚于当前 → 活动结束 ≥ 开始 →
  报名开始 ≤ 活动开始 → 报名结束 ≥ 报名开始 → 报名截止 ≤ 活动开始 → 经纬度。
- 越下限的报错带具体时刻，如「活动开始时间不能早于明天（2026-10-28 00:00:00）」。

### 2.3 前端 org-web（`ActivityCreate.vue`）

- `submit()` 按同口径预检，文案与后端一致；请求发出去之前就拦住，后端仍是裁决方。
- 活动开始、报名开始两个选择器加 `:disabled-date`，越界的**整天**直接不可选
  （时刻级越界仍由提交校验兜底）；下限随创建时刻跨过 12:00 动态变化。
- `maxVolunteers` 类型放宽为 `number | null`（`el-input-number` 清空写 null 是运行时事实，
  类型如实反映）。守卫后**提取局部变量**再带进 payload——对 reactive 对象整体展开
  不会保留属性的类型收窄，直接 `...form` 会把 `number | null` 塞进
  `ActivityCreateRequest` 触发 TS2322。

### 2.4 验证

- 服务端：`TimeUtilTests` 10 例（+3：中午前/中午后与整点边界、跨月跨年）、
  `VolunteerActivityServiceTests` 14 例（+6：两条「结束<开始」、两条开始时间越 12:00 下限、
  人数 0/null、结束=开始允许落库）、`RegistrationServiceTests` 4 例，全绿。
  12:00 越界用例用 `TimeUtil.earliestAllowedStart(now).minusSeconds(1)` 构造——
  恒为前一天 23:59:59，无论何时跑测试都必然越界，用例与运行时刻无关。
- org-web：`vue-tsc --noEmit` 与 `npm run build` 里的 `vue-tsc -b` 均通过。
  `vite build` 打包一步在本机沙箱内跑不起来（esbuild 服务子进程 `spawn EPERM`，
  属运行环境的进程边界，任何工程都一样，与本次改动无关）；打包验证需在沙箱外的
  终端自行执行 `npm run build`。

### 2.5 注记与边界

- 「结束时间等于开始时间」从拒绝改为允许，是按需求字面执行的**显式决策**，测试钉住；
  若日后想要严格晚于，改两处比较符即可，文案已按「不能早于」措辞。
- 本次规则只作用于**创建**入口（`POST /activities`）；志愿者报名（enrollment）的时间判断
  （是否在报名窗口内）是另一条路径，未动。

## 3. 志愿活动报名与活动群聊（V2）

### 3.1 功能面（需求 → 交付）

| 需求 | 交付 |
|---|---|
| 报名成功的志愿者进入群聊 | 报名落库后 `ActivityGroupService.joinActivityGroup` 自动入群（幂等） |
| 群管理员 = 机构账户 | 群行记 `organization_id`，机构权限全部由它裁决；机构**不是成员行**，不会出现在成员列表里 |
| 活动结束群聊自动关闭 | 双闸门：`@Scheduled` 每分钟扫 `ends_at` 关群 + 发送时实时校验 `ends_at > now()`（不等定时器） |
| 群内仅文字消息 | 内容 `@NotBlank @Size(2000)`，去首尾空白；无附件/语音通道 |
| 机构可开「需审核」 | `volunteer_activity.review_required`；开启 → 报名进 PENDING，机构批准才占名额入群 |
| 名额只统计已批准 | `approved_count` 只在 APPROVED 时条件更新 `+1`（`approved_count < max_volunteers`），满员 409 |
| 机构可看总报名人数 | `GET /api/v1/org/activities/{id}/enrollments` 返回 `summary{total,pending,approved,rejected,cancelled}` |
| 违禁词拦截 | `banned_word` 表，发送时包含匹配 → 400「消息包含违禁词「xx」，已被拦截」，不落库 |
| 举报 | 志愿者举报 NORMAL 消息 → 机构受理（撤回消息，RESOLVED）或驳回（DISMISSED） |

### 3.2 数据模型（V2 迁移，schema.sql 已镜像）

- `volunteer_activity` 加列 `review_required BOOLEAN NOT NULL DEFAULT FALSE`；
- 新表 `activity_group`（一活动一群，`uq_activity_group_activity` 唯一键兜底；状态 OPEN/CLOSED）、
  `activity_group_member`（volunteer_uid+group 唯一；软退出 `REMOVED`，生成列
  `active_member_key` 只对 ACTIVE 行唯一——同一人退出后可再次入群）、
  `activity_group_message`（content ≤2000；NORMAL/WITHDRAWN，撤回者与时刻留痕）、
  `activity_group_report`（同一消息同举报人**同时至多一条待处理**：生成列
  `pending_report_key`，状态非 PENDING 时为 NULL 绕开唯一键）、`banned_word`（词唯一，8 个种子词）。
- 报名表 `activity_enrollment`：uid+activity 唯一键挡重复，但唯一键只对
  PENDING/APPROVED 生效（生成列 `effective_enrollment_key`）——被拒/已撤后允许再次报名。

### 3.3 关键设计决策

1. **群聊走 REST + 前端轮询，不上 WebSocket。** 现有 1:1 会话的 `ConnectionPool`
   按登录会话建在内存里，多实例/重启即失效；群聊是持久化业务（历史可回看），本就以
   数据库为唯一事实源，轮询（5s）+ 游标翻页足够 MINI 规模。扩展点已登记（§3.6）。
2. **消息游标用 `created_at` 不用 id。** `IdGenerator.next()` 是随机 UUID 截断，
   无时间序，按 id 翻页会错序；游标取上一页最早一条的 `created_at`，`created_at < before`
   查 `limit+1` 条判定 `hasMore`，返回前反转为升序。
3. **审批的并发与回滚语义。** 批准 = 先条件更新 `PENDING→APPROVED`（抢到行的人才继续），
   再 `occupyQuota` 条件更新占名额，最后入群；名额已满抛 409 时整个事务回滚，
   报名行退回 PENDING，机构可改判他人。报名（免审）路径同序：插入 APPROVED → 占名额 →
   入群，满员 409 回滚后志愿者看到「名额已满」，无脏数据。
4. **机构撤回任意成员消息；志愿者不能删自己的。** 群内治理权收敛在机构（管理员），
   志愿者只有举报。撤回是条件更新 `NORMAL→WITHDRAWN`，抢不到行（已被撤）返回 409。
5. **状态机单点。** 活动状态推进只经 `scheduledSweep()`：
   `RECRUITING→(starts_at≤now)→IN_PROGRESS→(ends_at≤now)→ENDED`，同一次扫描顺带
   关闭所属 OPEN 群（关群原因「活动已结束，群聊自动封闭」）。发送路径的实时校验
   `requireGroupOpen` 是第二道闸，防「定时器还没跑到」的窗口期。

## 4. 站内通知（导航栏铃铛）与消息撤回时限

### 4.1 通知面（V3 `user_notification`，schema.sql 已镜像）

| 事件 | 接收者 | 标题 | 点击跳转 |
|---|---|---|---|
| 志愿者提交需审核报名 | 机构 | 新的报名待审核 | `/enrollments`（报名审核页） |
| 机构批准报名 | 志愿者 | 报名审核通过 | `/volunteer/group-chat?activityId=…`（直达群聊） |
| 机构拒绝报名 | 志愿者 | 报名未通过（含原因） | `/volunteer/enrollments` |
| 机构撤回群消息 | 群内全部志愿者 | 机构撤回了一条消息 | `/volunteer/group-chat?activityId=…` |

- 接收者是多态引用（`USER`=user_account.id / `ORGANIZATION`=organization.id），与群消息
  sender 同款：不建外键，查询一律带 `recipient_type` 防跨类型撞 uid。
- **写侧尽力而为**：`NotificationService.notify` 内部捕获异常只记日志——通知是锦上添花，
  不能让它的失败把报名/审核/撤回主事务拖垮；反过来「已通过」通知放在占名额/入群都成功
  **之后**发，万一事务回滚不会留下假通知。
- 读侧四个端点：`GET /notifications/unread-count`（角标）、`GET /notifications?before&limit`
  （游标分页，最新在前）、`POST /{id}/read`（幂等）、`POST /read-all`。管理员当前没有
  通知来源，接口对其返回空——不报错，为日后管理员侧通知留同一条通道。

### 4.2 消息撤回：时限 + 自撤 + 墓碑

- **时限**：`app.activity-group.message-withdraw-window-minutes`（默认 30 分钟），
  机构撤回与志愿者自撤**共用一条规则**，超窗 409「已超过可撤回时间」。没有时限的撤回
  等于可以悄悄改写群聊历史。显式取舍：处理举报时的「受理并撤回」同样受时限约束——
  超窗的被举报消息撤不了，机构只能驳回；时限优先于治理。
- **自撤**：`POST /api/v1/group-messages/{id}/withdraw`（志愿者），只能撤自己发的
  VOLUNTEER 消息；不发通知（自己操作的，群成员刷新即见）。
- **墓碑**：`listMessages` 不再过滤 WITHDRAWN，改为下发 `withdrawn=true`、`content=""`
  的墓碑行（原文永不下发——撤回的意义就是没人再看得到内容）。前端渲染成
  「机构撤回了一条消息 / 「张三」撤回了一条消息」，聊天里凭空消失一条比墓碑更让人困惑。

### 4.3 前端（org-web / user-web）

- 共享组件 `@shared/notifications/NotificationBell.vue`：角标未读数（上限 99，之后 99+，
  有未读时铃铛点亮变色）；hover 弹最近 8 条简述（标题+摘要+时间，点击直达）；点铃铛开
  **抽屉**看全部，可滚动「加载更早」、一键全部已读。角标 30 秒轮询（通知不是聊天）。
  API 面由宿主端注入（各自的 request 实例），组件不感知角色。
- `AppNav` 新增右上角 `actions` 插槽，两端布局各放一枚铃铛（宽窄屏都渲染）。
- 群聊页（两端）：墓碑样式；机构撤回按钮加时限内才显示的前端预判（后端仍是裁决方，

## 5. 举报治理体系（V4）：统一举报 + 预设处罚 + 申诉 + 恶意举报阈值升级

### 5.1 功能面（需求 → 交付）

| 需求 | 交付 |
| --- | --- |
| 可举报活动/机构/群聊/个人，路由给新的管理员角色 | 统一 `abuse_report` 表（四类目标列互斥 CHECK），新权限码 **`ABUSE_REVIEW`**（举报治理管理员）；权限码与出厂角色 **`REPORT_ADMIN`（举报治理管理员，固定授 ABUSE_REVIEW）** 都进 `AdminSeedInitializer` 启动幂等种子——SUPER_ADMIN 的「全量」随之自动带上 ABUSE_REVIEW；角色权限页/注册码页的角色下拉直接可见 REPORT_ADMIN，也可再建自定义角色挂同码。不引入新 principalType |
| 处罚不能随意设置，只能从预设选 | `preset_penalty` 字典；处置接口只收 `presetId` 且校验 **ACTIVE + 类别匹配**，自由裁量只有「驳回」 |
| 管理员可申请新预设（不能直接加） | 申请新预设进 `PENDING`，须**另一名**管理员批准（自批 403），批准才 `ACTIVE` |
| 活动举报：下架 / 下架并封禁机构 3 天 | `DELIST`（活动 CANCELLED + 封群）/ `DELIST_AND_BAN_ORG`（+ 机构封禁 N 天） |
| 机构封禁自动级联 | `BAN_ORG`：机构封禁限制 + **下架其全部未结束活动 + 逐个封闭群聊** + 发布活动入口守卫拦截（`AbuseGuardService.assertOrgCanPublish`） |
| 个人封禁踢出未结束活动 | `BAN_USER`：账户封禁限制 + **连带禁用账户**（`ENABLED→DISABLED`）+ 踢出全部未结束活动（APPROVED 释放名额并退群、PENDING 一并取消；已结束的不动——历史不是惩罚对象） |
| 查看目标历史被举报与违规记录 | `GET /admin/abuse/targets/history`：目标档案抽屉（举报列表含举报人 + 处罚列表） |

| 反向举报（匿名） | 举报被 `DISMISSED` 后，被举报的个人可反诉：系统以被举报人名义生成 `REPORT_ABUSE` 举报（目标=原举报人）；「针对我的举报」接口对举报人**永远匿名**，且**只返回被驳回的举报**（它是反诉入口，不是知情清单——待处理的与已处罚的不下发，处置意见也不下发），反诉入口只看得到 `counterReportable` 布尔 |
| 驳回占大多数 → 锁举报 → 禁活动 → 封账户 | `evaluateReporter`：近 30 天窗口内按驳回数阶梯升级（默认 10/15/20、驳回占比 ≥0.6 才锁举报；全部可配 `abuse.*`）；驳回与反诉两个时点触发；幂等、只升不降；禁活动/封账户档位自动踢出未结束活动并通知当事人 |

### 5.2 数据模型（V4 `V4__abuse_governance.sql`，schema.sql 已镜像）

五张表按外键依赖排序：`preset_penalty → abuse_report → penalty → appeal → abuse_restriction`。
约定沿用：CHAR(26) ascii 主键、DATETIME(3)、`version`、`deleted_at`、命名约束。
`user_notification` 的类型 CHECK 因 MySQL 不能原地改 CHECK 而 DROP 后 ADD，扩了
`PENALTY_APPLIED / APPEAL_DECIDED / REPORT_DISMISSED` 三个类型（处罚与申诉结果通知被处罚方，
举报驳回通知举报人，链接按接收端拼：志愿者 `/volunteer/penalties`、机构 `/penalties`）。
`abuse_restriction` 的 `expires_at` 空即永久；守卫查询统一带「未过期」条件，到期不查即可，
无需定时任务。

### 5.3 关键设计决策

- **处罚权分立**：预设「申请-审批」由不同管理员完成（`approved_by != created_by` 服务端校验），
  任何单人无法既造刑罚又用刑罚；处置时预设必须在 `ACTIVE` 且类别与举报对象匹配。
- **守卫与执行分离**：`AbuseGuardService` 只读限制表、被活动发布/报名/举报入口零环路引用；
  `AbuseService` 负责处罚与阈值升级的写路径——两者不会互相依赖成环。
- **踢人复用报名链路**：`ActivityEnrollmentService.kickFromAllActiveActivities` 走既有的
  条件转移 + 释放名额 + 退群代码，不另写一套平行状态机。
- **匿名边界**：被举报方所有可见接口（针对我的举报、我的处罚）都不含举报人标识；
  反向举报表单只有理由输入框，无从得知对方是谁。管理员档案页可见举报人（治理需要）。

## 6. admin-web 页面按权限显隐 + 权限申请（零门槛发起）

### 6.1 页面守卫：没有权限就看不到、也进不去

菜单此前已按权限显隐，但手输 URL 仍能直达页面（数据接口会 403，页面本身照渲染）。
路由表给每个页面补 `meta.permission`（与后端各 Admin*Controller 守卫码同源）：
`/users→USER_MANAGE`、`/organizations→ORG_MANAGE`、`/codes→ADMIN_REGISTRATION_CODE_CREATE`、
`/volunteer-review→VOLUNTEER_REVIEW`、`/abuse→ABUSE_REVIEW`、`/admins|/roles→ADMIN_MANAGE`；
聚合页 `/stats` 用 `permissionAny`（USER_MANAGE / ORG_MANAGE / VOLUNTEER_REVIEW 任一，
因为页面聚合调这三个接口）。`beforeEach` 守卫缺权一律重定向到 **`/permission-requests`**。
注册码与统计两个菜单项此前无条件展示，现与守卫同口径收口。

### 6.2 权限申请（V5 `admin_permission_request`，schema.sql 已镜像）

**发起不需要任何权限，只要是管理员**（principalType=ADMIN 即可）——这是刻意设计：
「没有权限就看不到页面」之后，必须给缺权限的管理员留一条不依赖任何权限的正式申请通道，
否则他们连「该找谁、要什么」都表达不出来。

- **申请语义是「我需要这项权限」**：表单只有**权限 + 理由**，不涉及角色——
  需要权限不等于要创建一个新角色，申请人全程不接触角色概念。
- 防噪音：权限须在字典中；同一申请人对同一权限同时只允许一条待审；
  自己已拥有该权限的直接 409。
- 审批须 **ADMIN_GOVERN**（谁能批权限，谁就得先有管权限的权限）；**自批拒绝**——
  与预设处罚审批同一条分立原则。
- 批准即给申请人开通：RBAC 的权限始终经角色解析，因此落地时系统把申请人加入
  **承载角色**（按权限自动生成 `PERM_<权限码>`，显示名即权限名；不存在则创建，
  角色与授权关系均按唯一键旧行复用置回 ACTIVE，不盲插）——
  这是纯机械步骤，不是申请人在「建角色」。驳回仅记录。
- ⚠️ 发布前改写了 V5（从「带 role_code/role_name」改成「只填权限与理由」）。
  若某个开发库**已经应用过旧版 V5**，直接重启会 Flyway checksum mismatch 起不来；
  开发库处置（无生产数据，直接重建该表）：`DROP TABLE IF EXISTS admin_permission_request;`
  + `DELETE FROM flyway_schema_history WHERE version='5';` 再重启，由新版 V5 重建。
  连带教训：改表结构时**实体字段必须同步删**——`AdminPermissionRequest.roleCode/roleName`
  漏删导致运行期 `Unknown column 'role_code'`；而全量单测全绿，因为 mapper 都被 mock，
  SELECT 列清单（按实体 TableInfo 生成）在 mock 测试里不可见。
- 端点：`POST|GET(mine|catalog) /admin/permission-requests`（任意管理员）+
  `GET|POST/{id}/decision`（ADMIN_GOVERN）；权限字典 `/catalog` 任意管理员可读
  （码表不是秘密，审批权才是闸门）。

### 6.3 前端（admin-web）

新增「权限申请」页（菜单无条件展示，唯一零门槛页面）：「我的申请」tab（发起对话框
只有**权限下拉 + 理由**两个输入；结果与审批意见可见）+「待我审批」tab（仅

## 7. 处罚矩阵扩展：暂时下架/封禁 + 群聊成为处罚对象（V6）

### 7.1 预设动作矩阵重排

- **单纯下架不再带封禁天数**：`DELIST` 定位为纯永久动作（活动 CANCELLED + 群聊解散），
  前端隐藏天数字段、后端 `validatePresetShape` 对带天数直接 400。
- **新增 `TEMP_DELIST` 暂时下架**：活动 SUSPENDED + 群聊**同时长**暂时封禁，到期自动恢复。
- **群聊成为处罚对象**（预设类别新增 `GROUP`，举报对象本就支持群聊，此前无处方可施）：
  `BAN_GROUP` 暂时封禁 N 天 / `PERM_CLOSE_GROUP_DELIST_ACTIVITY` 永久封群并下架活动 /
  `PERM_CLOSE_GROUP_BAN_ORG` 永久封群并附带机构处罚（机构侧时长取预设天数，空=永久）。
- **机构封禁分级联动**：永久 → 活动永久下架 + 群解散（原行为）；非永久 → 活动与群聊
  「至少暂时下架/封禁」**同时长**，到期恢复——不再一刀切永久下架。
- `DELIST_AND_BAN_ORG` 为 V4 存量动作保留可执行，但不再接受新建预设。

### 7.2 状态机与到期恢复（挂在 penalty 上）

活动与群聊各新增 `SUSPENDED` 状态（群聊带 `suspended_until` 列）。「暂时」的到期时刻
**不另设字段**，直接以 `penalty.expires_at` 为准：每分钟扫描（`AbuseService.
sweepExpiredPenalties`，`@Scheduled` + 暴露普通方法供单测）把到期的暂时处罚
恢复（活动按**自然时间轴**取回 RECRUITING/IN_PROGRESS/ENDED；群聊恢复 OPEN，
活动已结束则直接 CLOSED）并把处罚行翻 `EXPIRED`——扩展点 AB-01 的到期归档
就此部分落地；账户/机构封禁类限制仍由 AbuseGuardService 读时判定。

### 7.3 前端

- admin-web 预设表单：动作按作用对象联动（ACTION_MATRIX 与后端矩阵同源），
  天数字段仅对可带天数的动作出现（必填/留空=永久两种提示）。
- user-web 活动卡「已下架」、群聊「暂时封禁」标签与输入框提示；org-web
  「已下架（处罚中）」、群聊同口径。三端 `vue-tsc` 通过。

### 7.4 验证与边界

- `AbuseServiceTests` 16→24：新增暂时下架挂群、群聊处罚+通知机构、永久封群连带下架、
  机构暂时/永久两种联动、到期恢复翻 EXPIRED、DELIST 带天数 400、TEMP_DELIST 缺天数 400、
  GROUP 预设可建。全量 **298 例通过**（+8）。
- 边界：暂时下架期间活动不出现在公开列表、不可报名（状态机天然挡住）；已产生的报名与
  群成员关系保留，恢复后无缝继续；`DELIST_AND_BAN_ORG` 存量数据不受 V6 CHECK 收紧影响
  （动作枚举保留）；恢复扫描与生命周期扫描相互独立，重启可重入（条件更新）。

## 8. 处罚矩阵扩展二：禁止发布活动 + 附带时长独立（V7）

### 8.1 新动作

- **机构：`BAN_PUBLISH` 禁止发布活动**——比机构封禁轻一档：只挡新建/重新发布
  （`assertOrgCanPublish` 增查 `PUBLISH_BANNED` 限制），不触动既有活动与群聊；
  时长可设（空=永久），到期读时失效。
- **活动：`DELIST_AND_BAN_PUBLISH` 下架活动并禁止发布活动**——两个时长**分别设置**：
  主时长=下架时长（空=永久下架并解散群聊；有时长=暂时下架挂群聊，到期扫描恢复）；
  附带时长=禁止发布时长（**留空 = 与主处罚时长相同**）。

### 8.2 附带时长独立设置（通用规则）

预设新增列 `attached_duration_days`：`PERM_CLOSE_GROUP_BAN_ORG` 的机构处罚时长、
`DELIST_AND_BAN_PUBLISH` 的禁止发布时长都用它；**留空回退主处罚时长**
（`attachedDays()`：单独设置优先，都空=都永久）。`PERM_CLOSE_GROUP_BAN_ORG` 的主处罚
是纯永久（封群），故不再接受主天数（V6 版本用它兼作机构时长，V7 起由附带列接管）。
校验矩阵升为五元组（needsDays / allowsDays / allowsAttached），附带天数同样非负校验。

### 8.3 验证

新增 4 例（守卫 1 + 服务 3）：禁发布只挡发布不触活动、下架+禁发布 3/7 天独立生效
（断言附带到期明显晚于主时长窗口，证明未回退）、附带留空回退主处罚（群聊永久→机构永久）、
PUBLISH_BANNED 拦截发布且文案独立。全量 **302 例通过**（+4）；admin-web `vue-tsc` 通过。

## 9. 处罚组合化重构：基础惩罚 + 跨对象附带组件（V8）

### 9.1 设计模式

V6/V7 的做法是每种「组合处罚」一个动作枚举值（`PERM_CLOSE_GROUP_BAN_ORG`…），组合种类
随需求平方级膨胀。V8 改为**组合式**：

- **基础惩罚**（每种对象自己的封闭集合）：
  - 活动：`TEMP_DELIST` 暂时下架（需时长）/ `DELIST` 永久下架（群聊解散）；
  - 机构：`BAN_ORG` 封禁（可时长）/ `BAN_PUBLISH` 禁止发布（可时长）；
  - 群聊：`BAN_GROUP` 暂时封禁（需时长）/ `PERM_CLOSE` 永久解散；
  - 个人：`BAN_USER` 封禁账户（可时长；仅可作主惩罚）。
- **预设 = 主基础惩罚 + 附带组件**：机构/活动/群聊三者**互相附带**（附带组件取目标
  对象的基础惩罚集，不与主对象相同、同一对象不重复），**可复合共存**——例如
  「永久封群 + 暂时下架活动 5 天 + 封禁机构 2 天」三个基础惩罚并存于一个预设。
- **时长规则**：附带时长留空 = 跟随主处罚时长（主处罚永久则同为永久）；
  主处罚为永久时，附带暂时类必须自带时长。

### 9.2 落地

- 表：`preset_penalty_part`（预设组件）+ `penalty_part`（执行留痕，含解析后到期时刻）；
  `preset_penalty.action` 语义升级为「主基础惩罚」，`attached_duration_days` 退役，
  旧组合动作由迁移映射（如 `PERM_CLOSE_GROUP_BAN_ORG` → 主 `PERM_CLOSE` + 附带(机构, BAN_ORG, 原附带时长)）。
- 执行：`executePart` 统一分派主/附带组件，目标 id 按举报对象联动解析（群→活动/机构、
  活动→机构）；解析不到则跳过（机构处罚附带「下架活动」但无具体活动——机构面联动已覆盖）。
- 恢复扫描走组件行（暂时类到期→恢复对应对象），V8 前的动作式存量行保留原路径并去重。
- **举报合并展示**：新增 `/admin/abuse/reports/grouped`——对同一对象的举报合并为一条
  （对象 + 举报数 + 待处理数 + 最新状态），展开可见每条举报并逐条处置；管理端列表切换到该视图。

### 9.3 验证

新增 3 例（复合共存 3 组件执行留痕、组合校验四连拒 + 合法组合、同对象举报合并），改造
3 例（旧动作名 → 组合构造）。全量 **305 例通过**（+3）；admin-web `vue-tsc` 通过。

## 10. 治理台体验修正：预设按对象过滤 + 对话框防误关

V8 上线后的三处 admin-web 体验问题（`AbuseGovern.vue`）：

- **处置预设按对象过滤**：施加处罚时预设下拉原先列出全部 ACTIVE 预设，会混入作用于
  其它对象的组合。现按举报携带的目标 id 推断对象种类（活动/机构/群聊，仅
  `targetUserId` 即个人举报），只显示**主惩罚属于该对象基础惩罚集**的预设（判定集与
  后端 `BASE_ACTIONS` 同源，前端 `ACTION_MATRIX` 复用）；该对象无可用预设时占位提示
  「该对象暂无可用预设」。
- **预设对话框加宽**：申请新增预设含主惩罚 + 最多两条附带组件行，480px 过窄，

  点击遮罩不再关闭，避免长表单（组件行、意见）误点丢失。

## 11. 今日 Bug 修复总览（成因 → 解决）

收录全天踩坑与修复，作为快速回顾索引；各条详情见对应章节。

### 11.1 受护人代建即 500（最严重，详见 §1）

- **成因**：`registerProtectee` 代建受护人时直插 `ACTIVE` 状态的监护绑定，漏写
  `confirmed_at`，撞上 `ck_guardian_binding_confirmed` CHECK 约束（ACTIVE 必须有
  确认时间），必现 500。
- **解决**：插入路径补齐 `confirmed_at`，插入语义与约束对齐。

### 11.2 活动创建时间/人数无校验（详见 §2）

- **成因**：规则只存在于需求描述，前后端都没拦——可提交违反 12:00 规则、结束早于
  开始、报名开始晚于活动开始、人数 ≤ 0 的活动。
- **解决**：服务端作为唯一裁决方补齐全部规则校验，org-web 创建表单同步双向校验与提示。

### 11.3 V8 迁移三连败（过程性踩坑，结论沉淀于 V8 文件头）

- **败因一（语句顺序）**：组件数据 INSERT 写在建表 `preset_penalty_part` 之前，
  `Table doesn't exist`；另有陈旧的第二段 INSERT 误给全部活动预设挂组件。
  解决：重排为建表 → INSERT，删除陈旧块。
- **败因二（UUID 超长）**：`REPLACE(UUID(),'-','')` 产出 32 字符，而 id 列是
  `CHAR(26)`，严格模式报 `Data too long`。解决：改为
  `LEFT(REPLACE(UUID(),'-',''),26)` 截断。
- **败因三（CHECK 实时校验）**：把 `PERM_CLOSE_GROUP_BAN_ORG` 映射为 `PERM_CLOSE`
  时被旧 `ck_preset_penalty_action` 当场拒绝——MySQL 的 CHECK 约束**逐行实时评估**，
  「先改数据、后换约束」行不通。解决：顺序改为「先 DROP 旧 CHECK（放宽）→ 再
  UPDATE 数据 → 最后 ADD 新 CHECK（收紧）」，此规则写入 V8 文件头。
- **伴生问题**：失败迁移在 `flyway_schema_history` 留下 `success=false` 行阻塞下次
  启动；DDL 隐式提交导致半成品表残留。解决：一次性 JDBC 程序清理失败行与半成品表，
  验证回滚完整性后再重试。

### 11.4 一次性 JDBC 脚本无法编译

- **成因**：PowerShell `Set-Content -Encoding UTF8` 写出带 BOM 的文件 → javac 报
  「非法字符 '\ufeff'」；脚本风格顶层 `var` 无类声明 →「需要 class, interface」。
- **解决**：`[System.IO.File]::WriteAllText(path, code,
  [System.Text.UTF8Encoding]::new($false))` 无 BOM 写入 + 显式
  `public class X { public static void main }`。

### 11.5 前端类型检查错误（V8 改造残留，详见 §9）

- **成因**：合并举报改造移除分页但模板残留 `reportPage` 引用；嵌套表格回调
  `row.reports.find(...)` 产生隐式 any（长行编辑吞换行导致漏改）。
- **解决**：删除残留变量，抽脚本侧 `firstPendingReport(group)` 辅助函数。

### 11.6 治理台体验问题（详见 §10）

- **成因**：处置对话框预设下拉用全量 ACTIVE 列表，混入其它对象类型的预设（V8
  组合化后种类更多更显眼）；预设表单加组件行后 480px 过窄；点击遮罩即关闭导致
  长表单误丢。
- **解决**：按举报目标 id 推断对象种类、用与后端 `BASE_ACTIONS` 同源的
  `ACTION_MATRIX` 过滤预设（无可用时占位提示）；对话框加宽至 640px；两个对话框加
  `:close-on-click-modal="false"`。
