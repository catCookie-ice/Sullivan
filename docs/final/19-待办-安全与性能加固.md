# SullivanMINI 待办：安全与性能加固

**建立日期:** 2026-10-16  
**最近补充:** 2026-10-18（§7：Android 端补齐功能后新增的暴露面）  
**适用范围:** SullivanMINI `[MINI]`  
**背景:** 2026-10-16 接入扫码绑定与扫码授权登录后（见 `17-开发日记-2026-10-16.md`），
安全与容量面上的缺口被放大：扫码登录把「出示设备的凭据」和「监护人的授权」放到了**网络中间人可及**的位置，
而当前的传输是明文 HTTP、令牌无法作废、公开票据端点无限流。本文登记六项后续加固，
**均为 `[MINI]` 范围内应当做完的事**（不是 `[FULL]` 预留），按优先级排序。

> 本文只登记待办与做法，**不改任何正文口径**。其中涉及既有文档已写明的部分（`01` §5 的 `429`、
> `06` §6 的 TLS 反向代理、`14` §4 的 `sv:token:revoked:{jti}` 键）与本文互为呼应，
> 落地时以那几处原文为准。

## 1. 总览

| # | 优先级 | 事项 | 现状 | 主要收益 |
|---|---|---|---|---|
| SEC-01 | **P0** | 升级为 HTTPS | 全链路明文 HTTP | 堵住扫码票据与令牌被同网段嗅探 |
| SEC-02 | P1 | 完善限流策略 | 完全未做，无 `429` 出口 | 堵住公开端点的资源耗尽面 |
| SEC-03 | P1 | 引入 `jti`（令牌唯一 ID，随令牌过期自动清理） | 令牌无标识，签发即不可区分 | 为吊销提供可寻址的标识 |
| SEC-04 | P1 | 引入黑名单（服务端记录"作废令牌列表"） | 无任何吊销手段 | 泄露后可止损 |
| SEC-05 | P1 | 引入 refresh 机制（短 access + 长 refresh，吊销只需让 refresh 失效） | 只有 1800s 的单个 access token | 吊销粒度落到"每台设备一次登录" |
| PERF-01 | P2 | 引入 Redis 减小数据库压力 | Redis 仅用于管理员注册码；票据/绑定码全走 MySQL | 削掉轮询读与状态 CAS 的库压力 |

**落地顺序**：SEC-01 独立且收益最大，先做；SEC-03/04/05 是同一件事的三个零件，按序做；
SEC-02 与 PERF-01 可穿插；SEC-02 依赖 PERF-01 提供的计数器（除非先接受进程内计数）。

## 2. SEC-01：升级为 HTTPS（P0）

### 现状

后端是 `http://<局域网IP>:8642`，没有 TLS。Android 端因此必须开
`android:usesCleartextTraffic="true"`（`AndroidManifest.xml` 第 26 行，带已知风险注释），
baseUrl 也是明文——地址是构建期常量（`gradle.properties` 的 `serverBaseUrl`
→ `BuildConfig.SERVER_BASE_URL`，见 `17-开发日记-2026-10-16` §8），
它决定的是"连哪台服务器"，不含 scheme 之外的任何加密承诺。

### 为什么这是第一优先级

扫码登录的威胁模型**就是**网络中间人：公开票据端点在同一个 Wi-Fi 下人人可调，
明文传输时票据、`exchangeCode` 与最终令牌对同网段任何人可见。
结果是 `qr_login_ticket.secret_hash` 那套「客户端凭证只留在出示设备上」的设计**在网络层完全失效**——
它能防住"读数据库的人替出示设备兑换令牌"，但防不住"同网段抓包的人直接抄走令牌"。
密码登录同样是明文（监护人的账密就这么过一次网）。

### 做法

`06` §6 已经写明方向：「生产环境可由 Nginx/TLS 反向代理统一域名，但 Nginx 不是业务网关」。
按这个口径办，不要给 Spring Boot 直接加证书：

1. 前置 Nginx（或 Caddy）终结 TLS，反代到 `127.0.0.1:8642`；
2. 证书用**自签**即可（局域网内部使用），但要在 Android 端把该 CA 加进
   `network_security_config.xml` 的信任锚，而不是退回 `usesCleartextTraffic`；
3. Android 侧：`SessionStore.DEFAULT_BASE_URL` 改 `https://`，
   `AndroidManifest.xml` 删掉 `usesCleartextTraffic="true"`（或按域限制），
   登录页的「服务器地址」输入框加 `https://` 前缀校验；
4. WebSocket（`/ws/**`）同样要 `wss://`，否则实时会话仍是明文。

### 注意

- **不要**只加 `Strict-Transport-Security` 就认为做完了——那只管浏览器，Android 不受它约束。
- 自签证书在 Android 上的信任配置是这一步真正的工作量所在；
  可以顺带做一个"开发期信任全部"的 debug-only 变体，但**必须与 release 分开**。
- 完成后，`17-开发日记-2026-10-16` §5 第 1 条风险才可关闭。

## 3. SEC-02：完善限流策略（P1）

### 现状

**完全未做**：全仓 grep `RateLimit|Bucket4j|429` 在业务代码里零命中。
`01` §5 已经把 `429` 写进本 API 的 HTTP 语义（「限流 `429`」），
但**没有任何实现**；`ApiErrorHandler` 目前只处理 `ApiException` 与参数校验两类。

> 注意别把 `04` §6.3 D3 当成本项的先例：那里的 `429` 是**导航链路里服务端限流客户端**
> （客户端据此降帧），方向与本节相反，而且那条链路现已是预留点 `NAV-01`（被端侧检测替代）。
> 本节要做的是服务端**限制调用方**，两者只是共用同一个状态码。

### 要保护什么（按暴露程度排序）

| 端点 | 为什么需要 | 建议口径 |
|---|---|---|
| `POST /api/v1/qr/login-tickets` | **匿名可调**，每次写一行 MySQL；无限流即资源耗尽面 | 按 IP 计数，如 10 次/分钟；同时限制单 IP 的未消费票据数 |
| `GET /api/v1/qr/login-tickets/{ticket}` | 出示设备每 1.5 秒轮询一次，N 台设备就是 N×40 QPS 的读 | 按 IP 计数，放宽（轮询是正常行为），如 120 次/分钟 |
| `POST /api/v1/auth/login` | 撞库 | **按账号 + 按 IP 双计数**，如 5 次/分钟/账号；配合失败次数锁定 |
| `POST /api/v1/auth/register/user` 等 | 刷注册 | 按 IP 计数 |
| `POST /api/v1/qr/bind-codes/scan` | 试码（12 位字母表，59 bit，但可暴力尝试） | 按**监护人账号**计数，如 10 次/分钟 |

### 做法

1. 先选落点：**基于 Redis 的固定窗口/滑动窗口**即可，不必上 Bucket4j 那套令牌桶
   —— 本项目的限流目的是抗滥用而不是精确整形。
   若 SEC-02 先于 PERF-01 落地，可以先用进程内计数器，但**必须在多实例前换成 Redis**。
2. 加一个 `RateLimitFilter`（或按端点的 `@RateLimited` 切面），命中时抛
   `ApiException(HttpStatus.TOO_MANY_REQUESTS, ...)`，并让 `ApiErrorHandler` 顺带下发
   `Retry-After` 头。
3. **登录失败锁定**要一并做（当前 `AuthService` 完全没有任何失败计数）：
   连续失败 N 次后锁定一段时间，锁定状态放 Redis 并带 TTL，不要新增表。
4. 反代层（SEC-01 引入的 Nginx）也建议加一层粗粒度 `limit_req`，
   但**应用层限流不能省** —— 反代看不到账号维度。

### 注意

- 限流键要含端点作用域，否则「轮询 120 次/分钟」会把「建票 10 次/分钟」的额度吃光。
- 别对**已登录**的常规业务接口一把梭加限流，那会先伤到正常使用的受护人。
- 打码/验证码不属于本项范围（受护人是低视力群体，扫码页的手动输入兜底已经是无障碍妥协）。

## 4. SEC-03 / SEC-04 / SEC-05：令牌的标识、作废与续期（P1，三件一起做）

这三项是同一条链上的三个零件，**分开做会出现半成品状态**（例如有 `jti` 但没有黑名单 = 白加一个字段）。
现状：`JwtService` 只有 `issue(AuthPrincipal)` 与 `parse(String)`，TTL 固定 1800s
（`application.properties` 第 47 行），无 `jti`、无黑名单、无 refresh。
`JwtAuthenticationFilter` 只做签名与过期校验，解析成功后直接放行。

> **重要前提：refresh 不是"新增设计"，而是"补做一件已经写进需求、却整体漏掉的功能"。**
> 现状是规范集已完整描述了双令牌，服务端一行都没写：
>
> | 位置 | 原文要求 | 实现状态 |
> |---|---|---|
> | `01` **FR-02** 登录、令牌与退出 | 「退出后当前刷新令牌必须失效」 | **无 `/auth/logout` 路由** |
> | `04` 登录用例第 7 步 | 「服务端验证凭据和账号状态，**签发 JWT 与刷新令牌**」 | `TokenResponse` 只有 `accessToken`，**无 `refreshToken` 字段** |
> | `15` 阶段 3 交付物 | 「Java 注册、登录、**刷新令牌**、账号状态和统一错误响应」 | 阶段已过，该项未交付 |
> | `05` §2 / §4 / §6 | 登记 `auth_refresh_token`；唯一约束含「刷新令牌哈希」；按失效时间清理 | 表只在 `schema.sql`，**未进任何 Flyway 迁移** |
> | `06` §(identity 能力) | 「注册、登录、JWT、**刷新令牌**、角色资料」 | — |
> | `03` §(禁止读取) | 排除「刷新令牌」不得经普通资料接口读出 | — |
> | `db/schema.sql:51-68` | `auth_refresh_token` DDL（`token_hash` UNIQUE、`status` CHECK） | 库里没有这张表 |
> | `api/openapi.yaml:58-64` | `/auth/refresh`、`/auth/logout` 两条路径 | `AuthController` 只有 4 个路由，均无 |
>
> 也就是说：需求、用例、阶段计划、数据字典、架构、权限、DDL、契约**七处都写了**，
> 唯独实现和验收漏了——而且阶段 3 当时是以「登录返回 200 并拿到令牌」过的关，
> 没有回头比对 `04` 那一句「签发 JWT **与**刷新令牌」。
> 所以本次**不要新建第二套表或第二个路径**，照上表把已有的那套补齐即可；
> `TokenResponse` 加 `refreshToken` 字段属于**契约对齐**，不是新增契约。
>
> 另有两处**规范本身的缺口**要顺带补，别指望它们自己出现：
> `04` §3 UC-01 通篇没有「退出」流程（全仓 grep「退出/登出/注销」在 `04` 里零命中），
> 而 `01` FR-02 却要求「退出后刷新令牌必须失效」——**需求有条文、用例无流程**；
> `02` 也没有刷新令牌的状态枚举，而 `schema.sql` 的 CHECK 已经限定了
> `ACTIVE/REVOKED/EXPIRED` 三值，按 `README` §3 的权威顺序（`02` 高于 `schema.sql`）
> 应在 `02` 补一节与 DDL 对齐。
>
> 还有一处**缺 refresh 留下的痕迹**值得一并回看：`02` 志愿者兼任状态机末尾写着
> 「审核通过后申请人须重新登录以**刷新 JWT 中的 `VOLUNTEER` 角色**」。
> 这句话现在是**因为**没有 refresh 才成立的（令牌里的角色只能靠重新登录换掉）；
> SEC-05 落地后它要么改成走 refresh，要么明确写清"角色变更仍需重新认证"是有意为之
> （后者更安全——角色提权不该靠旧令牌自助续期）。别让这句话无声地变成错的。

### 4.1 SEC-03：引入 `jti`

**做法**：`JwtService.issue` 增加 `jti`（`UUID.randomUUID()` 或 ULID），
并在 `parse` 时把它带进 `AuthPrincipal`（或另开一个承载 `jti`/`exp` 的返回类型——
过滤器需要拿到 `exp` 才能给黑名单设 TTL，现在的 `parse` 把 `exp` 丢掉了）。

**你说的「会随着令牌过期自动清理」怎么落实**：

- `jti` 本身只是个标识，**不需要清理**，它随令牌一起过期；
- 需要清理的是**黑名单里对应那条记录**。所以黑名单条目的 TTL 设成
  `exp - now`（剩余有效期），令牌自然过期后条目自动消失，不必写清理任务；
- 这正是 `14` §4 已经登记的键：**`sv:token:revoked:{jti}`**，按原文用，不要另起命名。

### 4.2 SEC-04：引入黑名单

**做法**：`JwtAuthenticationFilter` 解析成功后，多查一次
`sv:token:revoked:{jti}` 是否存在，存在则 `clearContext()` 并返回 `401`。

**必须注意的取舍**：

1. **过滤器加一次 Redis 查询 = 每个请求多一次网络往返**。建议先在
   `JwtAuthenticationFilter` 里明确写出这个代价，或只对敏感端点查。
   不要为了性能引入本地缓存 —— 那会让吊销生效延迟，与吊销的目的相悖。
2. **Redis 不可用时的策略必须先定**，二选一，并且写进注释：
   - **fail-open**（读不到就放行）：可用性优先，但**此时吊销完全失效**；
   - **fail-closed**（读不到就 401）：吊销可靠，但 Redis 抖动会让**全站 401**。
   本项目目前所有 Redis 用法都是 fail-open（见 `AdminRegistrationService.writeRedisCode`
   的「Redis 不可用时静默失败」注释），但**令牌校验面比注册码面敏感得多**，
   建议 fail-open + 告警，并在文档里写明"Redis 不可用期间无法吊销"。
3. **上限**：黑名单只在令牌剩余有效期内存活，最长 1800s（引入 refresh 后 access 更短），
   所以内存占用天然有界，不必担心无限增长。

### 4.3 SEC-05：引入 refresh 机制

**口径**：**短 access token + 长 refresh token，吊销时只需让 refresh 失效**。

| | access token | refresh token |
|---|---|---|
| 形态 | JWT（无状态，带 `jti`） | **随机串 + 数据库哈希**（有状态） |
| 建议 TTL | 15 分钟（当前是 1800s = 30 分钟，要缩短） | 30 天 |
| 存哪 | 只在客户端内存/`SessionStore` | `auth_refresh_token` 表（`token_hash`，只存哈希） |
| 吊销 | 走黑名单（SEC-04），只在剩余 TTL 内有效 | **直接置 `REVOKED`**，立即失效 |

**为什么 refresh 用数据库而不是 JWT**：refresh 一旦泄漏危害是长期的，必须可即时撤销，
而"可撤销"与"无状态"天然矛盾。`auth_refresh_token` 表的字段（`status`
`ACTIVE/REVOKED/EXPIRED`、`token_hash` 唯一、`expires_at`、`device_label`）已经为此设计好了，
直接落地即可。

**做法**：

1. 新增迁移建 `auth_refresh_token` 表（当前只在 `schema.sql` 里，**数据库里没有**），
   DDL 照 `db/schema.sql` 第 51–68 行，下一版是 `V7`。
2. 登录（账密 **与** 扫码 exchange 两条路径）都改为返回 `{accessToken, refreshToken, ...}`。
   **扫码路径要给 refresh**：不然受护人每 15 分钟就要叫监护人重新扫一次，
   这与本次刻意"不给扫码路径签更短 TTL"的理由（见 `17-开发日记-2026-10-16` §5 第 2 条）冲突，
   缩了 access TTL 却不同步给 refresh，就是把问题从"令牌无法吊销"换成"受护人被频繁打扰"。
3. 实现 `POST /api/v1/auth/refresh`：按 `token_hash` 查表 → 校验 `ACTIVE` 且未过期 →
   **旋转**（旧的置 `REVOKED`，签发新的 refresh）→ 返回新的 access。
   旋转是必须的，否则 refresh 永久有效，等于没有 TTL。
4. 实现 `POST /api/v1/auth/logout`：把该 refresh 置 `REVOKED`
   （可选：同时把当前 access 的 `jti` 写进黑名单，让登出立刻生效而不是等 15 分钟）。
5. 客户端：`SessionStore` 增加 `refresh_token`；`ApiClient` 的拦截器在收到 `401` 时
   用 refresh 换一次新 access 并重放请求（**只重试一次**，避免死循环）。
6. 加一条**设备级的失效路径**：受护人换手机、或监护人发现异常时，
   能列出并吊销某个 `device_label` 的 refresh。

### 4.4 对齐既有设施

- `JwtService.parse` 现在丢掉 `exp`。做黑名单 TTL 前要把它带出来，
  否则要么给黑名单设一个猜的 TTL，要么改成每次查询都算——前者会留下"过期很久还能吊销"的垃圾键。
- `JwtAuthenticationFilter` 现在 `catch (RuntimeException ignored)` 静默吞掉解析异常，
  连日志都没有。排查"令牌为什么没生效"时这是盲区，建议至少 `debug` 一行原因。

## 5. PERF-01：引入 Redis 减小数据库压力（P2）

### 现状

`spring-boot-starter-data-redis` 已在 `pom.xml`，配置在 `application.properties` 第 28–30 行，
但**只有 `AdminRegistrationService` 在用**（注册码双写 + 原子核销），
而且用法是 fail-open 的（Redis 不可用就静默回退 DB）。
换句话说：**Redis 目前对数据库压力为零改善**。

### 当前最耗库的三处

| 位置 | 压力来源 | 建议 |
|---|---|---|
| `GET /qr/login-tickets/{ticket}` | 出示设备每 1.5 秒轮询，每台设备约 40 次/分钟的 MySQL 读 | 票据状态进 Redis（`status`/`exchangeCode`/`ttl`），MySQL 仍是权威记录，只在 `CONFIRMED`/`CONSUMED` 这类**状态跃迁**时写库 |
| `POST /api/v1/qr/bind-codes/scan` | 每次扫都读码 + 建绑定 + 走 `BindingService` | 码 → 受护人 的映射进 Redis，`active_code_key` 唯一约束仍留在 DB 兜底 |
| `JwtAuthenticationFilter`（SEC-04 落地后） | 每个请求多一次 Redis 查询 | 这一项是**新增**压力，注意别把 Redis 变成新的单点 |

### 做法与红线

1. **MySQL 始终是权威记录**（`05` §6 与 `14` §4 已经这么定），Redis 只做缓存与索引。
   「缓存命中不能跳过 Java 的行级权限检查」是 `14` §4 的原话，别绕过。
2. **键名照 `14` §4 的表用**，已登记的包括 `sv:loc:` / `sv:geo:` / `sv:vol:available:` /
   `sv:idem:` / `sv:perm:admin:` / `sv:bind:version:` / `sv:token:revoked:`。
   新增票据相关的键时要**回到 `14` §4 登记**，不要只在代码里起名。
3. 关系或权限缓存**必须带版本**（`sv:bind:version:{protectee_uid}` 就是为此）。
4. Redis 不可用时全部 fail-open，与现有 `AdminRegistrationService` 的写法一致；
   但 SEC-04 的黑名单是例外，需要单独决策（见 §4.2）。
5. 不要把 Redis 当作"顺手放点数据"的地方 —— `05` §6 已经写明它只承担
   最新位置、Geo 索引、可服务状态、幂等键、短时权限缓存与令牌吊销标记。

## 6. 落地顺序建议

| 步 | 事项 | 依赖 | 可独立验收的标志 |
|---:|---|---|---|
| 1 | SEC-01 HTTPS | 无 | 客户端 `https://` 可登录；抓包看不到明文令牌 |
| 2 | SEC-03 `jti` + SEC-04 黑名单 | 无（`jti` 先行） | 手工把某 `jti` 写进黑名单后，该令牌立即 `401` |
| 3 | SEC-05 refresh | SEC-03/04 | 登出后 refresh 立刻失效；access 过期可用 refresh 续 |
| 4 | PERF-01 Redis | 无 | 轮询路径不再产生等量 MySQL 读 |
| 5 | SEC-02 限流 | 建议在 4 之后（用 Redis 计数器） | 打 `POST /qr/login-tickets` 超过阈值返回 `429` + `Retry-After` |

> §7 增补的三个端点（找回密码两步、实时会话发起）归入上表第 5 步，
> 不单独占一行 —— 它们是 SEC-02 的**同一套机制**在新端点上的应用，不是新机制。

SEC-01 与 SEC-02 没有代码耦合，可以并行；SEC-03/04/05 建议由同一人一次做完，
分开提交容易留下"有 `jti` 没人查"这类中间态。

## 7. 补充（2026-10-18）：Android 端补齐功能后，暴露面又大了一圈

`17-开发日记-2026-10-18` 把 `client-web` 已实现的接口全量搬到了 Android 端。
**服务端一行没改，但明文链路上的端点变多了**，本文原先的登记没有覆盖新增的这几个：

| 新增端点 | 谁在调 | 为什么值得单独登记 |
|---|---|---|
| `POST /api/v1/auth/password-recovery/start` | 找回密码第一步 | **匿名可调**，传入登录名后会返回该账号**设过的找回方式的掩码**（手机号/邮箱末几位）。这是一个**账号存在性 + 联系方式泄露**的接口，明文传输下同网段可直接读取 |
| `POST /api/v1/auth/password-recovery/verify` | 找回密码第二步 | 匿名可调，且是**猜验证码/猜联系方式**的入口。当前没有任何失败计数，可无限次尝试 |
| `POST /api/v1/auth/register/user` | 注册 | 已在 §3 表中登记限流，此处不重复 |
| `POST /api/v1/realtime/sessions` | 实时会话发起 | 每次调用向已绑定的一方**推一条待接受会话**。无限流时可用于骚扰（反复发起），也会给对端制造一堆待处理的会话行 |

对应地，§3 的限流表要**增补两行**（口径从这里读取，落地时按 §2 的做法做）：

- `POST auth/password-recovery/start`：按 **IP + 按登录名** 双计数，从严（如 5 次/分钟）。
  它同时是账号枚举面，**返回内容不应区分「账号不存在」与「账号没设找回方式」**——
  这一条属于接口设计，不是限流能解决的。
- `POST auth/password-recovery/verify`：按 **IP + 登录名** 计数，并做失败锁定；
  与 `POST auth/login` 的撞库防护同等对待（它猜的是联系方式，而联系方式本身就是
  找回密码的最后一道门）。
- `POST realtime/sessions`：按**发起方账号**计数。

另外，Android 端新开的 `/ws/realtime` 长连接（`service/websocket/RealtimeSocket`）
同样跑在明文上（`ws://`）。§2 第 4 条已经写明 WebSocket 要一并升 `wss://`，
这次的实时会话功能让它从"将来要改"变成"现在就有明文长连接在跑"。

> 本次**未对上述任何一项做加固**，也**未验证**服务端对找回密码两步的实际行为
> （`verify` 是否已有失败计数需要回看 `AuthService`）。这里只是把新出现的面登记下来。
