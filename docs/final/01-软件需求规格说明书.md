# SullivanMINI 软件需求规格说明书

**文档版本:** v2.0  
**基线日期:** 2026-08-04  
**适用范围:** SullivanMINI `[MINI]`

## 1. 目的与约定

本文给出 SullivanMINI 可开发、可测试的功能需求。状态值以 `02-术语枚举与状态机.md` 为准，权限以 `03-角色权限与数据范围.md` 为准，业务步骤以 `04-用例与业务流程.md` 为准。

需求关键字“必须”表示验收强制项。“可以”表示允许但非强制。所有时间存储为 UTC，接口使用 ISO 8601，界面按用户时区显示。所有写接口必须校验 JWT、角色、行级权限和请求参数。

## 2. 总体说明

### 2.1 用户与运行环境

- 受护人主要使用 Android，依赖 TalkBack、摄像头、麦克风、定位和本地 TTS。
- 监护人可使用 Android 或响应式 Web。
- 志愿者可使用 Android 或响应式 Web。
- 公益机构和管理员使用响应式 Web。
- 服务端只分 Java 业务应用与 Python 导航应用，使用统一数据库，不采用微服务架构。

### 2.2 通用业务规则

1. 默认拒绝: 未明确授予的角色、操作或数据行均不可访问。
2. 客户端只负责展示和交互，角色与数据权限以服务端判断为准。
3. 受护人不能自主注册；监护人创建后，受护人可独立登录、导航、报警和自行申请公益服务。
4. 绑定只有在受护人确认后才赋予监护权限。
5. MINI 全部公益服务免费，不处理任何金额。
6. 删除业务记录默认采用状态停用或取消；有审计价值的申请、报名、报警不得物理删除。
7. 关联对象写入前必须在 Java 事务中验证存在性、角色、状态与数据权限；数据库外键不能替代授权。
8. 重复提交应通过业务唯一约束或幂等键避免产生重复有效记录。

## 3. 功能需求

### 3.1 身份与账号

#### FR-01 用户注册与角色入口

系统必须允许自然人选择 `GUARDIAN` 或 `VOLUNTEER` 注册。受护人不得自主注册，只能由已登录监护人创建。Android 必须在登录/注册前提供监护人、志愿者和受护人登录入口；Web 必须提供监护人、志愿者、机构和管理员入口。

**验收规则:**

- 使用唯一账号和合法密码可注册自然人账号，账号重复返回 `409`。
- 注册角色写入 `user_role` 后，普通用户不得直接修改角色。
- 监护人兼任志愿者时只新增一条 `user_role(USER, VOLUNTEER)` 关系，不创建第二个账号。
- 受护人创建事务必须同时产生 `ACTIVE`、`is_primary=true`、`permanent_flag=true` 的监护绑定。
- 受护人注册接口不对外开放；未授权调用返回 `403`。

#### FR-02 登录、令牌与退出

系统必须校验账号、密码和账号状态，成功后签发包含主体 ID、主体类型、角色和过期时间的 JWT。退出后当前刷新令牌必须失效。

**验收规则:**

- 密码错误统一返回 `401`，不得透露账号是否存在。
- `DISABLED` 账号返回 `403` 且不签发令牌。
- 过期、篡改或主体类型不匹配的令牌访问受保护接口返回 `401`。
- 日志不得记录明文密码、完整令牌或身份证明材料。

#### FR-02A 管理员注册码与启动初始化

管理员注册必须提交一次性注册码。注册码映射一个初始 `admin_role`，该角色通过 `admin_role_permission` 决定新管理员的初始权限。注册码只能由 `SUPER_ADMIN` 或 `HR_ADMIN` 创建；HR 管理员不得创建 `SUPER_ADMIN` 或 `HR_ADMIN` 注册码。

服务器启动时检查是否存在至少一个启用的 `SUPER_ADMIN`。不存在时，必须读取配置文件中的 `app.bootstrap.admin.login`、`app.bootstrap.admin.password` 和 `app.bootstrap.admin.display-name` 创建最高管理员；配置缺失则启动失败。

#### FR-02B 志愿者兼任申请与审核

持有 `GUARDIAN` 角色的自然人必须能提交志愿者兼任申请；具备 `VOLUNTEER_REVIEW` 权限的管理员必须能审核。审核通过后事务内追加 `VOLUNTEER` 角色，不创建第二个账号。申请限制（注册时间须满可配置天数，默认 90 天）必须由服务端校验。

**验收规则:**

- 非 `GUARDIAN` 角色或账号不可用提交申请返回 `403`；已持有 `VOLUNTEER` 角色返回 `409`。
- 注册未满配置天数提交申请返回 `400`，提示剩余天数；管理员审核通过时二次校验注册时长。
- 同一申请人最多一条 `PENDING` 申请，重复提交返回 `409`。
- 只有具备 `VOLUNTEER_REVIEW` 权限的管理员可查看/审核；拒绝必须填写原因。
- 审核通过事务内追加 `VOLUNTEER` 角色；申请人须重新登录刷新 JWT 中的角色。
- 审核结果（通过/拒绝）必须生成申请人的 `APPLICATION_RESULT` 通知（通知模块接入后生效）。

#### FR-03 个人资料

自然人、机构和管理员必须能读取自己的资料；自然人和机构可修改允许自助维护的字段。账号、角色、审核状态等受控字段不可通过资料接口修改。

**验收规则:**

- 主体只能读取和修改自己的资料，管理员治理接口除外。
- 手机号、姓名、联系方式按字段规则校验；非法输入返回 `400`。
- 修改成功记录 `updated_at`；敏感字段在非必要响应中脱敏。

### 3.2 监护绑定与位置

#### FR-04 发起绑定

已登录监护人必须能以受护人 UID 发起绑定请求；已登录受护人必须能以监护人 UID 发起绑定请求。系统创建 `PENDING` 请求并记录发起方 `requested_by`，不得立即授予监护权限。绑定关系是多对多。

**验收规则:**

- 目标不存在、角色与发起方不互补（发起方 `GUARDIAN` 目标须 `PROTECTEE`，反之亦然）时返回 `404` 或通用不可绑定结果。
- 相同监护人与受护人已有 `PENDING` 或 `ACTIVE` 关系时返回 `409`。
- 请求创建后仅接收方（非发起方）可确认或拒绝；请求 7 天后过期。
- 待确认期间监护人不能查看目标位置、代申请或接收其报警。

#### FR-05 确认、拒绝与解除绑定

接收方（发起方的另一方，受护人或监护人）必须能查看待确认请求并确认或拒绝。确认后关系变为 `ACTIVE`。监护人或受护人均可解除已生效关系；`permanent_flag=true` 的永久初始绑定不可解除。

**验收规则:**

- 非接收方处理请求返回 `403`；发起方之外的账号取消请求返回 `403`。
- 首条生效关系自动成为主监护关系；后续关系为普通监护关系。
- 主监护关系解除后，如仍有生效关系，系统将最早生效的一条提升为主监护；否则主监护为空。
- 拒绝、取消、过期或解除后立即撤销由该关系产生的数据访问权。
- 永久初始绑定（`permanent_flag=true`）不得通过业务接口解除，解除请求返回 `403`。
- 并发确认必须保证同一受护人最多一条 `is_primary=true` 的生效关系。

#### FR-06 位置上报与查看

受护人 Android 必须能在获得系统定位授权后上报位置。监护人只能查看与自己存在 `ACTIVE` 关系的受护人最新位置。

**验收规则:**

- 位置包含经纬度、采集时间和可选精度；服务端拒绝非法坐标和明显的未来时间。
- 活跃位置共享时上报间隔目标不大于 10 秒；超过 30 秒显示“位置可能已过期”及最后更新时间。
- 定位权限关闭、定位失败或无缓存时明确显示不可用，不伪造坐标。
- 解除绑定后原监护人再次查询返回 `403`；管理员默认无实时位置查看权。

### 3.3 全景分割导航与语音

#### FR-07 导航会话与帧分析

受护人 Android 必须能启动和停止导航会话。启动后采集并压缩摄像头帧，直接提交给 Python 导航应用；应用返回障碍物列表、引导文本、风险级别和处理时间。

**验收规则:**

- 只有 `PROTECTEE` 可创建导航会话和提交自己的帧。
- 单帧输入格式、尺寸和大小不合法时返回 `400`；超限请求返回 `413` 或 `429`。
- 基准环境目标为有效处理吞吐不低于 10 FPS、服务端单帧推理 `P95 <= 150 ms`、端到端引导 `P95 <= 500 ms`。
- 结果必须关联会话 ID 和帧序号；过期乱序结果不得覆盖更新结果。
- 停止会话后服务端拒绝继续写入该会话的普通帧。

#### FR-08 引导与安全降级

系统必须依据分割结果生成简短、可执行的中文引导。高风险障碍优先，连续相同低风险提示应抑制重复播报。

**验收规则:**

- 返回结果至少区分 `SAFE`、`CAUTION`、`DANGER`、`UNKNOWN`。
- 低置信度必须使用保守措辞，不得输出确定的“前方安全”。
- 连续无显著变化的普通提示间隔至少 2 秒；`DANGER` 可打断普通提示。
- 网络中断、超时、模型不可用或连续丢帧时返回/展示“导航暂不可用，请停下并确认环境”等降级提示。
- 无新分析结果时不得无限复用上一帧的“安全”判断。

#### FR-09 Android 本地 TTS

引导语音必须由 Android 系统 `TextToSpeech` 在本地合成和播报。后端只生成文本及优先级，不生成或存储 TTS 音频。

**验收规则:**

- Android 可配置语速、音量和是否播报普通安全提示。
- TTS 未安装、初始化失败或语言不可用时，以震动和高对比度文字提示，并允许重试。
- 高风险提示可中断低风险播报；停止导航会清空非报警播报队列。
- 服务端 API 响应及对象存储中不出现导航 TTS 音频文件。

#### FR-10 语音指令与替代操作

受护人 Android 必须支持启动导航、停止导航和触发报警三类语音意图。每项语音能力必须提供可访问的按钮替代操作。

**验收规则:**

- 语音识别不确定时要求确认，不执行猜测出的高风险操作。
- 报警指令确认后调用报警流程；网络不可用时保留本地失败状态并持续提示用户。
- 麦克风权限被拒绝不影响按钮操作。
- TalkBack 可读出控件名称、状态和执行结果。

### 3.4 安全报警与通知

#### FR-11 创建报警

受护人必须能通过语音或醒目的可访问按钮创建报警。系统必须先持久化报警，再异步分发。位置不是创建报警的前置条件。

**验收规则:**

- 请求包含客户端幂等键；相同受护人和幂等键只创建一条报警。
- 报警保存触发类型、创建时间、可用的位置快照和位置采集时间。
- 无位置时仍返回报警 ID 和已受理状态，并在通知中标识“位置不可用”。
- 受护人只能查看和解决自己的报警；重复解决保持幂等。

#### FR-12 报警接收人路由

报警创建时，系统必须查询该受护人的全部 `ACTIVE` 监护关系。有一名或以上生效监护人时，向全部监护人分别创建投递记录；只有生效监护人为零时，才查询附近且可服务的志愿者并广播。

**验收规则:**

- 两名生效监护人场景必须生成两名监护人的独立投递记录，主监护人不享有排他权。
- 有生效监护人但全部推送失败时，不创建志愿者广播；失败投递按策略重试并可见。
- 无生效监护人时，仅选择 `is_available=true`、位置新鲜且在配置半径内的志愿者。
- 无符合条件的志愿者时报警仍保留，并标记无可用接收人，不返回伪成功投递。
- 接收人集合在一次路由事务中固化；后续绑定变化不追溯改写该次报警接收人。

#### FR-13 报警查看、确认和解决

报警接收人必须能查看分配给自己的报警并确认收到。受护人可将报警标记为已解决；管理员只可在治理权限下查看记录，不得代替受护人伪造接收确认。

**验收规则:**

- 监护人仅可查看绑定受护人且投递给自己的报警。
- 志愿者仅可查看广播时分配给自己的报警，且不得查看受护人的历史位置。
- 任一接收人确认后更新其投递状态和报警聚合状态，不覆盖其他接收人的投递状态。
- 报警解决后保留报警和投递审计记录。

#### FR-14 通知中心

系统必须提供报警、绑定、机构审核、服务申请、活动报名和系统通知，支持列表、未读数和标记已读。

**验收规则:**

- 每条通知有明确接收主体，用户只能读取和标记自己的通知。
- 标记已读幂等；重复调用不重复增加审计或未读数。
- 推送通道失败不丢失站内通知，失败原因和重试次数可追踪。
- 通知正文不得泄露超出接收人权限的身份证明、完整联系方式或历史位置。

### 3.5 公益机构与服务

#### FR-15 机构注册与审核

公益机构必须能提交注册资料，初始状态为 `PENDING`。有机构审核权限的管理员可批准或拒绝，并填写意见。

**验收规则:**

- 待审核或被拒绝机构可登录查看自身审核状态，但不可发布项目或活动。
- 批准后机构状态为 `APPROVED`；拒绝必须有原因。
- 被禁用机构不可执行写操作，其已发布内容按状态规则停止新增申请和报名。
- 机构只能查看自身资料和审核意见。

#### FR-16 免费公益服务项目

已认证机构必须能创建、修改、开放、暂停和关闭自己的公益服务项目。项目必须明确免费，不得包含价格或支付字段。

**验收规则:**

- 项目至少包含名称、描述、名额策略和状态；有限名额必须为非负整数。
- 非 `APPROVED` 机构发布返回 `403`。
- 机构不能修改其他机构项目；受护人和监护人只能浏览 `OPEN` 项目。
- 暂停或关闭不删除历史申请；关闭后不可重新开放。

#### FR-17 提交公益服务申请

受护人可为自己申请开放项目；监护人可为与其存在 `ACTIVE` 关系的受护人代申请。申请初始状态为 `PENDING`。

**验收规则:**

- 监护人代申请时必须记录申请人和受益受护人，且服务端验证生效绑定。
- 同一受护人对同一项目已有 `PENDING` 或 `APPROVED` 申请时返回 `409`。
- 名额按已批准申请占用；并发批准不得超过项目名额。
- 项目非开放、机构非认证或名额已满时拒绝新申请。
- 提交和处理流程中不出现价格、订单或支付步骤。

#### FR-18 处理公益服务申请

项目所属机构可批准或拒绝待处理申请，可将已批准申请标记完成。申请人可在待审核阶段取消。

**验收规则:**

- 只有项目所属机构可处理，越权返回 `403`。
- 拒绝必须填写原因；批准、拒绝、完成和取消后通知申请人及受益受护人可访问的账号。
- 完成只允许从 `APPROVED` 转换；终态请求重复提交返回当前结果且不产生第二次名额变更。
- 被拒绝或取消不占用名额。

### 3.6 志愿活动

#### FR-19 发布和管理活动

已认证机构必须能发布免费公益活动，维护标题、说明、地点（文本 + 高德经纬度）、活动开始/结束时间、报名开始/结束时间、志愿者要求和人数上限。活动不创建群聊。

**验收规则:**

- `starts_at < ends_at`、`registration_starts_at <= registration_ends_at <= starts_at` 且人数上限大于 0，否则返回 `400`。
- 活动开始时间晚于当前时间；机构须为 `APPROVED`，否则返回 `403`。
- `location_lng`/`location_lat` 与 `location_text` 同空或同非空，经纬度越界返回 `400`。
- 发布后为 `RECRUITING`；到开始时间转为 `IN_PROGRESS`，到结束时间转为 `ENDED`。
- 机构可在开始前取消；结束或取消后不可报名。
- 只有所属机构可修改或取消活动。

#### FR-20 志愿者报名与机构审核

志愿者可报名招募中的活动，所属机构可批准或拒绝。志愿者可在活动开始前取消自己的待审核或已批准报名。

**验收规则:**

- 同一志愿者对同一活动最多一条非取消报名，重复报名返回 `409`。
- 只有 `VOLUNTEER` 可报名；只有活动所属机构可审核。
- 批准人数不得超过上限；并发审核需原子校验。
- 审核结果和活动取消必须生成通知。
- MINI 不创建会话、消息或活动群。

#### FR-21 志愿者可服务状态与附近匹配

志愿者必须能显式开启或关闭“可接收附近求助”，并在授权后上报当前位置。关闭状态、过期位置或超出半径的志愿者不得成为报警接收人。

**验收规则:**

- 默认可服务状态为关闭，必须由志愿者主动开启。
- 位置只用于当前附近求助匹配，不向其他普通用户公开。
- 匹配半径必须配置化；同距离按位置更新时间和稳定顺序选取。
- 志愿者关闭可服务状态后不再接收新广播，但已固化的报警投递保留。

### 3.7 管理与审计

#### FR-22 管理员治理

管理员必须按自身权限查看和处置用户、机构及业务状态。`SUPER_ADMIN` 管理管理员账号和授权；`OPERATIONS` 查看运营数据并处理获授权的机构审核与用户治理。

**验收规则:**

- 权限不足返回 `403`，不能仅通过隐藏按钮限制。
- 管理员不得查看用户密码、完整令牌或无业务必要的实时位置。
- 禁用账号、审核机构和修改权限必须记录操作者、对象、前后值、原因和时间。
- 具备 `VOLUNTEER_REVIEW` 权限的管理员可查看志愿者兼任申请列表并审核（通过/拒绝，拒绝必填原因）。
- 管理员不能删除报警、申请、报名和审核历史。

#### FR-23 运营统计

有统计权限的管理员必须能查看用户数、认证机构数、本月服务申请数、本月报警数、服务项目热度和志愿活动参与情况。

**验收规则:**

- 每个指标必须定义统计时间窗和状态口径，页面显示数据更新时间。
- 统计只返回聚合值，不返回不必要的个人敏感明细。
- 无数据时返回 0 和空列表，不报错或伪造样例值。
- 统计失败应显示不可用状态，不沿用无时间标识的旧数据。

#### FR-24 审计、关联完整性与幂等

系统必须对关键状态变更、管理员操作、报警路由和通知投递保留审计。业务关联同时使用数据库约束与应用层权限校验；创建类关键接口支持幂等。

**验收规则:**

- `schema.sql` 只创建一个 `sullivan` 数据库，不创建旧的服务 schema。
- 服务申请、报名、报警等写入主体 ID 前完成存在性、角色、状态和行级权限校验。
- 数据库或必要基础设施暂不可用时回滚事务并返回 `503`，不得写入半成品记录。
- 审计记录不可由普通业务角色修改或删除，并可通过 `trace_id` 关联请求。

### 3.8 实时会话与长连接

#### FR-25 长连接基础能力

已绑定监护人与受护人之间必须能建立基础实时会话（WebSocket 长连接），实现双向消息中继。会话创建与每条消息转发都必须校验双方仍存在 `ACTIVE` 绑定。`[FULL]` 的语音通话、受护人视角实时共享复用本会话类型，不在 MINI 验收范围。

**验收规则:**

- 双方无 `ACTIVE` 绑定发起会话返回 `403`。
- 会话只有发起方与接收方参与人可接受、拒绝或结束；非参与人访问返回 `403`。
- 会话类型仅 `BASIC`；`VOICE`/`CAMERA`/`LOCATION` 属 `[FULL]`，不得出现在 MINI 可达选项。
- WebSocket 握手必须校验 JWT 与会话参与人；中继每条消息时复查双方 `ACTIVE` 绑定，绑定已解除则拒绝转发。
- 断线后连接池自动注销该连接；会话可重新发起。
- 服务端维护连接池并对空闲连接心跳保活，超时剔除。

## 4. 外部接口与设备约束

| 接口/设备 | 用途 | 失败行为 |
|---|---|---|
| Android Camera2 | 导航图像采集 | 停止提交帧并提示检查权限或摄像头 |
| Android SpeechRecognizer | 语音指令 | 保留按钮操作，不猜测执行 |
| Android TextToSpeech | 本地播报 | 文字加震动降级，提示修复 TTS |
| Android/浏览器定位 | 受护人位置、志愿者附近匹配 | 显示不可用或过期，不伪造位置 |
| 推送服务 | 异步提醒 | 保留站内通知并记录重试 |
| MinIO | 图片资源 | 核心文字信息仍可访问，不阻塞报警 |

## 5. 验收通用规则

1. 每个 FR 至少包含一条正常路径、一条参数异常和一条越权测试；涉及状态的 FR 还必须覆盖非法状态转换。
2. HTTP 语义统一: 参数错误 `400`，未认证 `401`，无权限 `403`，不存在 `404`，冲突 `409`，限流 `429`，依赖不可用 `503`。
3. 写接口成功响应应返回资源 ID、当前状态和版本/更新时间；异步处理返回 `202` 时必须可查询结果。
4. 列表接口必须分页并限制最大页大小；排序字段使用白名单。
5. 所有服务端权限检查以令牌主体和服务端数据为依据，忽略客户端伪造的拥有者字段。
6. `[FULL]` 商业、AI 客服、聊天、视频等功能不参与本 SRS 验收。
