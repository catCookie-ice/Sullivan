# SullivanMINI 开发日记：2026-10-16

**开发主题:** 接入「扫码绑定受护人」与「扫码登录受护人账号」——参考 `参考1/try_1` 的交互，在服务端新建绑定码与登录票据两条链路，在 Android 端补出网络层、登录与监护人主页，并清掉 Compose/Hilt 死依赖  
**适用范围:** SullivanMINI `[MINI]`，`server-java` 与 `client-android/client-ward`  
**关联里程碑:** M3 Android 入口、登录、TalkBack 基线（补充：扫码绑定与扫码登录）

## 1. 今日目标

① 把 `参考1/try_1`（一个 Node demo，验证了「二维码绑定 + 扫码授权登录」这套交互）的功能接入本项目；
② 两个界面都落在 Android 端：受护人出示二维码、监护人扫码；
③ 服务端此前**完全没有二维码概念**（全仓 grep `二维码|扫码|qrcode|zxing` 零命中），因此这套链路要新建；
④ Android 端此前**没有账号体系、没有网络层**，`AndroidManifest.xml` 声明的 `LoginActivity` /
`GuardianActivity` / `VolunteerActivity` **对应文件根本不存在**，所以登录、网络层、监护人主页要一并建起来。

已确认的口径（用户选定，见 §3 的授权决策）：

| 问题 | 结论 |
|---|---|
| 扫码后何时生效 | **扫码即生效**，记为「受护人发起 + 监护人扫码确认」 |
| 绑定码的展示条件 | **仅登录后**可展示；未登录时受护人只能展示登录码 |
| 受护人登录页 | **只做扫码登录**，不做账号密码表单（其它登录方式后续开发） |
| 监护人登录 | 做**账号密码登录**（扫码授权要求监护人已被认证，这一步无法用扫码解决） |
| 二维码在哪几端 | 出示端与扫描端**都只做安卓端** |

## 2. 完成内容

### 2.1 服务端：两张表（`V6__qr_binding_login.sql`）

沿用 `guardian_binding` 已用过的「生成列做唯一约束」写法，把业务上的唯一性交给数据库表达，
而不是靠应用层自觉：

| 表 | 作用 | 关键约束 |
|---|---|---|
| `protectee_bind_code` | 受护人**登录后**出示的绑定码 | `active_code_key` 生成列 + UNIQUE ⇒ **每位受护人同时最多一张 ACTIVE 码** |
| `qr_login_ticket` | 受护人**未登录**时出示的登录票据 | 主键即票据；`secret_hash` 存 `clientSecret` 的 SHA-256，明文不落库 |

两张表的码都由服务端签发，客户端只负责放进二维码。

### 2.2 服务端：八个接口 + 两处小加固

| 方法 | 路径 | 谁能调 |
|---|---|---|
| `POST` | `/api/v1/qr/bind-codes` | 受护人本人 |
| `GET` | `/api/v1/qr/bind-codes/current` | 受护人本人 |
| `POST` | `/api/v1/qr/bind-codes/scan` | 监护人 |
| `POST` | `/api/v1/qr/login-tickets` | **公开** |
| `GET` | `/api/v1/qr/login-tickets/{ticket}` | **公开** |
| `POST` | `/api/v1/qr/login-tickets/{ticket}/exchange` | **公开** |
| `POST` | `/api/v1/qr/login-tickets/{ticket}/scan` | 监护人 |
| `POST` | `/api/v1/qr/login-tickets/{ticket}/confirm` | 监护人 |

`SecurityConfig` 的白名单按**精确路径**新增三条（现有风格就是逐条精确匹配，没有写成
`/api/v1/qr/**` 一把梭）——否则 `scan` 与 `confirm` 这两个真授权点会被一起放开。

两处加固：

- `BindingService.bindViaScan(protecteeId, guardianId)`：外层 `@Transactional`（否则两次提交之间失败会留下孤儿 `PENDING` 行），
  内部显式校验受护人账号 `ENABLED`、`requestBinding`、`acceptBinding`，并把新行的 `is_primary` **写死为 `false`**。
  **显式校验 `ENABLED` 是必须的**：`requireActiveRole` 在 `count > 0` 时直接返回，从不过问账号是否 `ENABLED`；
  而 `requestBinding` 里那个 `ENABLED` 检查针对的是 target（监护人）而不是 caller（受护人）。
- 换令牌复用 `AuthService` 的角色解析（`user_role` 的 ACTIVE 集合，空则回退 `account.roleCode`），
  抽成包级方法——另写一份一定会漂移。

### 2.7 受护人主页刻意不加登录前置

`ProtecteeActivity`（相机障碍检测）是**离线可用**的核心，全工程此前无网络。
因此**不给它加登录前置**：启动路径仍是 `RoleEntryActivity → ProtecteeActivity`，
只在界面上加一个「我的绑定码」按钮，点进去才要求登录。

这既保住了既有的端侧能力，也天然满足「绑定码仅登录后可展示」——
`POST /qr/bind-codes` 要求受护人 Bearer 令牌，`BindCodeActivity` 对未登录用户先走一遍扫码登录。

短码的朗读复用工程已有的 `PromptAnnouncer`：二维码对低视力用户零信息量，
「手动输入兜底」必须**双向可用**——受护人要能把码念给监护人听。

### 3.3 一次显式的授权决策：受护人登录页只做扫码登录

受护人登录页**不做账号密码表单**，意味着「监护人扫码授权」是受护人**唯一**的登录途径；
监护人（在任意设备上）可为自己名下**任一** ACTIVE 绑定的受护人换取一份完整 `accessToken`，
且可**随时重复**。这不是"帮长辈登录一次"，而是长期的账号代持能力。

这是用户明确选定的口径，已按下面的设计把爆炸半径压到最小：

- 唯一的真授权点是监护人的 `confirm`，且**服务端在同一事务内复核 ACTIVE 绑定**，绝不信任客户端传来的候选；
- 令牌**不出现在任何轮询响应**里，只经一次性的 `exchange` 下发；
- `exchange` 需要注册时遗留在出示设备上的 `clientSecret` **同时**匹配 `exchange_code`；
- 票据一次性消费，`CONSUMED` 不可回退；
- 每位受护人同时只有一张绑定码、TTL 120 秒。

**代价必须写清楚**：该路径绕过了「受护人知道自己的密码」这个唯一的持有证明。
一旦监护关系被滥用，受护人**没有第二条独立登录途径**可以自证。
在补上受护人自主登录方式（或绑定解除/申诉流程）之前，这条缺口是真实存在的。

### 4.6 `role` 缺失返回 500 的既有缺陷：已修

上一轮报告的那处缺陷本次**已修**（`RegistrationService.registerUser`）：

```java
// 改前：Set.of 的不可变集合在 contains(null) 时抛 NPE
if (!Set.of("GUARDIAN", "VOLUNTEER").contains(request.role())) { ... }
// 改后：先判 null，null 与不在白名单一律落到同一句 400
if (!"GUARDIAN".equals(request.role()) && !"VOLUNTEER".equals(request.role())) { ... }
```

**为什么在校验层堵不住**：DTO 上 `role` 只标了 `@Pattern(regexp = "GUARDIAN|VOLUNTEER")`，
而 `@Pattern` **不校验 `null`**（`@NotNull` 才管）。所以"省略 `role`"能通过请求校验，
第一个碰到 `null` 的就是服务层这一行 —— 这也是该缺陷能在公开接口上活到现在的原因。

补了两个用例钉住它：`missingRoleIsABadRequestNotAnInternalError`（断言 `400` +
`verify(userAccountMapper, never()).insert(...)`，即校验没过就不许落数据）与
`unknownRoleIsRejectedAsBadRequest`（`PROTECTEE` 这类越权自助注册同样 400）。
`RegistrationServiceTests` 从 2 例增至 4 例，服务端全量从 113 例增至 **115 例，全绿**。

> 同类的 `Set.of(...).contains(...)` 写法在 `AdminRegistrationService.java:68` 与
> `RealtimeHandshakeInterceptor.java:57` 也有，但那两处的参数分别是 `@NotBlank` 字段与
> 数据库读出的非空列，**拿不到 `null`**，因此不构成同一缺陷，本次未动。

## 5. 已知风险

| # | 风险 | 说明 |
|---|---|---|
| 1 | **明文 HTTP** | 后端是 `http://<IP>:8642`，需 `usesCleartextTraffic="true"`。在明文下票据与最终令牌对**同网段任何人**可见，`clientSecret` 的"设备绑定"在网络攻击者面前完全无效——而网络攻击者恰是扫码登录最现实的威胁模型。使用范围必须限定在**可信局域网**，或先把后端放到 TLS 后面 |
| 2 | **无法吊销** | `JwtService` 只有 `issue/parse`，无 jti / 黑名单 / refresh，TTL 1800s。所以「一次性消费」只约束票据，**约束不了已发出的令牌**。（本次**有意**没给扫码路径签更短的 TTL：那会逼着老年受护人反复叫监护人来扫，且不解决真正缺的那一环） |
| 3 | **限流未做** | `POST /qr/login-tickets` 公开可调用，无 IP 限流即资源耗尽面（写 MySQL + 轮询读）。与 `参考1` README 记的"限流与锁定"缺口一致 |
| 4 | **绑定码熵偏低** | 12 位、30 字符字母表（约 59 bit），不是计划里的 ≥128 bit。**这是有意取舍**：低视力用户要能把码**念出来**，所以字母表去掉了 0/O/1/I/L/U。补偿是 TTL 120 秒 + 每位受护人同时一张 + 单测钉死字母表 |
| 5 | **无 Redis** | 登录票据不用 Redis，DB 行是唯一权威，原子性靠对 `status + version` 的一次 CAS UPDATE。理由：票据生命周期只有两分钟且一次性，引入 Redis 只是多一个必须与库一致的真相源 |
| 6 | **首次构建需联网** | 拉 `com.google.zxing:core:3.5.3`（本地 Gradle 缓存里原本没有） |
